# DataQueryExecutor 查数底线与 Schema Chunk 的分层约定

**运行时真相源**：`app/services/ai/executors/prompts.py` → `DataQueryPrompts.GLOBAL_GUARDRAILS`
**配套 Schema 侧**：`app/services/metadata_rag_service.py` → `render_table_schema_yaml` 的 chunk note
**本文件**：架构说明与措辞草案（运行时以代码为准）

---

## 1. 分层约定（本文件的核心结论）

| 层次 | 内容 | 存放位置 | 特征 |
| :--- | :--- | :--- | :--- |
| **字段语义**（是什么） | `partition_fields` / `index_fields` / `dimension_role` / `hierarchy_group` / `hierarchy_order` 各自代表什么 | **随 Schema 走**（chunk note，会进入向量索引正文） | 描述性、无命令动词、简短 |
| **行为规则**（怎么用） | 何时该用、禁止什么、缺条件怎么办 | **只留 `GLOBAL_GUARDRAILS`**（代码） | 单一权威、可命令 |

**为什么必须这样分：**

1. **改策略的成本**。chunk note 会进入向量索引正文（本地 Redis 向量 + 同步出去的 RAGFlow 知识库）。行为规则写在那里，意味着每次微调查询策略都要**全量重建元数据向量索引**，RAGFlow 模式还要额外重新同步。搬到代码后，**改一次部署即生效**。
2. **口径会漂移**。同一议题在两处各自表述时，很容易一处写"优先"、另一处写"不得"，模型收到互相冲突的指令。行为规则只留一处即可根除。
3. **省 token**。chunk 每命中一次就会重复一遍规则文本。

## 2. 历史问题（这次修正的动因）

同一个议题原先存在 **3 处口径**且互相打架：

| 议题 | ① chunk note（索引正文） | ② `GLOBAL_GUARDRAILS` | ③ 规则 12 |
| :--- | :--- | :--- | :--- |
| 用户没给时间范围 | 「先**收窄时间/数量**或向用户确认」 | 10.1：「先**追问**时间范围」 | 「**必须本轮直接给出结论**……禁止停轮」 |
| 未标注维度的字段能否 GROUP BY | 「**优先用** `dimension_role != none` 的字段」（柔和） | 16：「无该标记的字段**不得**作为分组维度」（绝对） | — |

**两个具体后果：**

- **静默收窄范围**：① 授权静默收窄、③ 又要求必须出结论，模型最省事的解法就是悄悄收窄后照常回答——用户问"订单总量"可能拿到"近一年订单总量"且不被说明。
- **普通分组查询被打坏**：`dimension_role` 默认为 `none`，且为 `none` 时 `build_table_schema_dict` **根本不输出该键**，因此"无该标记"是**默认状态**。字面执行 ② 的绝对禁止，等于"没有任何字段可以作为分组维度"，而"各地区销售额"这类问题必须 GROUP BY。`GLOBAL_GUARDRAILS` 又明确"优先于智能体业务描述"，因此它会压过 ChatBI 智能体自己的"先明确统计粒度"。

## 3. 现行行为规则全文

### 规则 10.1（查询性能）

```text
10.1 查询性能：Schema 中的 partition_fields 标出表的分区字段，index_fields 标出表的索引字段。
当问题本身带有时间/范围条件时，必须把该条件落到对应的分区字段上，不要只写在语义相近的其它字段上；
当问题本身涉及索引字段的等值/范围过滤或 JOIN 时，优先在这些字段上做条件。
禁止为了「命中分区/索引」而添加用户没有提出的过滤条件，也不得臆造过滤取值。
禁止 SELECT *、无 WHERE 的明细全表扫描和无界大结果集；必须设置合理 LIMIT/聚合范围。
若问题缺少范围条件且可能触发大表全扫：允许先执行一次带明确范围假设的探查查询，
但必须在回答中显著说明实际使用的范围与口径（如「以下为近 30 天数据」），
禁止静默收窄范围后当成用户要的全量结论；确有必要时可同时告知范围可以放宽。
```

三处要点：
- 分区裁剪**只落实用户已提出的条件**，不再"必须优先生成过滤条件"（那会凭空造条件）
- 新增**禁止臆造过滤取值**，堵住"为了用上索引而硬加 `tenant_id='default'`"
- 与规则 12 的冲突用**"必须披露"**化解，而不是"静默收窄"或"停轮追问"

### 规则 16（维度与下钻）

```text
16. 维度与下钻：Schema 中带 `dimension_role`（time/geo/category/identifier）的字段是已标注的分析维度，
用户要求「按XX看/按XX拆开/下钻到XX」时优先选用这些字段。
未标注的字段不是禁用项：用户明确点名了某个未标注字段，或问题只能用未标注字段表达时，
照常用它做 GROUP BY，不得以此为由拒绝、反问或改写用户诉求。
禁止 GROUP BY Schema 中不存在的字段，也不得把表名、指标名或 table_desc/term 当作维度字段。
同一 `hierarchy_group` 的多个字段构成一条下钻路径，按 `hierarchy_order` 从小到大=从粗到细，
下钻时切换到同组中 `hierarchy_order` 更大的字段做 GROUP BY。
无法确定下钻目标时，先列出可用维度与层级供用户选择。
```

`dimension_role` 的定位改为**"这是标注过的、可信的维度"**，而不是**"只有它才能分组"**。真正的护栏是"禁止臆造维度"，这条保留。

### chunk note（字段语义，无行为规则）

```text
# 字段提示：partition_fields 标出表的分区字段，index_fields 标出表的索引字段；
dimension_role（time/geo/category/identifier）标出字段的分析维度角色，
hierarchy_group 相同的字段按 hierarchy_order 从小到大构成由粗到细的下钻链。
```

## 4. 契约护栏

`tests/test_chatbi_guardrails_contract.py` 以否定式断言锁定本约定：

- `GLOBAL_GUARDRAILS` **不含**「不得作为分组维度」；**含**「未标注的字段不是禁用项」
- 规则 10.1 **含**「不得臆造过滤取值」「显著说明实际使用的范围与口径」；**不含**「先收窄」
- chunk note **不含**任何行为命令（`先收窄` / `必须优先` / `禁止无界全表扫描` / `不得作为分组维度` / `查询必须尽量命中分区和索引`）
- chunk note **仍含**全部字段语义与既有的表名纪律（`禁止写成 FROM dataset.table_name`）

`tests/services/test_metadata_query_optimization.py` 同步更新：只断言字段语义进入 chunk，不再断言行为规则进入 chunk。
