# 双轴代码评审

代码评审常见的两种失效：只看着代码挑风格，忘了需求是不是做偏了；或者只对需求，代码里的坑全放过去。

## 适合用它的时候

- 分支要合了，想在自己 merge 前过一遍
- 帮别人看 PR，但不确定该从哪儿下手
- 改动很大，一个人看完容易漏

## 两条轴

| 轴 | 问的问题 | 依据 |
|---|---|---|
| Standards | 这段代码符合我们项目的写法吗 | 仓库里文档化的编码规范 |
| Spec | 这次改动真的实现了原始需求吗 | 来源 issue / spec |

两条轴用并行的子智能体各跑一遍，最后并排贴出来。分开跑的好处是互不干扰：审规范的不会因为"需求做得挺对"就放过命名问题，反之亦然。

## 注意

基线（commit / branch / merge-base）要说清楚。基线选错，整个评审都在看错误的 diff。
