为什么是服务端分页 推荐

  • 库数量上限在 RAGFlow 侧，几百到几千都正常；前端全量分页只是少渲染，内存和首屏请求没省。
  • 后端已经有 page/page_size 和全量 total，只差把 过滤条件也下沉。
  • 列表页的 「全部选中」必须明确是"当前页"还是"全部结果"：这里按当前页全选，跨页勾选保留，避免一次误删 860 个库。

交互细节（都在原型里可点）

  • 每页条数改变 → 回到第 1 页，而不是停在越界的页码。
  • 搜索/筛选/排序改变 → 回第 1 页，并清掉"当前页全选"，勾选保留。
  • 总页数 ≤ 7 显示全部；否则 1 … 当前±1 … 末页。
  • 底部条常驻（列表内部滚动），不随表头粘顶跑掉。

待确认 风险

  • "全部知识库"计数：total 要在过滤后计算，否则分页条写"共 860 个"、列表里却只有 12 个。
  • 批量删库的"全选"语义要在文案里写死，不能只靠复选框。
  • 后端每次仍会全量拉 RAGFlow（60s 缓存）：分页解决的是渲染，不是回源成本。

树为什么不做页码 结论

  • 树是空间记忆：用户靠"在哪个部门下面"找东西，翻页会破坏位置感。
  • 展开状态、当前选中、右键菜单都挂在节点上，翻页后这些状态要么丢、要么对不上。
  • 树天然有分组这个维度，用"分组折叠 + 组内增量"已经能控制住 DOM 数量。

落地要点

  • 每组默认渲染 6 条，点一次 +10，只在需要时 append，不重排全树。
  • 分组头显示的是该组真实总数（含未渲染的），不是已渲染条数。
  • 树底固定一行"已显示 120 / 860 · 加载更多"，让人知道还没到底。
  • 搜索时切平坦结果列表（带部门路径后缀），不再套部门层级，避免"命中项藏在折叠组里找不到"。

搜索必须下沉 依赖后端

  • 现在树搜索会预加载所有库的文档列表来比对文档名（并发 4 + 300ms 防抖），库一多就是一串 RAGFlow 请求。
  • 分页之后"本地全量过滤"直接失效：搜索必须变成服务端 keyword，并返回命中总数。
  • 文档名搜索要么后端跨库检索，要么明确降级为"仅按库名/负责人/ID 搜"。

顺带：聊天资源抽屉 另一处

  • 抽屉里"库 → 文件"是第二份文件列表（KnowledgePortalDrawer），每库固定拉 100 条。
  • 它适合「还有 N 份 · 加载更多」而不是页码：抽屉本身是窄的滚动容器。
  • 如果先做库页面的分页，记得把这个调用点一起收口，否则 100 条以上仍然静默丢失。

关键取舍：文件夹 vs 分页 建议

  • 现在的表格是树形展开（文件夹行 + 子层缩进 + 拖拽移动）。树形 + 页码 = 翻页后展开状态对不上、文件夹可能被切到两页。
  • 建议改成「进入文件夹」导航：点文件夹 = 按路径过滤，面包屑回退，分页只作用在当前过滤结果上。
  • 文件夹本身不占分页行数，用顶部文件夹 chips 承载；文档总数与分页条始终一致。
  • 拖拽移动保留：拖到 chip 上即移动（原型里没做拖拽，视觉上留了位置）。

三种视图怎么分页

  • 列表 / 网格：共用同一个 page/page_size，切换视图不重置页码。
  • 解析看板：按状态分列，每列只取前 8 条 + 「该状态共 N 份 → 切到列表筛选」，不参与分页。
  • 看板不翻页是刻意的：它的用途是"看哪堆积压"，不是逐条读。
  • 搜索/状态筛选变化 → 回第 1 页；清空后回到原页码会让人困惑，所以统一回 1。

必须先修的后端 阻塞

  • total 改成 RAGFlow 返回的真实总数（响应里本来就有，_extract_documents 把它丢了）。
  • sort 落到服务端：否则"第 2 页"是本地排序后的切片，翻页顺序不稳定。
  • 轮询/上传后刷新要只刷当前页，不能回第 1 页，否则解析中的文档会跳走。

接口契约：现有能力 / 缺口 / 要加的参数

接口现状分页所需结论
GET /api/portal/ragflow/datasets 支持 page/page_size，total 是全量真实值；但没有 keyword / 部门 / 可见范围 / 排序参数，过滤都在前端。 加 keyword、visibility、dept_id、sort，并在过滤后再算 total。 改后端
GET /api/portal/ragflow/datasets/{id}/documents 支持 page/page_size/name，但 total 返回的是当前页条数。 返回真实 total；补 sort、status、folder 过滤。 阻塞
list_documents()（RagFlowClient） 只回 docs 数组，total 在 _extract_documents 里被丢掉；>100 条时循环拉多页。 返回值带上 total，并支持按 total 精确分页。 阻塞
useKnowledgePortal.ts（聊天资源抽屉） 每库固定 page_size=100，只拉第一页；抽屉里是滚动容器 + 最大高度，看不出"还有多少"。卡片头部展开即请求。 首屏只取前 20 条 + 「还有 N 份 · 加载更多」；或直接复用 PaginationBar（抽屉里用"加载更多"更合适）。 改前端
列表缓存 datasets 有 60s TTL + 单飞锁；documents 无缓存。 分页后每页一次请求，缓存窗口够用；翻页命中缓存才不会卡。 够用
前端分页组件 没有统一组件：Users.vue / AuditLogs.vue 各写一套，样式不一致；只有 parsePageInput 是共用的。 抽 usePagination + PaginationBar.vue（总数/页码/每页条数/跳页）。 补组件

方案对比 三选一

  • A 服务端分页（推荐）：列表页页码、文件列表页码、树增量。
    优点：规模无上限、首屏快、内存稳。
    代价：后端要补参数，搜索/排序必须下沉。
  • B 前端全量分页：仍拉全量，只在内存里切。
    优点：改动最小，一天能上。
    代价：860 个库、1286 份文档时首屏照样慢，只是 DOM 少了 —— 治标。
  • C 虚拟滚动：不翻页，滚到哪渲染到哪。
    适合树和看板；表格里"共 N 条 / 跳到第几页"的诉求还得靠 A。
  • 建议组合：列表 + 文件表格走 A；树走 A（增量）+ C（虚拟滚动，可选）；看板走"每列前 N"。

改动清单（确认后按此实现）

  • 后端：list_documents 返回 total；/datasets 补 keyword/visibility/dept/sort；文档接口补 sort/status/folder。
  • 前端：新建 PaginationBar.vue + usePagination.ts；KnowledgeBaseManagement 的列表页与树改接分页数据源。
  • DocWorkspace：树形表格 → 文件夹筛选 + 面包屑；列表/网格共用 page；看板每列前 8。
  • 状态：搜索/筛选/排序变更统一回第 1 页；轮询只刷当前页；每页条数写进 localStorage。
  • 边界：跨页勾选保留且提示；批量操作只作用于已勾选；翻页时保留滚动位置。
