平台备注说明

现状卡点（左侧窄树里发生了什么）

红点是可复现的高频操作阻力，按影响排序。

1 文档和部门共用一个滚动轴：展开一个库后，树长到几百像素，切库要重新滚回上面找知识库；滚动位置不记忆，刷新后全部展开。
2 384px 放不下文档信息：只有文件名，没有解析状态、切片数、大小、上传人；长文件名一律截断，重名文件无法分辨。
3 文件夹只有一层：folder_structure 是「文件夹名 → 文档ID数组」，同名冲突、不能嵌套，「制度文件 / 2025 年度」这种层级做不出来。
4 移动文档只能悬停点按钮：每个文件要 hover → 点「移动到文件夹」→ 下拉选目标，一次只能移一份；没有拖拽，不能批量移动。
5 没有排序 / 筛选 / 分页：接口支持 page/page_size 但前端一次拉 100 条，超过就看不到；找「哪些解析失败了」只能逐个点开。
6 未分类是无底洞：根目录平铺，新上传的文档全部落在最底部，没有任何「待整理」入口提示。
P0
先让文档可浏览

主区表格 + 表头排序 + 状态/类型筛选 + 多选批量条。不动数据结构，只重排页面，1 个页面内可完成。

P1
目录升级为多级

新增 folders[]（id / name / parent_id）与 assignments{docId: folderId}，旧 {名称: [ids]} 读取时视作根级文件夹，向后兼容。拖拽移动、批量移动同时上线。

P2
找得到 / 管得动

未分类收口、最近访问、收藏、保存筛选、批量打标签、解析看板；接口补 sort / status / total 与分页。

取舍
为什么不直接上「文件夹树」

再深一层的树会让左栏更挤，且与「部门 → 库」两级语义打架。浏览交给主区域（面包屑 + 列表），树只承担选库，是更稳的职责切分。
