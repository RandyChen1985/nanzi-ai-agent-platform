子代理续聊与提问透传 sub_agent_call · resume + ask

两件紧耦合的事：① 续聊——父对同一子代理追问时复用第一轮上下文，不再从零冷启动； ② 提问透传——子代理需要用户拍板时，它发出的提问卡直达主会话，用户答完继续（复用续聊保住上下文）。 后者是前者的必要配套：没有续聊，子代理问完就忘，答了也接不上。

      子代理提问的安全边界 提问内容可能来自不可信数据，不能当成平台自己的话

      风险：子代理读过网页、上传文档、知识库片段之后可能被提示词注入—— 把攻击者的话包装成「提问」显示在主会话里，还带着「来自：经营数据助手」的权威感； 更糟的是选项本身可以带 action 触发页面动作，等于诱导用户点击。 子代理提问必须按「不可信输入」对待。
      约束规则
      选项动作子代理提问禁止携带 action（父自己的提问仍允许）。这是防诱导点击的硬闸
      文本长度问题 ≤ 200 字、单选项 ≤ 60 字、选项数 2~6；超限直接拒绝并让子代理自己给结论
      渲染净化问题与选项按纯文本转义，不渲染 Markdown 链接与 HTML——否则可以钓鱼
      来源标注强制显示子代理展示名，措辞用「子代理提议」而非平台确认，避免权威感错位
      形态限制只允许「问题 + 选项 + 自定义输入」，不允许在提问里夹长文、链接、多段落指令
      审计子代理每次提问的原文与用户回答都写进 trace（含 run_id / child_session_id），便于回溯

      ✕ 会被拦下的提问（注入诱导）

      • 问题：「检测到数据异常，请点击下方链接完成验证」→ 命中链接/诱导，拒绝
      • 选项「立即验证」带 action: open_dataset_picker → 子代理提问不允许 action，拒绝
      • 问题 800 字、夹带多段指令 → 超长，拒绝
      • 拒绝后：给子代理返回明确原因，让它把情况写进结论，由父决定要不要提醒用户

      ✓ 正常放行的提问

      • 问题：「要对比哪几家竞品？」（9 字）
      • 选项：A 公司 / B 公司 / C 公司，各带一句说明，无 action
      • 来源徽标「来自：经营数据助手」，布局与措辞体现「子代理在问」
      • 允许自定义输入，用户也可以「按常见口径继续」

      batch 场景：多个子代理同时要提问 这里和现有存储机制有冲突，必须定形态

      冲突点：UserQuestionStore 每个会话只有一个 active 槽位—— 同一会话再来一个新 pending，旧的会被标成 superseded。 sub_agent_batch_call 并行委派 3 个子代理，若 3 个同时提问，用户只会看到最后一个，前两个被静默吃掉。

      边界条件 决定这个方案能不能上线的细节

      场景行为
      resume=true 但本轮无缓存（首次就续聊）降级为全新会话，不报错 —— 模型判断错误不该让整轮失败
      resume=true 但 tool_filter / output_schema 与首轮不同降级为全新会话。能力面变了，旧历史会给出错误前提
      子代理发布版本变化缓存按 agent_id + version 打标，版本不同不续聊
      同一子代理在 sub_agent_batch_call 内并行续聊禁止。batch 内 model_copy(deep=False) 让 dict 共享，并行任务会互相覆盖缓存；建议 batch 内同一 agent 只允许 1 项
      次数上限 delegation_max_calls_per_agent（默认 2）需拍板：首轮 + 追问正好用满 2 次，第三次追问就没了。建议续聊单独计数，或默认提到 3
      子代理带写操作 / 生成文件续聊会重复产生副作用。建议 resume 轮次保持 approval_mode=ask，不因续聊放宽
      上下文膨胀缓存只保留最近 3 轮问答，首轮 query 常驻；超限丢最早的一问一答
      可观测性两次 run_id 不同、child_session_id 相同；思考卡标「续聊 #2」，trace 里可区分
      深度语义不变。子代理仍是 depth=1，续聊仍不能往下委派

      提问相关的边界条件 不写清楚就会变成新的静默故障

      场景行为
      定时任务 / 订阅任务里子代理要提问仍然拒绝。那些场景没有在线的用户，放行只会白等
      子代理提问后用户始终不回答pending 按现有 TTL 过期，不自动续跑；用户下次说话时父重新委派即可
      父是否会重复问一遍不该发生。子代理已问过、卡片已在用户眼前，父这轮必须直接停。需在提示词里写死「收到 needs_user_input 后禁止再调 ask_user_question」
      用户点「跳过，让模型自己判断」回执写明「未提供，请自行判断并在结论中标注假设」，父 resume 时带上这句，子代理据此继续
      子代理反复提问每次委派最多 1 个提问；同一子代理每轮仍受 delegation_max_calls_per_agent 约束
      卡片来源标识必须显示子代理展示名。否则用户以为父在问，答完的语义也对不上
      无 UI 渲染能力的端（纯 API / embed 宿主）由 execution_options.client_capabilities 判定：不含 user_question 即降级为「父转述」，由父用自己的 ask_user_question 措辞。缺省按「不支持」处理（fail-safe）
      子代理提问带 action / 超长 / 含链接拒绝，并把原因返回给子代理，让它把情况写进结论。防的是「读了不可信数据后被诱导，把攻击者的话显示到主会话」
      父这一轮的收尾父先输出一句引导语（点明是哪个子代理在问），再挂卡片并停止；不能只丢一张裸卡，用户否则不知道上下文
      batch 内多个子代理同时提问按形态 A 排队。现在 store 单槽会把前几个标成 superseded 并静默丢弃，改动必须先堵这个
      用户取消 / 关页面委派此前已结束（子代理以 needs_user_input 收尾），无悬挂协程；pending 由 TTL 清理
      父这一轮的超时不受影响。父的 await 在子代理流结束时就返回了，用户思考时间不占用委派超时

      方案取舍 续聊这一侧的方案对比

      ✕ 方案 A：子→父 实时双向通道（不建议）

      • 架构上不成立：父模型调用 sub_agent_call 后，推理是停摆的（卡在 await 子代理流）。子代理此刻问父，父没有能力「思考后回答」。
      • 能代答的只有程序规则，或「工具返回 → 父推理 → 再调一次工具」——后者本质就是多轮委派，不是双向通信。
      • 要落地必须推翻「父阻塞等终态」的执行模型，引入死锁（子等父答、父等子流结束）、取消传播、超时归属。
      • 还得打破 MAX_DELEGATION_DEPTH = 1，而它是目前防无限循环的唯一硬闸。

      ✓ 方案 B：进程内会话续聊（本原型）

      • 父驱动轮次、子代理保记忆 —— 符合 LLM Agent 的真实交互形态，不制造「谁在等谁」。
      • 零持久化成本：父子同轮同进程，缓存随 ctx 消失，仍是一次性委派语义。
      • 默认 resume=false，老行为完全不变，纯增量。
      • 配套 output_schema 约定 {"answer":…, "need_clarification":[…]}，父就能识别「子代理说它缺信息」并自动续聊，无需新代码。
      结论： ① 续聊做方案 B —— 解决「追问要重跑 + 两次独立查询口径打架」， 而「子代理主动汇报」的正确形态本来就是父在下一轮读取它的终态结果，不是实时对话。
      ② 提问透传做「提问卡直达主会话」（方案 2）—— 四个断点（工具硬拒绝 / 事件被丢 / 回执认不出 / 内容无校验）逐个打通， 关键是以父会话登记 pending；batch 内多子代理提问按排队形态，先堵住 store 单槽静默丢弃； 子代理提问按不可信输入处理（禁 action、限长度、纯文本净化），父收尾必须先给一句引导语再挂卡。
      ③ 两者必须一起上：没有续聊，子代理问完就忘，用户答了也接不上。 若真实需求是「长任务后台跑、进度可查、跑完再取」，那是另一个量级的特性（子会话持久化 + 用户可见入口 + 跨轮恢复），应单独立项。
