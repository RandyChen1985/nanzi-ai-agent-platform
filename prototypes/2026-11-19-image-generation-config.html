图像生成 · 系统设置「图像」分组 + 智能体工具调用闭环

平台目前只有看图能力（read_image 走多模态模型识别），没有画图能力。 本原型给出完整闭环：系统设置 → 图像配好模型服务 → 平台自动向智能体暴露 generate_image 工具 → 用户在对话里说「画一张…」→ 图片直接渲染在消息里，可预览可下载。 四个场景分别是：① 配置界面 ② 对话里实际使用 ③ 智能体里怎么勾选 ④ 调用链路与实测取舍。

参数分组

图像Image Generation

接入一个 OpenAI 兼容的图像生成服务。启用后平台会向智能体暴露 generate_image 工具，用户在对话里说「画一张…」即可出图，图片直接显示在消息中，无需跳转外部页面。

启用图像生成 关闭后 generate_image 不会下发给任何智能体，模型看不到这个工具，也不会产生空调用；已生成的图片与产物链接保留。

模型服务

先定协议，再定地址
同一个网关往往同时提供多种上游协议，同一个模型可能只支持其中一种。先选格式，地址与模型都按它拼装。
接口格式
image_api_format
选错格式的典型症状：404（路径不对）、Model mismatch 或 No available channel（该渠道不支持这个协议）、 以及「出图了但尺寸/张数没生效」（协议不认识这些参数）。改完点下方「测试生成」立刻验证，不用进对话试。
网关另有 Gemini 原生格式 与 通义千问格式，当前版本未接入：前者缺可验证的渠道（响应体结构未能实测）， 后者返回图片 URL 需要二次下载、且同一模型走原生 OpenAI 格式已能正常出图，没有额外收益。
API 地址
image_api_base_url
末尾不要带 /。前两种格式填到含版本号前缀为止（如 https://api.example.com/v1，平台自己接 /images/generations 或 /chat/completions）；Gemini 原生格式填到根地址（如 https://api.example.com，平台拼 /v1beta/models/…）。示例值不是真实网关。
API 密钥
image_api_key
按凭据加密存储（ENCRYPTION_KEY），接口列表中显示为掩码；留空提交表示保持原值不变。此处为原型占位值，不是真实密钥。
模型
image_model
必须与 GET {API 地址}/models 返回的 id 完全一致——手打容易差一个字母就 404，点右侧按钮直接拉列表选更稳。 部分网关会对模型做别名映射：你填的 id 与响应体 model 字段自报的上游名可能不一致，属正常现象，不影响调用。

生成参数

下发给模型的默认值
默认分辨率
image_default_size
用户没在对话里指定比例时用这个。格式必须是 宽x高——实测传 1328*1328（星号） 接口不报错但会静默回退成 1024×1024，平台内部统一按 x 拼接。
允许的分辨率
image_allowed_sizes
勾选的才写进工具说明，模型只能从中挑，避免它编出一个服务端不认的尺寸被静默降级。
请求超时
image_timeout_seconds
秒
覆盖整次 HTTP 往返。实测单张 1024×1024 约 4~5 秒，横版大图约 6~7 秒；给足余量是为了应对排队。
单次最多张数
image_max_images_per_call
张（上限 4）
模型在一次工具调用里最多能要几张。设 1 时每张单独出、单独计费，也最容易看清每张的耗时。
风格前缀
image_prompt_prefix
非空时会拼在用户提示词前面，用来统一企业视觉调性。留空则完全按用户描述生成。

点工具卡可展开入参 / 出参。图片是直接渲染在消息流里的——工具把 PNG 落盘后发布成带签名 token 的 /api/v1/chat/generated-files/… 链接，前端 MessageRenderer 会识别这个前缀并挂上下载按钮，不走 /static/uploads 那种无鉴权裸链。
输入区的参数面板与图片下方的微调胶囊是同一套设计的两个入口：能不说参数就不说，说了也只是「横版 / 竖版」这种话，界面上不出现像素值。
这些选项本质都是提示词词汇，不是接口参数——实测网关对 seed、negative_prompt、quality、background 一律静默丢弃，watermark 虽被接受但出图无差异。所以真正可调的只有 prompt、size、n，面板做的只是把「我要一张什么样的图」翻译成模型听得懂的话，并替用户省掉打字。代价是注入的词越多、用户自己的描述占比越低，因此维度只开风格与色调两项。
「画面内不要出现文字」曾做过一版开关，因面板过挤被去掉（需求方：选项太多）。但实测结论值得留在这里——同一句「咖啡品牌海报」，不加尾缀会印出一整段乱码（RETAICRUFE / THIHERICUSE），只说「不要文字」只压到剩一个大字（RORON），而写成「构图上只保留插画主体，不要排版任何文字、字母、数字或水印，标题位置留白代替」才能做到零文字。关键在末尾给出替代方案，否则模型会继续拿文字填版面。将来若重新加回，照这句措辞抄。

工具的可用性有两道闸：系统设置 → 图像 → 启用图像生成是总闸（关了整个平台都没有这个工具）， 这里勾不勾是每个智能体的开关。总闸关闭时本行置灰，勾了也不会生效，避免配好了却不生效的困惑。新建智能体默认不带这个工具，需要谁用就手动勾谁——生图有成本，不该默认对所有智能体开放。

为什么做成「内置工具 + 系统设置开关」，而不是别的形态
候选形态它能解决什么为什么这次不选
采用内置工具 generate_image 用户在对话里说一句就出图，图直接进消息流与产物库；配置集中在「系统设置 → 图像」，一处管住密钥与尺寸。 —（代价是只在平台对话内可用，但这正是本次要补的缺口）
外部 MCP 服务 可被 Claude Desktop、Cursor 等外部客户端复用同一套生图能力。 配置会散成两处（MCP 管理 + 系统设置），权限和产物托管各一套；平台内还得指望模型自己判断该调 MCP 而不是别的东西。已经有 text_generate_image 这类 MCP 工具在跑，正好说明这条路上手门槛高、体验不统一。
独立「绘图工作台」页面 适合精细调参、批量出图、反复重绘。 用户得离开对话切到另一个页面，做不到「说着话就出图」。可以作为后续增强，但不是第一版的核心场景。
技能包（Skill） 把行业提示词模板沉淀下来复用。 技能本质是提示词 + 脚本，解决不了「从哪调模型」这个问题——底层仍然缺生图能力。等工具上线后，技能可以作为它上面的模板层。

关键取舍（都来自刚才的实测，不是推测）
决策点选择依据 / 原因
默认请求通道 用POST {base}/images/generations（原生 OpenAI 图像格式） 实测同一模型 Qwen-Image-2.1-Turbo：size 真实生效并回显（1664x928 出图 6.4s，像素尺寸吻合），n=2 一次回两张，参数写错会明确报 invalid size format。这三件事在 chat 通道上都做不到。
是否保留 chat 通道 保留作为可选项 chat 通道兼容性更广（模型 id 大小写都能匹配、网关普遍支持）。代价是：尺寸格式错了不报错、静默回退 1024×1024，一次只能出一张，且同一模型出图体积约 0.9 MB（原生格式 5.6 MB，画质细节更足）。
为什么做成可配置 用设置项 image_api_format 三种格式是同一个网关对不同上游暴露的协议，同一模型未必都支持：实测 qwen-image-21-turbo 走 chat 能出图，走 /images/generations 直接 503 model_not_found（必须精确写 Qwen-Image-2.1-Turbo）。写死一种迟早卡在某个网关上。
尺寸格式 强制宽x高，平台侧统一拼装 chat 通道下 1328*1328 不报错但静默回退 1024×1024；原生图像格式下则直接报 invalid size format, must be WxH。两种协议表现不同，但都要求 宽x高，所以前端只给勾选项、不让手打。
图片怎么给前端 复用generated_file_service 发布 artifact 已有 /api/v1/chat/generated-files/<id>?token=… 带签名、30 天有效，MessageRenderer 会识别并渲染。避免新增无鉴权的 /static/uploads 裸链。
工具名 generate_image 与既有的 read_image 成对，语义一眼可辨；也和外部 MCP 的 text_generate_image 区分开，正好借这次把两条链路收敛到平台内置这条。
开关关闭时 不注册而非注册后报错 工具说明会占系统提示词的篇幅，模型也可能对着不可用的工具反复尝试。直接从工具清单里摘掉最省事。
失败处理 超时读配置；网络错误重试 1 次；其余错误原文回给模型 模型看到「401 密钥无效」能直接告诉用户去改配置，比工具内部吞掉错误、只报一句「生成失败」有用得多。
用户怎么调参数 三层默认自动 → 结果上微调 → 显式面板 普通用户根本不知道 1664x928 是什么，所以第一层是什么都不选：工具说明里内置「场景 → 尺寸」映射（大屏/主视觉→16:9，手机推文→9:16，头像/图标→1:1），模型按用户的话自己判断。 不满意时用第二层——出图后下方直接给「再来一版 / 换成竖版 / 换个风格」几个胶囊按钮，点一下就把追问填进输入框。 只有想精确控制的人才展开第三层面板，而且面板里画的是形状和「16:9 横版」这种说法，不出现像素值。
面板选的比例怎么传到后端 走对话拼成结构化前缀随消息发出 前端把面板选择渲染成一句带参数的上下文（如 [生成参数] 比例=16:9 风格=扁平插画 张数=2）附在用户消息里， 模型据此填 generate_image 的入参。不新增消息协议、不改 runtime，第一版最省事；界面上则只显示成几个可删除的 chip。

已确认的四条口径（本轮评审定的）

按这个范围实现第一版，不多铺。

  • 工具默认不勾选：系统开关打开只是「平台具备这个能力」，具体哪个智能体能用，由管理员在智能体工具清单里手动勾——新建智能体默认不带上。
  • 第一版只做文生图：不接参考图 / 图生图，参数面收窄到 prompt / size / n 三个。
  • 不做配额：不限制每日张数，先看实际使用量再决定要不要加。
  • 分组放在侧栏最末：「其他参数」之后。

本期不做、但已经留好位置的部分

接口与结构上都留了扩展位，后续加不改现有形态。

  • 参考图 / 图生图：接口本身支持传 image_url 参考图（实测「换雪夜背景 + 加红围巾」能保持原画风），等第二版再把参数面打开。
  • 提示词增强：用主模型把用户一句话扩写成更完整的绘画提示词，明显提升出图质量，代价是多一次 LLM 调用与延迟——适合放在「高质量模式」开关后面。
  • 审计日志：谁在哪个会话生成了什么图、耗时多少，接现有审计链路即可。
  • 配额与计费：如后续需要，按 knowledge_quota_* 的现成范式加，不影响工具本身的接口签名。
