知识库编辑权限范围 · 让「能看的人」可选是否也能改

现在的口径分两种：授权成员恒为只读（两级写权限都不含他们），而 TEAM 库的归属部门成员本来就能改文档 （resolve_knowledge_dataset_access 里已经在 content_writable_ids 里）。所以要做的不是「新开一层权限」，而是 把这份编辑权交给库的管理者按库配置：public 库可选「谁能编辑」，TEAM 库可选「部门成员能不能编辑（默认能）」。 策略存进 knowledge_base_metadata.extra_config，按钮前置条件是 element:knowledge:edit。

权限矩阵（加完这块之后）

能力管理员归属人被授权（只读）被授权（可编辑）
查看 / 检索✓✓✓✓
改文档内容（上传/删除/解析）✓✓✗✓
改库设置 / 可见范围✓✓✗✗
分配授权成员✓✓✗✗
删库 / 转移归属✓✓✗✗

关键边界：编辑权 ≠ 管理权。开了「可编辑」的人能改文档，但不能改这个库归谁看、谁被授权——否则他可以把库改成公开再拉人进来。

数据落点

  • knowledge_base_metadata.extra_config 里加一段命名空间，不动表结构、不加迁移：
{
  "edit_policy": {
    // public 库：readonly（默认）| granted | all_viewers | selected
    // team  库：readonly | team_members（默认，= 现状）| selected
    "mode": "readonly",
    "editors": [                 // mode=selected 时生效，只支持具体用户
      { "user_id": 178, "user_name": "chenxiaolong", "real_name": "陈小龙" }
    ],
    "updated_by": "chenxiaolong",
    "updated_at": "2026-11-05T17:05:00+08:00"
  }
}
  • 读取侧只认 extra_config.edit_policy，缺失/非法值一律按 readonly 兜底 —— 老库不需要数据回填。
  • 判定仍在 resolve_knowledge_dataset_access 一处收口：把策略并进 content_writable_ids，不新增第三套集合。

几个必须先定死的语义

  • TEAM 库现在就是「部门成员可编辑」：判定函数里部门成员（含下级）本来就在 content_writable_ids 里。所以部门级这个开关是允许收回去，不是新开权限——默认值必须保持 team_members，上线当天行为才不会变。
  • public 库默认 readonly：被授权成员现状是只读，默认值必须对齐。
  • granted 与 all_viewers 的差别只在「默认库」：accessible_ids 有两个来源——显式授权与系统默认库。granted 只给前者编辑权，all_viewers 连默认库带来的全员可见者也给。没有这个差别，两档就是同一个东西。
  • 不支持角色：selected 只选具体的人。角色授权是另一条链（granted 已经按角色生效），编辑权不跟角色走，避免「角色成员一变动，编辑权悄悄扩散」。
  • private 库不显示这个设置，也不支持 selected。
  • 不做申请编辑权：KnowledgeAccessRequest 只处理访问申请，不扩展。
  • 收窄立即生效：判定是每次请求现算的，从 all_viewers 改回 readonly 后，下一个写请求就被拒。

接口改动（最小集）

  • PUT /api/portal/knowledge/datasets/{id}/edit-policy：body 为 {mode, editors}，后端校验「管理员或归属人」，写进 extra_config，落一条 KnowledgeAuditLog。
  • GET 侧直接复用现有数据集详情返回，把 edit_policy 一起带出来，前端不用多打一次请求。
  • 写操作端点（上传/删除/解析文档）已经是 require_dataset_write_access，不需要逐个改——判定函数扩展后自动生效。
