MCP 工具 · 参数级凭据注入

现在凭据只能填进 MCP 的 HTTP Header。但真实场景里更多是「工具方法的入参要密钥」—— 查 12306 要 api_key、调内部 CRM 要 tenant_token。这些值既不该让模型编， 也不该让用户硬编码在提示词里。本原型对比三种打通方式。

方案 A

工具级声明 + Schema 剔除

管理员在工具参数上标记「来自凭据」，该参数从模型可见的 schema 里移除，运行时按用户绑定注入。

模型看不到 → 不可能编值
方案 B

只绑定，不动 Schema

模型仍能看到并填写该参数，注入层在调用前用凭据值覆盖它。

改表最少，但值可能被覆盖
方案 C

按用户动态 Schema

工具注册时查当前用户的绑定，动态删掉他绑过的参数。

同一工具对不同人长得不一样

MCP 服务详情

mcp-public-admin-hcp · 8 个工具

点开工具，在每个参数右侧点 钥匙图标 标记「这个值从凭据中心取」。标记后该参数不再出现在模型可见的参数列表里。

已标记的绑定槽位

槽位一旦标记就固定下来，用户绑定挂在它上面。

标记参数后这里会出现槽位

槽位怎么拼

// 消费者 = mcp_server（复用现有绑定表）
consumer_type = "mcp_server"
consumer_id   = "<server_id>"
slot          = "arg:<短工具名>:<参数名>"

// 例：
arg:get-interline-tickets:api_key
arg:query-customer:tenant_token
为什么带工具名：同一个服务下多个工具可能都有 api_key， 不带工具名会互相覆盖。用 : 后的短名（get-interline-tickets）， 不带服务名前缀——consumer_id 已经是服务了。

我的 MCP → 平台服务

mcp-public-admin-hcp

管理员绑了全局的，这里直接显示「管理员已配」——用户零配置就能用； 绑自己的会覆盖它。同一个工具，张三绑他的 key、李四绑他的，互不可见。

全部绑定完成。这个服务对这个用户的出站连接会按次隔离——不会和他人的串号。

三道闸门仍然生效

1
平台策略：secret_policy_* 四开关，脚本类默认关。
2
用户偏好：个人在凭据中心里允许的场景。
3
凭据自身：allowed_scenarios 要含 mcp、allowed_hosts 要含该服务域名。
参数级注入不新增闸门，走的是和 Header 完全相同的那一套。只是槽位前缀从 header: 变成 arg:。

没绑会怎样

×
和现在的 Header 一样：调用直接失败，不退回空值、不退回模型编的值。
!
报错要说清是哪个参数没绑 —— 「凭据未填」太笼统，用户不知道去配哪个。

注入发生在哪一行

        

          
# app/services/ai/tools/mcp_factory.py
async def _execute(**kwargs) -> Any:
    # 别名映射（现有）
    kwargs = {alias_to_param.get(k, k): v for k, v in kwargs.items()}

    # ← 新增：按 arg: 槽位注入
    kwargs = await apply_mcp_arg_bindings(
        tool_record, kwargs,
        user_info=user_info,
        denials=denials,
    )

    async for item in stream_remote_tool_with_progress(
        server_id=tool_record.server_id,
        tool_name=raw_name,
        arguments=kwargs,
        ...
    ):
        yield item

三个方案怎么选

        

          

            
维度ABC

            
              
模型看不到密钥参数是否是

              
表结构改动1 个字段无1 个字段

              
工具定义稳定是是否

              
提示词缓存友好是是否

              
用户绑了就能用需管理员先标是是

            
          

          

            建议 A。B 的问题不是「实现麻烦」，而是语义不对：模型被告知有这个参数、
            还给了描述，它一定会填；平台再默默覆盖，等于骗了模型一次，日志里也看不出谁给的。
            C 会让同一工具对不同用户长得不一样，Agent 的工具缓存和提示词前缀全都要按用户重建，得不偿失。
          

        

      


      

        
A 的代价

        

          

            1
            
需要管理员先标记。用户不能自助把一个参数变成「凭据参数」——否则模型看到的
            schema 就跟着用户变了，回到方案 C 的坑里。

          

          

            2
            
远端改了参数名会失联。同步工具时如果 api_key 改名成
            access_key，绑定槽位就废了。需要在同步逻辑里检测并告警。

          

          

            3
            
嵌套参数暂不支持。只处理 properties 顶层。像
            {"config": {"api_key": ...}} 这种深层结构先不做——占了少数，实现成本翻倍。
