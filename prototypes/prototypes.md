# 原型规范（prototypes/）

本目录存放**需求评审用的静态 HTML 原型**，也就是「先做原型、你确认后再实现」这条流程里的产物。
它不参与构建、不进镜像路由，纯粹给人用浏览器打开看。

## 一、总览导航

打开 [`index.html`](./index.html) 可以看到全部原型的列表：日期、标题、类型，支持搜索（`⌘K` / `Ctrl+K`）。

**这个页面是脚本生成的，不要手工编辑：**

```bash
python prototypes/build_index.py
```

脚本会扫描本目录所有 `YYYY-MM-DD-主题.html`，读取每个文件的 `<title>`，重写 `index.html`。

## 二、命名规范

```
YYYY-MM-DD-主题.html
```

| 部分 | 规则 | 示例 |
|---|---|---|
| `YYYY-MM-DD` | 原型**首次创建**的日期，不是提交日期 | `2026-11-02` |
| `主题` | 小写英文，用连字符分词，2~4 个词，能看出是哪个功能 | `knowledge-doc-workspace` |
| 扩展名 | 一律 `.html` | — |

补充约定：

- **一个需求一个文件**。同一需求的多套方案做在同一个文件里（tab 或左右并排），不要拆成 `xxx-a.html` / `xxx-b.html`。
- 确实需要独立成组时，用 `-variants` 后缀，如 `2026-10-30-timeline-variants.html`。
- 文件名里**不要**出现 `mock`、`prototype`、`test` 这类冗余词——目录本身已经说明了。
- 下划线不用，统一连字符。
- 改名后必须重新跑 `build_index.py`，并同步更新引用它的文档（`tests/CHECKLIST.md`、`docs/superpowers/**`）。

历史上有过 `html/mock/`、`docs/mockups/` 两处存放点，已统一收敛到本目录，不要再往别处放。

## 三、文件内部规范

1. **自包含**：CSS、JS 全部内联在同一个文件里，不引用外部 CSS/JS/图片/字体（包括 CDN）。要求双击就能用浏览器打开、断网也能看。
2. **`<title>` 必填**，格式为 `功能 · 做了什么`，例如：
   ```html
   <title>知识库 · 文档组织管理优化原型</title>
   ```
   总览页的标题直接取自这里，写清楚才找得到。
3. **多方案**要有方案编号（`方案 A / B / C`）和一句话取舍说明，方便对着选。
4. **假数据要像真的**：用真实感的项目名、人名、时间，不要 `foo` / `测试1` / `asdf`。
5. **可点击优先**：至少让主要交互（切换 tab、打开抽屉、勾选行）能点，静态截图做不到的事情正是原型存在的意义。
6. 可选：给非默认类型标注
   ```html
   <meta name="prototype-kind" content="方案对比">
   ```
   不写时脚本按标题关键词推断（`交互原型` / `方案对比` / `效果预览`）。

## 四、新增原型的流程

1. 在 `prototypes/` 下新建 `YYYY-MM-DD-主题.html`，按上面第三节写。
2. 跑 `python prototypes/build_index.py` 刷新总览。
3. 在 `tests/CHECKLIST.md` 对应需求行里，把这个原型路径写进「改动文件」列。

实现完成后：

- 原型**保留不删**——它是这次需求的评审记录，日后追溯设计理由要看它。
- 只有确认完全无价值时才删除，且必须同步跑一次 `build_index.py`。

## 五、和其它目录的分工

| 目录 | 放什么 | 不要放什么 |
|---|---|---|
| `prototypes/` | 可交互的 HTML 原型、方案对照页 | 实现代码、接口文档 |
| `prototypes/shots/` | 原型配套的截图、前后对比图 | — |
| `prototypes/resource-cards/` | 某个原型的子资源（css/图为一体的小项目） | — |
| `docs/diagrams/` | 架构图、流程图 | 交互原型 |
| `docs/html/` | 对外发布的技术长文 | 原型 |
| `docs/superpowers/` | 需求规格与实施计划（引用原型路径） | 原型本体 |
