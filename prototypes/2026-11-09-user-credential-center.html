凭据中心 · 用户级密钥管理与自动注入

现状：平台里有关「凭证」的东西散在四套互不相通的机制里 —— 系统配置的 is_secret（值明文落库）、 工具参数的 {user.xxx}（只有身份没有密码）、${CREDENTIAL:...}（只是个"未填"标记）、 MCP 的 auth_headers（加密但只服务 MCP）。同一条 token 要在三个地方各存一份，轮换必漏。 而工具调用的入参以明文落进 ai_agent_execution_traces，会话历史、Redis 运行态同样没有脱敏。

这一版把「我的凭据」做成个人中心里的一级入口：一人一套、显式绑定、模型永不可读、全链路指纹脱敏。

1凭据和消费者必须是显式绑定，默认零授权 建完凭据不等于能用。必须再勾「允许给哪个 MCP / 工具 / 脚本用」。没有这条，模型就能诱导任意工具去读你的全部凭据 —— 绑定关系才是这套东西的安全地基。
2模型永远不能「读」凭据，只能触发已绑定的槽位 引用语法 ${secret:key} 只写在配置里，不写在对话里。即使被 prompt injection，模型也拿不到值 —— 它只能调用一个已经填好凭据的工具。
3凭证建完即不可读，包括创建者自己 只给「测试连通性」和「轮换」。想核对就去试一次接口，而不是把密码显示出来。变量类（租户号、接口地址）才可读可复制。
4指纹扫描负责脱敏，不再靠猜键名 每条凭据存一份 sha256 前 16 位。落库前把文本里所有"像凭据的 token"算一遍哈希去比对，命中就替换成 ${secret:key}。用户自定义格式的 token 也跑不掉。
5域名白名单把「自动注入」关进笼子 一条凭证只能发往你声明的域名。否则「自动注入」就是个万能外泄通道 —— 模型可以把 secret 拼进任意 URL 的 query 带走。
6只分两类，但这两类决定了整个产品形态 变量（接口地址、租户号）可读可复制，就是个共享常量；凭证（密码、Token）永不可读。分级不是为了好看，是为了让「贴出来无所谓」和「贴出来要出事」走两条完全不同的路。

紫色那行是系统级隐藏参数：它不进模型可见的 properties，模型既看不到这个 header 存在，也改不了它的值。 这是平台已有的 x-nanzi-system-params 机制 —— 凭据只是把它的「固定值」换成了「引用」。
模型看到的工具 schema 只有 jql 和 maxResults 两个参数。对模型来说，这个工具"不需要身份" —— 身份由平台补齐。

为什么不能让模型填 header

放开 header 参数暴露给模型 → 模型为了"完成任务"可以把 token 拼到任意位置，一次 prompt injection 就能带走
收紧 header 由平台绑定 → 模型只会生成 jql，注入发生在执行器，值不进入任何一轮对话

注入发生在哪儿

1平台解析 env 映射，mysql.ops.password 解密
2写进 子进程的 environment，不进命令行参数（ps 看不到）
3脚本 os.environ["DB_PASSWORD"] 取用
4stdout / stderr 落库前过指纹扫描，命中就替换成 ${secret:...}

无人值守的三个额外风险

① 过期不能静默。凭据过期 → 任务直接失败 + 告警，不能"跑完了但什么都没查到"。

② 停用要连带。凭据一停用，所有引用它的任务立即失败，并在任务列表标红。

③ 离职要断。创建者离岗（账号停用）后，其任务与凭据一并冻结，不留给下一任自动继承。

想"临时用一下"怎么办

不做临时授权。对话里说「用我的 Jira token 调一下」时，模型做不到 —— 它没有读凭据的能力。 正确路径是：如果工具已绑定 → 直接用；如果没绑定 → 对话失败卡片上给「一键绑定」按钮，跳到这里完成绑定，再重试。 多一步，但没有"一次性放行"这种能被诱导出来的口子。

用户直接贴密码怎么办？
输入层做一次指纹扫描：命中已知凭据 → 气泡下方提示「检测到疑似凭据，已替换为 ${secret:...}，上下文与历史都不会留明文」。 注意：只能兜住已在凭据中心里的值。用户手贴一个新密码进来，平台无法判断真假 —— 这部分靠"输入前提示"和"历史页脱敏开关"共同约束。
这一屏是整套设计的核心证据：值只在第 2 步存在一瞬间，左边（模型）和上面的日志（审计）都只看到引用。

为什么是三层，而不是一个总开关。三种人问的其实是三个问题：管理员问「这个部署允许什么」， 你问「我的东西能不能被脚本读」，某一条凭据问「它能去哪」。合成一个开关，最严的那层会把所有人卡死； 拆成三层取交集，每一层都能单独收紧，且永远只能收紧、不能放宽——这是它比「一个总开关 + 默认开」更安全的地方。

三、安全边界：12 条硬约束

逐条可验证
#约束为什么落在哪
1凭证明文永不下发前端编辑页只显示"已设置"，提交新值才算修改；连创建者自己都看不到API 出参过滤
2库内存密文 + 指纹密文供注入，指纹供脱敏扫描；两者都不含明文value_encrypted / value_fingerprint
3解析结果包成 SensitiveValuerepr 返回 ***、str 抛异常 —— 防 f-string、防 json.dumps、防异常堆栈utils/secret_value.py
4绑定是白名单，默认零授权
系统级绑定还要带 bound_by		没有 binding，任何工具都取不到；A 绑定的系统凭据只对 A 生效 —— 否则 B 用同一个共享工具时等于白拿授权sys_secret_bindings
·bound_by_user_id
5域名白名单强制校验把 secret 拼进任意 URL 是最容易得手的外泄路径allowed_hosts
6场景白名单同一条凭据不该既能在对话里用、又能在脚本里读allowed_scenarios
7模型不可读、不可改绑定引用只出现在配置里；工具 schema 不含值；prompt 里也取不到注入层位于工具执行器
8全链路指纹扫描工具回显、脚本 stdout、历史、trace、Redis 运行态、日志、导出、分享，八个出口一套扫描utils/secret_scanner.py
9删除凭据不删使用记录审计要能溯源到"曾经用过"，凭据本身可以销毁usage_logs 断言软删
10过期即失效 + 到期前 7 天提醒定时任务无人值守，过期必须失败并告警，不能静默跑空expires_at 校验
11导出/分享只导引用MCP、工具包、会话分享都只见 ${secret:key}，接收方自己填值bundle / share 服务
12轮换保留 7 天双写换密钥不能让线上任务立刻全挂；新旧版本并存过渡sys_secret_versions
