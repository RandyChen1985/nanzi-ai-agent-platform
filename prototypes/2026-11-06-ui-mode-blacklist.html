    设计说明

    生效规则、数据放哪、代码改哪

    核心口径：只按角色控制、并集 deny wins、必须二选一、管理员不禁。黑名单只锁「界面形态 + 该形态能到的页面」，数据权限照旧由 menu:* / element:* 决定。

    生效规则并集，不可抵消
    角色 一线客服 cs_agent：禁用专业模式 { pro }
    角色 数据分析师 data_analyst：不禁用 { }
    ↓ 多角色求并集
    最终 禁用 { pro } → 只能用「用户模式」，专业页面重定向 ✓
    1默认全放行：列默认空串 = 两种都能用。存量角色、存量用户零迁移零感知。
    2只按角色：用户表不加字段，用户编辑弹窗不加页签。多角色取并集，任一角色禁掉就没有该模式。
    3必须二选一：blocked = 'user,pro' 直接非法。前端拦截 + 后端 400，两道。
    4管理员不禁：服务层判「users.role='admin' 或持有 code='admin' 的业务角色」→ 有效黑名单恒为空；角色页也不允许给 admin 配非空值。守卫不用单独判，拿到的本来就是空集。
    5服务端说了算：前端只做「不展示 + 重定向」；PUT /ui-mode 必须再校验一次并返回 403，改请求体绕不过去。
    6只锁形态，不当权限：禁 pro 的人仍受原 menu:* 约束；这里只是把「能到的页面」收窄到用户模式那一层，不放宽任何权限。
    数据放哪：只给角色加一列用户表不动

    「禁用用户模式」为什么不改 URL避免过度设计
    1用户模式不是一个独立的页面集合，只是同一批页面的简化排布——专业模式能到的页面包含用户模式能到的页面。
    2所以禁 user 只需：不渲染简化侧栏、切换入口只留专业模式、登录直接落工作台。页面集合不变，不需要白名单。
    3真正需要拦的是反方向：禁 pro 之后，专业模式独有的页面（用户管理、系统配置、调试台…）不能再靠敲地址进去。

    两个实现细节需要你知道

    1. 已登录用户的 URL 拦截什么时候生效？守卫读的是登录快照（同步、零请求），所以管理员改完角色后，受影响的用户要刷新或下次登录才拿到新的拦截规则；但「切模式」接口是实时的，他一按就被 403 顶回来。如果要做到秒级，得让守卫异步拉一次 /portal-prefs——代价是每次首屏多一个请求，不建议。
    2. 用户模式里「更多 → 系统概览」(/dashboard) 要放行吗？现在按「菜单里有的就放行」处理，所以有 menu:dashboard 的受限用户仍能进概览。如果你们认为概览属于专业模式专属，把它从白名单里摘掉即可（一条常量的差别）。

    原型仅用于确认交互与落点 · 未改动任何实现代码 · 确认后按「迁移 → 服务 → 接口 → 守卫 → 前端」顺序落地
