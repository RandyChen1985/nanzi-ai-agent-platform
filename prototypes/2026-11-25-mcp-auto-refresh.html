这套东西落在哪、怎么跑

现状：刷新只能手点「同步工具」，而 sync_tools() 是整批覆盖——远端改了描述、加了参数、删了参数， 点一次就被静默吃掉，库里只剩一个 last_sync_at。本方案把「探测」和「应用」拆开： 自动只负责发现差异并留痕，应用仍由人确认。

页面插入点（都在现有组件里，不新增一级导航）

位置改哪个文件加了什么
左栏服务卡片 · 指标行 McpServerRegistry.vue 指标行（现有「N 工具 / 已发布 / 远端已删除 / 已分享 / 相对时间」） 插入紫色 3 项定义变更 徽标；相对时间从「最近同步」扩成「最近检查」，hover 显示同步与探测两个时间
左栏筛选区 · 待办 chip McpTodoKey 加一个 key（现有 offline / unpublished / stale-tools / stale-sync） 右栏空状态「值得处理」多一项「定义有变更 2」，点一下左栏就只剩有变更的服务 —— 零新组件
左栏顶部 · 提示条 搜索区下方，与 McpFlowGuideBanner 同一套视觉 进页面惰性探测后发现变更时出现一次，可关闭；点击直接开抽屉

三种触发时机

1每日 04:30 巡检

复用现有 APScheduler 常驻任务（已有 02:00 / 03:00 / 03:30 / 04:00 四条，错开）。

  • 范围：只探已启用的公共服务；个人服务、禁用服务都不探
  • 并发 3、每服务抖动 0–90s、单服务 30s 超时
  • 发现变更 → 写变更表 + 发管理员通知
  • 只在开了 TASK_SCHEDULER_ENABLED 的那台跑
2进页面惰性探测

保证看到的是新的，成本只跟「有多少服务过期」成正比。

  • 列表接口返回 last_probe_at，超过 6 小时的进待探队列
  • 前端批量 POST /servers/probe，一次最多 10 个
  • 不阻塞列表渲染，探测完只更新徽标
3活跃会话热刷新

智能体正在用这个服务时连接是现成的，tools/list 几乎免费。

  • 触发点：call_remote_tool 成功后
  • 条件：该服务 last_probe_at 超 15 分钟
  • fire-and-forget，不进调用链、不加延迟
  • Redis 去抖锁，防止并发下重复探

数据表：变更历史（按你的要求落表）

新增一张表，只存「差异项」，不存全量工具快照。

CREATE TABLE sys_mcp_tool_definition_changes (
  id            VARCHAR(36)  PRIMARY KEY,
  batch_id      VARCHAR(36)  NOT NULL,   -- 一次探测一批
  server_id     VARCHAR(36)  NOT NULL,   -- FK → sys_mcp_servers CASCADE
  tool_name     VARCHAR(255) NOT NULL,   -- 全名 server:tool
  change_kind   VARCHAR(32)  NOT NULL,   -- 见下
  severity      VARCHAR(16)  NOT NULL,   -- safe|notice|breaking
  before_value  TEXT,                    -- 仅变化部分的 JSON
  after_value   TEXT,
  detected_at   DATETIME     NOT NULL,
  detected_by   VARCHAR(24)  NOT NULL,   -- nightly|page|hot_call|manual
  status        VARCHAR(16)  NOT NULL,   -- pending|applied|dismissed
  handled_at    DATETIME,
  handled_by    INT,
  INDEX idx_srv_status (server_id, status),
  INDEX idx_detected (detected_at)
);

change_kind 取值与分级：

tool_added / tool_removednotice 复用现有「待发布 / 远端已删除」机制，只提示
description_changedsafe 描述文本变了
param_added_optionalsafe 新增可选参数
param_removedbreaking 会让凭据槽 arg: 失效
param_required / param_type / param_enumbreaking 已绑定智能体可能调不通
annotations_changednotice destructive 相关变化要标红

两张现有表各加两列：sys_mcp_servers 加 last_probe_at / last_probe_status / probe_failure_count / last_probe_error； sys_mcp_tool_cache 加 definition_hash（描述+schema+annotations 的规范化 sha256）与 definition_changed_at。

为什么探测必须走独立只读路径

现有 sync_tools() 一次调用会同时：覆盖 tool_description / parameter_schema、把远端没返回的工具标 is_available=false、下架已发布工具、删掉失效的凭据槽。探测如果复用它，「看一眼」就等于「应用」。 所以探测是另一条路径：拉 tools/list → 算 definition_hash → 跟库里比 → 只写变更表。 这样每天探 24 次也不会误下线任何工具，现有「远端返回 0 工具需 force」的保护也不会被绕过。

三个坑

坑怎么绕
UserContext 服务没法后台探 user_assertion_enabled 的服务连 tools/list 都要按用户签名的断言，后台没有「当前操作者」。降级为 needs_user，卡片上显示「需用户签名，无法后台探测」，进页面时用当前管理员身份探，或手动同步。
不能靠 updated_at 判断变没变 它是 onupdate=datetime.now，只反映你上次同步的时间。必须存独立指纹：sha256(json.dumps(canonical, sort_keys=True))，并先剥掉 x-nanzi-* 扩展字段，否则 key 顺序和空白差异会天天报假变更。
参数变更不会剔智能体版本引用 工具删除时会 prune_agent_versions_by_names，但参数增删/类型变化不会。所以变更项上要直接点名「影响 3 个智能体版本」，而不是等运行时参数对不上。

已定 / 待定

已定：落表存历史、只通知管理员、加一个全局「定义变更」页签、探测与应用分离。

建议仍按整批应用：「应用所选」内部走一次 sync_tools()（幂等，复用现有 0 工具保护与 stale_arg_slots 凭据槽清理），勾选只用来筛选你看哪些。逐项应用要单独写部分同步逻辑，容易和现有清理路径打架。
