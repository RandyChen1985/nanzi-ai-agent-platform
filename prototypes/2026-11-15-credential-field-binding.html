字段级绑定：从「整条凭据」到「选定具体字段」

结构化凭据已经能录入了，但配置工具时只能整条绑上去——一个 SMTP 凭据只能整体塞进某个 header， 拿不到「只要密码」这种粒度。这个原型把绑定粒度下沉到字段，并统一 header、参数、环境变量三处的表达式。

核心结论 01

绑定到字段，不是绑定到整条

选中结构化凭据后必须再选一个字段，生成 ${secret:key.field}。 单值凭据保持原样（${CREDENTIAL:jira.prod.token}），不强制迁移。

核心结论 02

一处语法，三处生效

Header 值、参数值、脚本环境变量都写同一套 ${secret:key.field}， 注入层按「本次槽位绑定的那条凭据」解析，不新增特权路径。

核心结论 03

整段 JSON 灌进 Header 要拦住

结构化凭据仍写成 ${CREDENTIAL:key} 时，会把整份 JSON 塞进请求头。 这种情况不再默认允许，要给明确警告并要求选字段。

为什么参数级不用文本引用

          

            

              参数值是要交给对方 API 的「一个精确值」，不是给人看的文本。如果这里也允许
              Bearer ${secret:} 这种拼接，就等于允许在参数里写模板语言，
              而参数的类型（数字 / 布尔 / 数组）会在字符串化之后失真。
            

            

            

              所以：绑定记录本身多一列 value_path（字段路径，空 = 整段）。
              注入时按路径从解密后的 JSON 里取值并保留类型，header 仍然是文本引用——
              因为 header 天生就是字符串，那里才需要前缀拼接。

这一版刻意不做

          

            

              ·跨凭据引用：${secret:a.b} 只能引「本次槽位绑定的那条」。
                放开等于绕过绑定白名单，任何写了引用的地方都能读到任意凭据。
            

            

              ·嵌套路径的图形化选择：a.b.c 这种深层结构先支持手写，
                选择器里只列第一层字段。
            

            

              ·表达式运算（拼接、默认值、条件）：没有需求，且会变成一个需要沙箱的模板引擎。
            

          

        


        

          
取舍：为什么不改成「每条字段一条凭据」

          

            

              拆成 mail.smtp.host / mail.smtp.password 多条独立凭据，看似最省事，
              但会把「一份配置」打散：轮换密码时得记得同步改地址；列表里出现一堆同源凭据；
              授权与绑定也要逐条维护。结构化录入的意义正在于「一份配置是一个整体」，
              所以字段级取用必须发生在取用侧，而不是把存储拆碎。

为什么是「一条路径应用到所有命中」，而不是给每条候选单独配

      

        

          

            
每条候选凭据单独配字段（不采用）

            
DEPT-FIN   → password
DEPT-SALES → password
DEPT-OLD   → smtp_pwd
DEPT-CS    → （单值，无字段）

            

              规则的意义是「按身份自动挑」，一旦要维护候选清单与各自的字段名，规则就退化成一张手工对照表：
              新部门入职要改规则，凭据换了模板也要改规则，而改的人往往不是配规则的人。
            

          

          

            
一条路径应用到所有命中（采用）

            
取用字段 = password
命中哪条都取 password
没有这个字段 → 拒绝并说明

            

              再配一个模板约束，「字段名一致」就从「靠人自觉」变成配置能保证、运行时能校验的事：
              模板不符的凭据直接按未命中处理，而字段集合由模板定义给出，字段也能下拉选。
            

          

        


        

        

          被拒绝的那条怎么救？两条路：① 用「轮换」把老凭据改成同一模板（键名统一，规则不用动）；
            ② 那条老凭据单独用固定绑定配字段路径——规则负责大多数，个别特殊的走固定绑定，
            两者在同一槽位可以并存（规则未命中时回退到固定那条）。

              映射表不是新的存储：「参数 A 取字段 x」就是一条固定绑定
              （slot=arg:send_mail:A、secret_id 相同、value_path=x）。

几个必须说清的边界

      

        

          
情形处理

          
            

              两个参数要同一个字段
              允许。两条绑定各自指向同一字段，注入同一份值——比让人复制两份凭据干净。
            

            

              某个参数已经按规则提供
              映射表里灰掉不可改，并标「由规则提供」。规则是按身份挑，不能被一条固定凭据盖掉。
            

            

              来源改成按规则匹配
              指定了模板约束就能下拉（字段集合由模板定义确定）；没指定就只能手填字段名。
            

            

              规则挑到模板不符的凭据
              按未命中处理（与 on_miss 走同一条路），不会拿另一种结构的凭据去取字段。
            

            

              固定 / 规则来回切
              字段值原样保留——两边存的都是同一个字段名字符串，切回去不用重选。
            

            

              换了一条凭据
              已选字段若在新凭据里不存在，行内立刻标红并清空，不等到保存才报错。
            

            

              某参数原来绑的是别的凭据
              保存时对「本次参与映射的参数」增删覆盖；没参与映射的参数一律不动。
            

            

              单值凭据
              不进这个 tab——它只有一个值，逐参数配就行，硬塞进映射表反而多一步。
