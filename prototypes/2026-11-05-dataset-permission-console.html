数据集权限管理 · 数据集 / 表 / 字段 / 行 四层门禁

现状：一个数据集权限 = 数据集里所有表、所有字段；行级配置在另一个页面；范围、有效期、模拟都无法表达。 这一版把四层收进同一个入口：数据集级决定进不进得来，表级决定进来能看哪几张表， 字段级决定每张表能看哪几列，行级决定每张表能看哪些行。

1四层是一条门禁链，不是四个并列 Tab 表范围和字段范围都是「授权条目」上的字段，不是独立实体；先有数据集权限，表级才有意义；先能看到表，字段级才有意义。页面用「按主体 / 按表 / 字段范围 / 行级 / 模拟」五种视角看同一条链。
2表级只做「全部 / 指定」；字段级额外给「排除」 表级黑名单与新增表天然冲突：新表默认可见就会静默扩大授权，所以表级只留白名单（fail-closed）。 字段级相反——业务刚需是「整张表放开、只挖掉 id_card 这类列」，所以字段级给「限定 / 排除」两种； 新增列时按「排除」以外的方式默认可见，会在页头提示复审。
3用户级条目可显式收窄，覆盖角色 角色授权取并集；但同一个人一旦有用户级条目，就以用户级为准。否则「给某人缩小权限」永远只能删角色——会误伤同角色其他人。
4新增表默认继承「全部」，但必须待确认 页头常驻「N 张新表已继承 M 条全部范围授权」。默认不打断使用，但绝不静默——审阅前可先挂起新表。

最终生效结果

这套 UI 落到现有代码上，改哪里

  • 数据模型：沿用 ai_agent_resource_permissions（resource_type='metadata'）， 新增 scope JSON 列：{"mode":"all"|"list","tables":[id...]}； 字段级复用同一列，在 scope 里追加 columns： {"mode":"list","tables":[12,15],"columns":{"12":{"mode":"exclude","names":["id_card","mobile"]}, "15":{"mode":"include","names":["task_id","status"]}}}。 没写 columns 的表 = 全部字段，老数据零迁移。 行级继续放 meta_datasets.row_filter_config，不新建策略表。
  • 权限判定：enforce_dataset_table_permissions() 在现有 enforce_physical_table_permissions() 的 has_dataset_permission() 分支之后加一层表级判定： 命中用户级条目 → 用用户级 scope；否则用角色 ∪ 全体 scope；list 模式下不在白名单即拒。
  • Schema 输出：fetch_dataset_schema_core() 按同一 scope 过滤表，否则模型会看到并尝试查询被禁表。 字段级同理：表 YAML 里的 columns 只输出可见列——模型看不到被排除的字段，也就不会去 SELECT 它们。
  • 字段级执行兜底：只过滤 schema 不够（模型可能凭上下文写 SELECT id_card）。 执行期在 enforce_table_scope_for_refs 之后加一层列校验：解析 SELECT 的列引用， 命中被排除的字段即 [Permission Denied]；SELECT * 在有列收窄的表上直接拒绝， 要求模型写显式列名。这条是「两道防线」在字段维度的延续。
  • 接口：GET/POST/DELETE /api/portal/metadata/datasets/{id}/permissions 增加 scope、expire_at、row_policy 三个字段；新增 GET .../permissions/simulate?user_id= 供模拟器使用。
  • 兼容：历史授权没有 scope 时按 {"mode":"all"} 处理，行为与现在完全一致（数据集内全表可见）。

四个待你确认的取舍

  • 要不要「排除表」模式？我倾向于不做。若业务确实要「全部减 3 张」，用「指定」勾选其余表即可；黑名单会让新增表默认可见，风险更高。
  • 行级策略要不要变成可复用对象？这版没有：行级仍是数据集内配置、按主体命中。好处是零迁移、与现有 SQL 重写完全兼容；代价是跨数据集复用同一套「按部门过滤」要复制一份。
  • 用户级「覆盖」还是「并集」？这版给的是「用户级存在即覆盖」。如果你们更希望权限只增不减（并集），页面上就要去掉「收窄」语义，这条要定。
  • 字段级取交集还是并集？这版给的是交集：同一张表，任何一层排除了某个字段，这个字段就不可见。 方向与表级相反，是有意的 —— 表级「全员基线不可收窄」是说不能凭空少给；字段级反过来， 全员排除掉的敏感字段（id_card / mobile）不能被个人或角色配置重新放开，而个人对某张表的收窄也必须生效。 代价是「个人想临时放开一个敏感字段」做不到，只能改全员或角色配置。
  • 「全部表」模式下要不要逐表配字段？这版要：新增表默认全部字段，但敏感字段常常是 「先全表放开、再挖掉两列」，所以「全部表 + 逐表排除」必须允许。代价是表多时面板会长， 所以列表默认折叠、只显示摘要，点「设置」才展开字段勾选。
  • 「全员」条目能不能被个人条目收窄？这版不能：全员范围是公共基线，任何人只要进了这个数据集就至少能看这几张表。所以王敏被收窄到 5 张后，实际可见是 5 ∪ 全员 4 = 7 张。如果业务要求「收窄到 5 张就真的只有 5 张」，全员条目就得改成「默认基线、可被覆盖」。
