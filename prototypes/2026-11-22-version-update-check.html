优点

代价

这个方案的取舍

优点

能完整回答三件事：有没有新版本、新版本改了什么、要不要现在升级（含迁移组数提示）。自动检查开关与「最近/下次检查时间」有地方放。

代价

新增一个页面与入口；普通用户其实只想知道「有没有」，不一定想看 changelog。

折中

关于面板（方案 A 的形态）只放一行状态 + 「查看详情」，详情落到这一页。A 与 B 可以同时存在，不是二选一。

自动检查怎么跑

不建议浏览器直连 Gitee：会吃 CORS、吃限流，且 N 个用户 = N 次请求。

服务端侧：一个每日一次的任务（沿用现有调度）请求 /tags，结果写缓存（24h 有效）+ 记录「最近检查时间 / 失败原因」，前端只 GET 一个只读接口。

请求频率每实例每天 1 次
缓存 TTL24 小时
失败策略不重试，次日再查
手动检查节流60 秒 1 次
离线环境显示「无法获取，可忽略」

C · 不主动找也能看见：一次性横幅

自动检查发现有新版本时，在用户模式的首页顶部（或右下角）出一条可关闭的横幅；「稍后」当次消失，「忽略此版本」写进用户偏好，直到出现更新的 tag 才再提示。

⬆ 发现新版本 1.0.24（当前 v1.0.23.0，2026-11-22 发布） 稍后 忽略此版本
首页内容区（示意）：横幅贴在内容区顶部，滚动时固定在内容区而不是整页顶栏，避免和平台顶栏抢高度。

交互细节

「稍后」= 本次会话不再出现（sessionStorage），下次打开还会提示；「忽略此版本」= 写进用户偏好， 只在出现比 1.0.24 更大的 tag 时才重新提示。两条动作的区别必须在文案上写清， 否则用户会以为「稍后」等于不再提示。

为什么不做强提示

升级动作是运维的事（要跑迁移、重启服务），普通用户点「升级」也做不了什么。 所以横幅只负责「告知 + 指向发行说明」，不提供「一键升级」这类点了会失望的按钮。

判定规则（三条，缺一不可）

1. 归一化：去掉 v/V 前缀与首尾空白，四段版本与三段 tag 一律右补 0 到四段再比。

2. 逐段数值比较：按数字比，不按字符串比——1.0.9 < 1.0.10，字符串比会判反。

3. 只认「严格大于」：相等、本地更新（打补丁构建）、预发布 tag、dev 构建，一律不提示。

为什么不能只比前 3 段：现在 1.0.24.0 与 tag 1.0.24 相等是对的；但一旦本地出现 1.0.24.1（补丁构建），只比前 3 段会把它判成「和 1.0.24 一样」。补零后逐段比，1.0.24.1 > 1.0.24.0， 既不误报也能容纳补丁号。
