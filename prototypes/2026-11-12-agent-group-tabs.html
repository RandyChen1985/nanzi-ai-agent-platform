2字段该存哪：表里已经有三个「像分组」的字段，但都不能用

字段真实语义（读代码与迁移注释得出）谁在读能不能当业务分组
ai_agents.owner_group
VARCHAR(50)		 迁移注释写的是「所属组 (预留)」/ PG 注释「所属用户组」——指组织架构上的用户组，不是业务分组 分享服务、系统级发布服务在元数据里传递它；已有索引 idx_owner_created(owner_group, created_at) 不行：这是权限/组织维度。拿它当业务分组，以后想「按用户组授权智能体」就无路可走
ai_agents.capabilities
JSON		 模型注释原文：「Tags for routing e.g. ["data","coding"]」——给 AI 路由用的能力标签，多值 路由 / 调度时会读，影响「这条请求该派给谁」 不行：多值 → 一个智能体出现在多个页签、计数相加大于总数；且会把「导航口径」和「路由口径」绑死
ai_agents.agent_type 枚举式类型（GENERAL 等），已经是筛选维度之一 筛选、卡片文字、部分运行时分支 不行：这是「机制类型」，不是「业务域」；且已有独立筛选入口
ai_agents.group_name
本次新增 VARCHAR(64)		 单值业务分组，只服务列表页的分组页签与筛选 只读：智能体中心的页签 / 筛选 采用：与 meta_datasets.group_name、tools.group_name 完全同构，三页一套口径

与「技能分组」的区别值得说清：技能是文件（分组写进 SKILL.md 才不会被复制/分享弄丢）， 智能体是数据库实体——所以这里就该老实加一列，跟元数据管理那次一致。

3三套 UI 方案（点上面工具条切换，下面是真实页面复刻）

推荐
A · 搜索行下方一条分组页签
与工具注册表、元数据管理、技能工作台完全同一套组件与计数口径。
  • 一眼看到所有业务域与各自数量
  • 位置在搜索行下、卡片上，不动左侧结构
  • 分组多时收进「更多分组 ▾」
重排
B · 内容区左侧分组栏
分组 ≥ 10 个时更好翻，但要给这一页新增一条左栏。
  • 好处：分组很多时纵向列表更好扫
  • 代价：一级 Tab(5) + 左栏 + 搜索行，层级变三层
  • 代价：与「我的技能」左栏形态重复，占用横向空间
最小
C · 只把分组塞进「筛选」面板
改动最小，但补不上「看不到分布」这个原始问题。
  • 好处：不动布局，只多一个下拉
  • 代价：用户仍然不知道有哪些分组、各多少
  • 代价：与已有 6 个筛选混在一起，更难被发现

6新建 / 编辑弹窗里的分组字段

编辑智能体

✕
基本信息能力标签专家团排版样式

单选，只用于智能体中心的页签与筛选。不参与权限、不进 AI 提示词，也不影响路由—— 那是「能力标签」(capabilities) 的职责。

字段放在「基本信息」tab 的第三行（名称 / 标识之后），与描述同属「这是什么」； 候选值来自全平台已有分组 + 常用建议，也允许直接输入新名字。

需要你拍板 4 件事

  1. 分组落库用新字段 group_name，还是复用已有的 owner_group？ 建议：新增 group_name——owner_group 的注释是「所属用户组」， 是组织/权限维度，还被分享与发布服务在用；拿它当业务分组，以后「按用户组授权智能体」就没地方放了。
  2. 页签放在哪一屏？ 建议：只放「全部智能体 / 我的智能体」两个视图（方案 A）。 「分享给我 / 我分享的 / 专家团」不做分组——那是待办与协作队列，不是浏览场景。
  3. 页签上的数字算不算其它筛选？ 建议：算（除分组本身之外的所有条件）—— 这一页有 6 个筛选，如果页签数字只算搜索，用户勾了「只看已启用」后会看到「页签说 5、点进去 3」。 原则始终是：页签数字 = 点进去看到的条数。
  4. 要不要「批量设分组」？ 建议：本期先单条（新建/编辑弹窗里改 + 卡片更多菜单里改）， 但有 12 个以上存量智能体时一条条点会烦——如果你要，我可以顺手做成「批量模式里多一个『设置分组』」。
