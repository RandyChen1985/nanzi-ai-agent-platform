四个设计取舍

    
「可视化 JSON 编辑器」有很多种做法，下面是我建议的边界。

    

      

        
问题建议理由

        

          嵌套结构怎么办
          顶层扁平键值对；值是对象/数组时，该行类型标 JSON，值格换成小编辑框
          
            硬做任意层级树形编辑器，复杂度和出错面都比手写 JSON 更大。
            凭据实际九成是扁平 key-value；真嵌套的少数人切到「写 JSON」更顺手。
          
        

        

          类型谁来定
          按输入自动推断（纯数字 → number、true/false → boolean），可手动下拉改回文本
          
            自动推断能覆盖大多数情况，但不强制：手机号、身份证、前导零的编号
            必须能改回字符串，否则 013800138000 会被吃掉前导零。
          
        

        

          敏感字段
          每行一个「敏感」勾选，勾上后值打码显示、且不进列表摘要
          
            结构化凭据整段已加密，但列表摘要（value_summary）会拼非敏感字段。
            不标敏感 = 密码明文出现在列表上。
          
        

        

          和 JSON 视图的关系
          两个视图编辑同一份数据，随时切换，切换时校验并提示丢不掉什么
          
            懂 JSON 的人不该被表格拖慢，不懂的人不该被迫写 JSON。
            切到键值对无法表达的嵌套时，明说「这几行要保持 JSON」，而不是悄悄拍平。
          
        

      

    

  


  
  

    
落地要动的地方

    

      
    
        
  • 只影响「自定义 JSON」一个模板。带固定字段的模板（邮箱 / 数据库 / API Token…）本来就是表单，不需要改。
    • 
        
  • 存储格式不变。仍是 value_format='json' + 那段 JSON 文本，键值对编辑器只是换了个输入方式，老记录照常读。
    • 
        
  • 敏感标记要能落到后端。现在 secret_fields 来自模板声明；自定义 JSON 没有模板，需要把勾选的字段名一并提交，否则摘要会漏。
    • 
        
  • 校验复用现有的。顶层必须对象、不能为空对象、key 不能重复——这些 errors.__raw 已经在做，只是把错误挂到具体行上。
    • 
      

    

  


  

    原型说明：表格可增删行、改类型、勾敏感，右上角可切到「写 JSON」，两侧实时同步并显示注入预览。
