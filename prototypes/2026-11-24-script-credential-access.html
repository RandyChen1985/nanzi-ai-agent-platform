脚本读取凭据

skill 里的 python 脚本要调第三方 API，key 放凭据中心。自有凭据默认可用，不用配置绑定；授予来的凭据要显式开启。脚本用 nanzi-credential get <key> 取值，值不进环境变量、不落盘常驻。

1自己的凭据，默认就能用 你创建的凭据默认允许脚本读取，不用再绑到任何消费者。管理员授给你的凭据默认关闭，需要你显式打开。
2取值走 helper，不走环境变量 env 一条命令就能看到所有变量，还会继承给子进程。helper 按需取一条，每次调用都落审计。
3MCP 和 API 工具仍然要绑定 那条通道是"平台代你发请求"，必须知道你允许发给谁。脚本是"你自己取值"，两者不是一回事。

脚本里怎么用：一行命令，四种失败

helper 由平台写进工作区（.nanzi/），脚本里当普通命令调用。失败会把原因说成人话，而不是让脚本作者去猜。

那绑定还要不要？要，但只管出站注入

三条通道的授权方式不一样，因为「谁在发请求」不一样。这张表是这次设计里最容易混淆的地方。

通道 谁发请求 值在哪出现 要不要绑定
MCP 服务 平台代发，连到声明的服务 出站请求头 要绑 · 且域名白名单
API 工具 平台代发，参数里写 ${secret:key} 出站请求头 / 参数 要绑 · 且域名白名单
脚本工具 平台子进程，env 注入 子进程环境变量 要绑槽位 env:NAME
skill / bash 脚本
本次新增		 脚本自己发，平台不参与 脚本内存里 不绑 · 按凭据归属授权
⚠

前三行平台能控制出站，所以能拦住"发到不该发的地方"。第四行不行——脚本拿到值之后发给谁，平台看不见。这就是为什么脚本通道默认只对自有凭据开放，而授予凭据必须手动开启。

ℹ

换句话说：绑定是给「平台代发」用的，脚本通道没有代发这回事，所以不能用绑定来表达授权。如果硬要引入"绑到某个 skill"，一个 skill 改名就失效，且没人会去维护它。

只有下面几处会真的读到凭据的值。
会注入
MCP 服务 · 请求头header:
绑定盖过固定 Token。绑定失效时直接报错，不退回固定 Token。
API 工具 · 请求头 / 参数位header · path: · query:
只补空位，手填了真实值的头不会被覆盖。
脚本 · 两条通道 本次扩展
env:MY_KEY 给脚本工具；技能/任意 bash 用 nanzi-credential。
前提：勾「脚本可用」+ 两层开关都开。
边界：值交给脚本后平台拦不住打印与外发，只留记录。
三道闸门都要过
  1. 平台策略：是否允许脚本读凭据（默认关）
  2. 你的偏好：再单独打开一次（默认关）
  3. 这条凭据：勾「脚本可用」

这些凭据会被用在哪里

只有下面几处会真的读到凭据的值。
先分清通道：技能里的 .py / .js 是被 Bash 执行的，没有环境变量注入——os.environ["MY_KEY"] 拿不到东西。脚本工具才读环境变量。
Bash / Shell值走 stdout，可直接 $( ) 接住
# 先看看有哪些可用的（只给标识和名称，不含值）
nanzi-credential list

# 取一条，值走 stdout
KEY=$(nanzi-credential get weather.api.key)
curl -s -H "Authorization: Bearer $KEY" https://api.example.com/v1/weather
Python失败时 exit 1，stderr 是中文
import subprocess

def get_secret(key):
    result = subprocess.run(
        ["nanzi-credential", "get", key],
        capture_output=True, text=True, timeout=30,
    )
    if result.returncode != 0:
        raise RuntimeError(result.stderr.strip())
    return result.stdout.strip()
取不到时，先看是哪一层
· command not found：不在 Bash 工具里跑
· 「平台或你的偏好关闭了…」：闸门 ① 或 ② 没开
· 「没有授权给当前场景」：闸门 ③ 没勾
· 「没有这条凭据」：标识拼错，先 list
helper 只能由平台在 Bash 里准备：票据每次执行前写入、执行完删除，所以它不能拿去本地或别的机器跑。
