方案设计 · 钉钉 / 飞书 / 企业微信 三渠道统一

消息通道多渠道：统一多群配置 + 按群 ID 精确指定

钉钉、飞书、企业微信三套渠道走完全一样的逻辑：每个渠道可以配多个群， 每个群有平台维护的群 ID和名称、可以单独启用停用、可以设一个默认群。 发送时：AI 指定了群 ID 就发给那个群（不存在或已停用则忽略、不兜底）， 没指定就发默认群。另外新增一个 list_notification_channels 工具， 让 AI 能主动查「我到底有哪些可用的通道」。

本期范围

✓
三渠道都支持配多个群 钉钉 / 飞书 / 企业微信，每渠道最多 10 个群，各自的默认群、启用状态独立
✓
新增 list_notification_channels 工具 AI 主动查询：有哪些渠道、每个渠道下有哪些群、群 ID / 名称 / 是否默认 / 是否启用
✓

✕

② AI 怎么知道有哪些通道：新增 list_notification_channels

参考 list_accessible_datasets 的做法：一个工具返回当前用户全部渠道 + 群的结构化清单， 带 id / name / enabled / is_default。 

# 工具签名
list_notification_channels(channel_type?="dingtalk", include_disabled?=false)

# 返回（JSON 字符串）
{
  "channels": [
    {"type": "dingtalk", "label": "钉钉", "default_id": 12, "items": [
        {"id": 12, "name": "运维告警群", "enabled": true,  "is_default": true},
        {"id": 13, "name": "每日数据日报", "enabled": true,  "is_default": false},
        {"id": 14, "name": "旧项目群（已弃用）", "enabled": false, "is_default": false}
    ]},
    {"type": "feishu", "label": "飞书", "default_id": 21, "items": [...]},
    {"type": "wechat_work", "label": "企业微信", "default_id": 31, "items": [...]}
  ],
  "note": "钉钉默认群 id=12（运维告警群）。停用的群不会作为发送目标。"
}
ℹ 为什么不把清单塞进工具描述：三个渠道最多 30 个群，全塞进描述会让每次调用的上下文变臃肿， 而且用户新加群后描述不会自动刷新。用 list 工具按需查，数据实时、描述保持简洁。
◻ AI 的使用路径：用户说「发到运维群」→ AI 调 list_notification_channels 找名字含「运维」的群 → 拿到 id=12 → 调 send_dingtalk_message(..., group_id=12)。 没找到就如实告诉用户「你没有叫运维的群，现有的是 A/B/C」。

三个发送工具：group_id 和 group_name 二选一

用户说「发给运维告警群」是最自然的说法，不该逼模型先查一遍 ID 再发。 所以两个参数都收：ID 精确、名称好用，服务端统一解析。 

send_dingtalk_message(title, content, group_id=None, group_name=None)
send_feishu_message(title, content, group_id=None, group_name=None)
send_wechat_work_message(content, group_id=None, group_name=None)   # 企微本来就没有 title

# 用户说「发给运维告警群」 → 模型直接传名称，不用先查
send_dingtalk_message(title="...", content="...", group_name="运维告警群")

# 重名时模型会收到候选列表，再改用 id 精确指定
send_dingtalk_message(title="...", content="...", group_id=13)
ℹ 优先级：group_id > group_name。 两个都没传 → 发默认群。两个都传且指向不同群 → 以 id 为准（名称会被忽略并记一条日志）。

名称怎么解析（三步，越往后越松）

步骤规则命中 / 不命中
① 归一化精确匹配 去掉首尾空格、忽略大小写与全半角、去掉模型爱加的「群」后缀 唯一命中 用它 ／ 无 进第 ② 步
② 唯一包含匹配 群名包含用户说的串（或反过来） 只命中 1 个 用它 ／ 命中多个 报候选、要求用 id
③ 都不中 —— 忽略，不发送（不兜底默认群）
⚠ 重名只能靠 ID：用户配了两个都叫「项目群」的群时，名称解析会直接拒绝并回「有 2 个叫项目群的群：id=15、id=17，请用 id 指定」—— 绝不替你猜一个。这跟「名称可以重复、可以随时被改」的现实一致。

发送时的解析顺序

规则很短：指定了就发指定的，没指定就发默认的。指定的不可用就忽略，不兜底。

1

传了 group_id 或 group_name

名称先按三步解析成唯一一条记录，再统一校验：存在、属于当前用户、渠道类型匹配（不能拿钉钉 ID 去发飞书）、已启用。

全都过 → 只发这一个群
2

传了但校验不过

不存在 / 不是自己的 / 渠道不匹配 / 已停用 → 忽略，消息不发送。回执写明原因并列出可用群 ID。

忽略：本条不发送，不兜底
3

没传 group_id

用该渠道的默认群（每人每渠道最多一个）。

发默认群
4

没设默认 / 一个启用群都没有

没设默认 → 用该渠道最早的启用群；一个都没有 → 返回可读错误，引导去个人中心配置。

⚠ 「忽略」意味着消息会丢——这是你要的语义（指定错了就不发，不擅自改投默认群）。 为了不让它静默发生，回执写「消息未发送」+ 列出该渠道的可用群 ID，AI 一般会当场改对重发。

③ 回执

三渠道措辞统一，只把渠道名换掉。要能区分「没这个群」「群停用了」「webhook 失效」。

✓ 已发送到钉钉「每日数据日报」(id=13)
✓ 已发送到飞书「飞书项目群」(id=21，默认群)
✗ 未发送：钉钉群 id=99 不存在。 当前可用钉钉群：id=12「运维告警群」、id=13「每日数据日报」
✗ 未发送：群 id=14「旧项目群（已弃用）」已停用。 当前可用钉钉群：id=12「运维告警群」、id=13「每日数据日报」
✗ 发送失败：token is not exist (Code: 300001) 目标：钉钉「运维告警群」(id=12)
ℹ 三种失败必须区分：「群不存在」是 AI 指错了群、「群已停用」是配置问题、 「token 失效」是 webhook 本身坏了。混在一起说会让用户完全找错方向。

迁移与兼容

目标：存量零感知。没配多个群、也没传 group_id 的智能体，行为与今天一模一样。

表结构
user_notification_configs 去掉 ux_user_notification_channel 唯一键， 新增 name（群名称）、is_default（0/1）。不需要新增 ID 列——主键就是群 ID。 存量行回填 name='默认群'、is_default=1。
三个渠道共用这一张表，channel_type 区分，迁移一次全部搞定。
为什么敢改这张表
12 处读取全部经过 get_config_by_type_raw()。内部改成 「启用优先 → is_default 优先 → id 升序，取第一条」，所有调用点（三个发送工具、定时任务投递、邮件服务） 一行都不用改，行为等价于今天「只有一条记录」。
新增公共函数
list_notification_channels(user_id)（供 list 工具用）与 resolve_notification_channel(user_id, channel_type, group_id)（供三个发送工具共用， 统一做存在/归属/渠道匹配/启用四项校验）。三个工具不再各写一遍。
工具改动面
三个 Input 各加一个可选 group_id: Optional[int]；新增 list_notification_channels 工具并在 registry 注册（含权限白名单与证据类型）。 ToolConfigItem 与智能体版本配置完全不动。
定时任务
任务投递走 NotificationService.send_*(db, user_id, ...)，内部同样用「默认渠道」， 因此任务通知行为不变。以后若想让任务发到指定群，可在任务的渠道配置里加群 ID 选择（本期不做）。
不做的事
不允许工具传 webhook（SSRF 风险）；不做标签路由；不做工具级指定群；本期不做 @某人。
