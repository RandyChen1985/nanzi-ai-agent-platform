编辑用户 · 权限配置 · 数据资产 —— 让「角色已有」的资源显示出来

核实结论：5 个页签（智能体 / 知识库 / 数据集 / 外部 API / 可用模型）是同一个机制问题，与「界面访问」「禁用资源」已有的继承展示不同步。 下面的原型把 5 个页签统一成「勾选 + 不可选 + 角色/全员已有徽标」，并做了「现状 / 建议」对照开关。

定稿（2026-11-24）：采用方案 B（卡片保持原样，顶部汇总 + 「仅角色已有」筛选）； 徽标文案统一用笼统的「角色/全员已有」——前端只拿得到「并集 − 直配」，分不清某一项是业务角色 给的还是全员基线给的，标错来源比不标更难排查。本轮不改后端；需要精确到角色名时再补 inherited_sources[]。方案 A 保留在此仅作对照。 实现在此之上多两处口径（原型未画）：① 角色授予的资源若已下线/被删除，计数含它而列表没有卡片， 真实页面在汇总条用「另有 N 项未在列表展示」提示（本原型用虚线条目表达同一件事）； ② 「本页全选」只作用于当前筛选可见的可直配项，候选为空时不动作（否则一次点击会清掉看不见的直配）。

计数口径 页签徽标

  • 徽标 = 直配 + 角色已有，也就是「这个用户实际能用几项」，与页签语义一致。
  • 右上角小号数字 = 其中角色授予的条数；悬停显示拆分（如「直配 1 · 角色 3」）。
  • 禁用资源页签口径不变——它是黑名单计数，已有「来自角色（只读）」专块，不要混进这套数字。
原因：现在徽标只算直配，角色给了一堆资源的用户，在「智能体」页签上显示 0，管理员会以为他没权限。

「本页全选」必须跳过继承项 防固化

  • toggleSelectAll 现在把 selectableResources 全塞进直配——加上继承项后，全选会把它们写成用户直配。
  • 按钮文案改为「本页全选（不含角色已有）」；「全部取消」只清直配。
  • 同理，提交 payload 仍然只由直配构建（buildUserPermissionPayload 已如此）。
后端只在命令 / 工具 / 技能上做了角色派生剔除，资产五类没有兜底，前端这一关必须自己守住。

可用模型页要单独说清楚 方向相反

  • 模型是白名单：未配置 = 不限制；一旦有值，只能在这些模型里切换。
  • 角色已选的模型会并入白名单——用户页取消勾选也不会生效（后端按并集算），所以必须禁用、并给出「去角色页调整」的出口。
  • 页签说明补一句：本页显示的是「直配 + 角色」的合并白名单。
这是唯一一个「角色授予会收紧而不是放宽」的资源类型，文案照抄其它页签会误导。

徽标要区分来源 角色 / 全员基线

  • 数据集页的继承项里会混入 subject_type='all' 的全员基线授权，标成「角色已有」是错的。
  • 低成本做法：徽标写「角色 / 全员已有」，tooltip 说明「由角色或全员基线授予，只读」。
  • 要精确到「哪个角色」，需要后端新增按来源拆分的字段（如 inherited_sources[]），前端单独做不了。
本轮若不想动后端，先用笼统徽标；来源明细那块在原型里已画出效果，标了「需后端补字段」。

旧后端降级 usingEffectiveFallback

  • 响应里没有 direct_permissions 时，整块按并集处理，此时无法区分继承。
  • 这种形势下必须关闭徽标与灰勾（否则会把用户的直配项全标成"角色给的"），回落到当前行为。
  • 已有 resolveUserPermissionEditState().usingEffectiveFallback 可直接用。
宁可不显示，也不能标错来源——标错比不标更难排查。

列表过滤不能把继承项藏掉 失联 / 私有 / 搜索

  • 「隐藏失联知识库」默认开、模型搜索会过滤、私有库被禁用——继承项也不能被这些过滤隐藏，否则用户有权限却查不到来源。
  • 优先级：私有库（永不参与授权）＞ 失联（保留但提示）＞ 角色已有（只读）。
  • 角色授权指向的资源已被删除/下线时，渲染一条虚线「列表外」提示项，别静默吞掉。
原型里「外部 API」页放了一个已下线的例子，可以看到虚线卡片的处理方式。

改哪个文件 实现时（本轮不动代码）

  1. frontend/src/utils/permissionLists.ts：给 UserPermissionEditState 增加 inheritedAssets（5 类差集，复用现成的 diffInheritedIds），新增 isInheritedAsset 判定。
