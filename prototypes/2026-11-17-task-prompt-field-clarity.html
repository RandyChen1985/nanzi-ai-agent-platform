两个指令字段怎么填 —— 现状问题与三套引导改法

用户的困惑不是「字太小」，而是三个字段层面的问题：名字是内部术语（执行指令 / 任务约束指令）、两栏看起来平级（像要写两遍指令）、 占位符是术语堆叠而不是示范。下面三套方案按改动量递增，都能在一个 HTML 里点开对比。

问题 1 · 命名

「执行指令」「约束指令」长得一样

两个都叫「指令」，用户读不出「一个是写任务、一个是写规矩」。字段名的实际含义是 要做什么 / 怎么做，但页面上没有一个字这么说。

问题 2 · 占位符

给的是术语碎片，不是示范句

约束框写着「用无序列表呈现、按移动端阅读排版；禁止输出图表代码块…」，四个维度并列，用户读到的是名词列表，学不到「我该写一句话还是写一排」。

问题 3 · 分工说明

关键解释藏在 10px 浅灰小字里

「要做什么填上面、怎么做填这里」放在输入框下方、字号最小、颜色最浅，还必须点 ? 才能看到完整版。填的时候眼睛在框里，看不到它。

为什么用户会卡住

  • 两个字段是平级的两个「指令」：视觉权重相同、都用大写字母标签，用户第一反应是「要写两遍吗」。
  • 占位符在教「维度」而不是「写法」：四个维度并列给到人，等于没给示范。执行指令那句「帮我查一下…」又像随手聊天，和旁边「插入模板 / AI 优化 / 资源限定」这些重装备相互矛盾。
  • 「可选」只是一枚灰标签：用户不清楚不填会不会任务失效，于是倾向硬凑内容，反而更容易和平台规范打架。
  • 分工说明位置错误：解释放在框下方 10px 浅灰处，而完整仲裁说明要主动点 ?。填的时候看不到。

影响面：这两处文案在 TaskCenter.vue 表单里，以及 TaskPromptComposer.vue 的占位符； 后端术语（config.task_constraints / 「任务执行指令」）不需要跟着改。

方案 A 改了什么

  • 标签改成人话：主标签 要做什么 / 输出有什么要求，旧术语降为浅色副标（执行指令 / 任务约束），文档和老用户还能对上号。
  • 占位符改成示范句：先说「写什么结构」，再给一整句真实例子，用户可以直接照抄改字。
  • 「可选」写成后果：从灰标签 可选 改成 选填，不填就不生效，消除「不填会不会废」的顾虑。
  • 分工说明上移并改双向指引：第一栏末尾指向第二栏（格式要求去哪儿），第二栏末尾指回第一栏（任务写哪儿）。

代价：低。纯文案替换，不动结构、不动数据。需同步更新 tests/frontend/test_task_constraints_contract.py 里锁定的几句文案断言。

局限

  • 两栏依然平级，没有先后关系；顺序感靠读文字建立，不是靠视觉。
  • 用户仍然要自己判断「这属于格式还是属于任务」，判断错了没有反馈。

方案 B = A 的全部 + 三件事

  • 序号 1 / 2 建立先后：不再像两个并列的「指令」，而是「先写任务，再写要求」。第 2 栏用灰序号 + 「留空不影响任务」，弱化它的存在感。
  • 常驻提示条贴在输入框上方：不再靠下方小灰字和 ? 弹窗。第 1 栏的提示条直接点明「格式类要求去第 2 栏」。
  • 空态一键加常用约束：不会写就点，最典型的是「不要图表」——这正是当初做这个字段的起因。
  • 写错位置的实时纠偏（试着在第 1 栏输入「不要画图表」）：检测到格式类措辞就提示并支持一键搬移。

代价：中。只动前端一个文件（TaskCenter.vue）+ 契约测试；不动后端、不动数据结构。

两处需要你拍板

  • 「移到第 2 栏」纠偏提示：设计文档里曾把「老任务约束迁移辅助」定为不做（理由：改为文案引导即可）。本次反馈正好说明纯文案不够，建议重启这一项，但范围收窄为「实时提示 + 一键搬移」，不做历史任务批量迁移。
  • 空态常用约束 chip：设计文档里「约束模板下拉」也定为不做（理由：和帮助弹窗示例重复）。这里改成框内一键加、不开弹窗，不重复；但确实新增了交互，需你确认接受。

保存时拆成「任务内容」+ 3 条「输出要求」：不要图表 / 用列表 / 金额按万元。可在保存前展开微调。

方案 C 的做法与代价

  • 认知负担最低：用户只面对一个框，不用判断「这句该写哪儿」。
  • 代价 1 · 多一次 LLM 调用：每次保存都要拆分，定时任务量大的租户会产生不可忽视的调用量。
  • 代价 2 · 拆错就是静默错：把业务口径拆进任务层，或把任务动作拆进约束层，用户不展开看根本发现不了，反而比现在更难排查。
  • 代价 3 · 兼容面大：已有任务两栏数据要能回填进单框；create_recurring_task 工具写入的路径也要跟着改。
  • 代价 4 · 与「优先级」的产品叙事冲突：这个字段的价值就在于「我明确知道它进了 system」，自动拆分让这件事变得不可见。

结论：不推荐。除非后续确认「两栏」本身就是错的抽象。

怎么用这张表

  • 替换现有 ? 弹窗里那四条「输出形态 / 业务口径 / 数据范围 / 禁止事项」抽象条目 —— 用户能对号入座，而不是读定义。
  • 最后一行的留空示例很关键：明确告诉用户「不是每栏都必须填」。
  • 左边「场景」列写的是人的目的（移动端看、只想要结论），不是字段术语。

一句话取舍：如果只想低成本止血，选方案 A（半天内可交付、零结构改动）； 如果按这次反馈认真解决「不知道怎么填」，选方案 B（A 的全部 + 序号 + 常驻提示 + 一键加 + 位置纠偏），其中「一键加」和「位置纠偏」两处属于之前设计定案里明确不做的项，需要你点头。 方案 C 只在「两栏本身就是错的抽象」这个前提下才值得讨论。
