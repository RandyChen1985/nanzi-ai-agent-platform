# 候选正文实时流式设计

## 目标

让不依赖工具和当前轮证据校验的通用问答在模型输出时立即更新正文；如果模型随后决定调用工具，则撤回这段候选正文，并将其保留为过程说明，避免未核实文本留在最终回答区。

## 范围与边界

- 仅适用于 `general` 对话，且当前轮不要求 grounding 证据校验的 AgentScope 原生流。
- 数据查询、知识库、外部搜索及任何当前轮证据受限的路径维持现有的“过程说明后提升”为正文的策略。
- `todo_write` 是记事工具，不触发撤回；其后的终帧仍按无工具正文处理。
- 非 `todo_write` 工具一经发起，本轮此前的候选正文都必须撤回并提交为过程说明；本工具轮之后继续采用保守输出策略。
- 不改变历史落库、权限确认、外部执行恢复、多智能体最终合成及 grounding 的既有语义。

## 事件协议

### 无工具的通用问答

1. 后端收到文本 delta 后输出 `{type: "answer_delta", phase: "candidate"}`，并在状态机中累计为正文。
2. 前端沿用现有 rAF 缓冲将其写入正文。
3. `MODEL_CALL_END` 不再额外发射 `process_narration_promote`，避免正文重复。

### 候选正文后出现工具

1. 后端先输出 `{type: "retraction", final: false, content: ""}`，清空前端候选正文和后端已累计的候选正文。
2. 后端将候选内容发为 `process_narration` 与 `process_narration_commit`，使其在时间线保留为过程说明。
3. 工具执行后产生的文本继续走现有保守路径，只有在模型调用结束时才提升为正文。

### todo_write

`todo_write` 仅更新待办卡，不改变候选正文归类，也不触发撤回；若该轮没有其他工具，候选正文在结束时保持为正文。

## 后端状态机

`process_narration` 状态新增候选正文标记。它负责三件事：

- 判断当前回合是否有资格实时发送候选正文；
- 累积候选文本，并在无工具结束时避免重复 promote；
- 遇到非记事工具时，按“撤回 → 过程说明提交”的顺序收敛状态。

资格由运行时显式传入，不能仅根据“尚未看到工具”推断。这样数据、知识库和 grounding 路径仍保持保守策略。

## 前端行为

前端继续复用 `answer_delta` 的 rAF 缓冲。处理 `retraction` 前必须先 flush 已缓冲正文，再执行共享 SSE 分发器，确保撤回不会被后到的 rAF 片段重新写回。`process_narration` 继续显示在执行时间线，不写入正式正文。

## 验收与测试

- 通用无工具流：首个文本为 `answer_delta/candidate`，最终正文恰好出现一次。
- 候选文本后出现业务工具：事件顺序为 `answer_delta`、`retraction(final=false)`、`process_narration`、`process_narration_commit`；最终正文不含候选文本。
- `todo_write` 后结束：不发撤回，候选文本保留在正文。
- 不具备候选资格的流：保持原有 `process_narration → process_narration_promote`。
- 前端运行时覆盖 rAF 缓冲后撤回，断言没有残留候选正文。
- 覆盖执行性能统计：分别记录首个可见事件与首个正式正文，避免将候选过程误记为最终正文 TTFT。

## 非目标

- 不为数据、知识库或需要 grounding 的路径启用候选正文。
- 不改变模型、工具、锁、会话持久化、权限恢复或多智能体调度的调用顺序。
- 不引入新的用户配置项；是否允许候选正文由服务端运行时依据路由与证据要求决定。
