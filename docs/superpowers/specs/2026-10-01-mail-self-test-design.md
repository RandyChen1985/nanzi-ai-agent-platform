# 个人中心「测试发信」设计

**日期：** 2026-10-01
**需求（用户原话）：** 「个人中心，修改邮件（按钮）的后面，加个测试的按钮，测试发送邮件，方便看看自己的邮件是否能（收到），只有全局邮件服务开启了才显示，否则不显示该按钮」

---

## 1. 目标

个人中心的邮箱卡片里，在「修改邮箱」后面加一个「测试发信」按钮，让用户自己验证「平台邮件服务 + 我的邮箱」这条链路是否通。

## 2. 范围

**做：** `GET /auth/me` 新增可用性标志位；新增 `POST /auth/me/email-test` 自测端点；个人中心邮箱卡片加按钮。

**明确不做（已与用户逐项确认）：**
- **不提供任意收件人**（收件人固定为本人邮箱，请求体不接受 `to`）
- 不新增配置项、不新增开关、**不新增数据库迁移**、不建表
- 不吃公开接口面（标志位放在需登录的 `/auth/me`，不放 `/config/public`）

## 3. 显示条件（三者同时满足）

| 条件 | 取值 |
|---|---|
| 全局邮件服务可用 | `load_global_smtp_settings() is not None` |
| 用户已设邮箱 | `userInfo.email` 非空 |
| 不在邮箱编辑态 | `!isEditingEmail` |

用户选定：**没设邮箱时按钮直接不显示**（旁边本就是「设置邮箱」，引导自然），而不是置灰或点击后报错。

## 4. 标志位来源

`GET /auth/me` 的 `data.mail_service_available`。

个人中心本来就会调这个接口（`PersonalCenter.vue:200` → `userInfo.value = response.data.data`），因此**不新增请求**；也避免把「平台邮件是否配置」暴露到未登录可访问的 `/config/public`。

## 5. 新端点 `POST /api/portal/auth/me/email-test`

与既有的 `PATCH /auth/me/profile` 同族命名。仅需登录（`require_api_key`），不要求任何 `element:*` 权限。

### 5.1 收件人固定为本人

实时查库取当前用户邮箱（**不能**用 `require_api_key` 注入的 user dict：它缓存在 Redis、TTL 1 小时，改了邮箱会发到旧地址 —— 与 `/auth/me` 里 `current_email` 的处理同因）。

**请求体不接受任何收件人字段。** 这不是省略：一旦允许传 `to`，任何登录用户都能借这个按钮给任意地址发信，平台等于垃圾邮件中继。已有的管理端 `POST /configs/email/test` 允许任意收件人，是因为它要求系统配置权限（`element:system:config_save`）。

### 5.2 响应契约

| 情况 | HTTP | 响应体 |
|---|---|---|
| 发送成功 | 200 | `{"ok": true, "message": "测试邮件已发送，请查收"}` |
| SMTP 发送失败 | 200 | `{"ok": false, "message": "<失败原因>"}` |
| 未设邮箱 | 400 | `{"detail": "请先在个人中心设置邮箱"}` |
| 全局邮件服务未启用 | 503 | `{"detail": "平台邮件服务未启用或配置不完整"}` |
| 冷却中 | 429 | `{"detail": "操作过于频繁，请 N 秒后再试"}` |

为什么发信结果用 200 + `ok` 而不是错误码：与同族的**管理端测试端点**（`{"ok": bool, "message": str}`）保持一致，前端只需读两个字段就能把「收到的原因」原样呈现给用户 —— 这正是用户点这个按钮想看到的东西。

为什么未启用用 503：沿用邮件找回确立的约定（平台级不可用 → 503；与提交内容无关的前置条件）。

### 5.3 检查顺序与冷却

顺序：**未设邮箱(400) → 服务未启用(503) → 冷却(429) → 发送**。

- 先做前置检查，冷却只在**确实要发送**时才消耗。
- **冷却无论发送成败都计**（60 秒/人）：否则 SMTP 配错时用户可以无限猛刷，把一次配置故障放大成持续负载。
- Redis 键 `auth:mailtest:cd:{user_id}`，`SET NX EX 60`，不建表。
- 命中冷却时把剩余 TTL 写进提示文案，用户知道要等多久。

### 5.4 复用

`load_global_smtp_settings()` + `send_mail()` + `run_in_threadpool`（SMTP 同步阻塞，必须丢线程池，否则卡住事件循环）。

## 6. 正文

不写死站点地址（与 `build_review_mail` 的既有取舍一致：平台没有「站点基础地址」配置项）。

```
主题：【{发件人名称}】邮箱可用性测试
您好，{账号名}：

这封测试邮件发送到了您在个人中心设置的邮箱。
收到它说明平台邮件服务与您的邮箱均可正常收信。

（本邮件由系统自动发送，请勿直接回复）
```

## 7. 前端

邮箱卡片右侧按钮组（`PersonalCenter.vue:806-813`）内新增「测试发信」，位于「修改邮箱」**之后**：

- 显示条件见 §3
- 点击进入发送态（按钮禁用、文案「发送中…」）
- 成功 → toast「测试邮件已发送，请查收」；失败 → toast 显示后端 `message`
- 冷却期内按钮禁用并显示剩余秒数，与后端 60 秒一致（后端仍是最终裁决，前端倒计时只是体验）

## 8. 测试

**后端**（新增 `tests/test_mail_self_test.py`）：
1. `/auth/me` 的 `mail_service_available` 随全局邮件服务可用性变化
2. 只发给本人实时查库的邮箱（构造带 `to` 的请求体也**不能**改变收件人）
3. 未设邮箱 → 400
4. 全局服务未启用 → 503
5. 冷却：首次成功；紧接着第二次 → 429 且提示含剩余秒数
6. **冷却在发送失败时同样被消耗**（防对故障 SMTP 猛刷）
7. SMTP 抛异常 → 不冒泡成 500，返回 `ok:false`
8. 响应体不含密码/API Key 等凭据
9. 改了邮箱后测试信发往**新**邮箱（防 Redis user dict 陈旧值）

**前端契约**：按钮受「邮件服务可用 + 邮箱非空」双条件控制；位于「修改邮箱」之后；冷却常量 60 秒；不提供收件人输入框。

**反向验证**：逐条注入变异（去掉冷却、冷却只计成功、收件人改读请求体、去掉双条件之一、把实时查库换成 user dict），确认对应用例变红，且每次变异前后做字节级还原校验。

## 9. 风险

| 风险 | 处置 |
|---|---|
| 被当成任意收件人发信的中继 | 收件人固定为本人，请求体无 `to`（§5.1），并有测试钉住 |
| 用户猛刷耗 SMTP 配额 | 60 秒/人冷却，成败都计（§5.3） |
| 改了邮箱仍发往旧地址 | 实时查库，不读 Redis 缓存的 user dict（§5.1），并有测试钉住 |
| 把平台邮件配置状态泄露给未登录用户 | 标志位只放需登录的 `/auth/me`（§4） |
| 按钮显示了但发不出去 | 未启用时不显示按钮；后端仍返回明确的 503 文案 |

## 10. 验收标准

1. 全局邮件服务开启且用户已设邮箱时，「测试发信」出现在「修改邮箱」之后
2. 邮件服务关闭，或用户未设邮箱时，按钮不显示
3. 点击后本人邮箱收到测试邮件，正文为 §6 内容
4. 收件人不可由请求指定
5. 60 秒内重复点击被拒（429，提示含剩余秒数），发送失败也占用冷却
6. 未启用 → 503；未设邮箱 → 400；SMTP 失败 → 200 + `ok:false` 且原因可读
7. 零迁移、零新增配置项、不改公开接口
8. 后端用例与前端契约全绿，既有基线不退化
