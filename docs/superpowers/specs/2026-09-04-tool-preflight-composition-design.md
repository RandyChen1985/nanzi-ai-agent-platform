# 工具预检精度、流式撤回与多工具证据合同设计

## 目标

在保留现有工具权限、思考卡片、证据门禁和历史上下文语义的前提下，补齐六类通用场景：能力咨询不应被强制调工具、预检异常时应避免误选工具、POST 查询应能声明只读、中文概括不应被过度误杀、严格证据门禁应支持可选流式撤回，以及复合问题应按工具分别建立证据合同。

## 范围与非目标

本设计基于运行时工具的名称、描述、权限和证据类型，不为车票、天气或任何具体业务工具增加特判。默认门禁模式保持当前的安全缓冲模式；默认单工具路由、权限确认、历史摘要和前端 retraction 消费协议不改变。

不在本次范围内的是让服务端替模型自动执行所有多工具调用、用新的 LLM 调用做语义相似度判断、把工具结果写入可见正文、删除 `<backend_tool_run_summary>`，或修改数据库实例/表结构。

## 方案

### 1. 元问题采用独立的前置判定

新增 `_looks_like_tool_meta_query()`，返回“仅能力咨询”信号。只有“支持/能否/有没有什么工具/怎么用/需要什么参数”等元问题且没有真实业务目标时才命中；包含具体查询目标的混合句仍进入正常路由。

命中后，预检仍可以向模型提供已绑定工具的能力摘要，但不得设置具体 `tool_choice`、`force_first_call` 或当前轮证据门禁。`ask_user_question`、明确点名工具调用、Office 写入、子代理委派等已有显式动作优先级高于元问题过滤。

### 2. Fallback 使用更高阈值和候选差距

`resolve_evidence_tool_fallback_nudge()` 默认最低分为 `0.35`。只读且有 evidence types 的候选按相关度排序；存在第二候选时，第一名必须至少领先 `0.10`，否则返回空。元问题、少于两个有效信号、仅命中泛化停用词的候选直接返回空。

最佳候选仍只能是当前已绑定工具，且 fallback 只锁定证据型具体工具；它不改变常规预检的阈值，也不把写工具转换为读工具。

### 3. Generic API 统一按只读查询工具处理

`sys_api_tools` 的产品约束是只登记只读接口，因此 Generic API 工厂不再根据 HTTP
方法区分读写，GET 和携带复杂查询条件的 POST 都注册为只读工具，并默认声明
`EXTERNAL_TOOL` 证据类型。该约束只影响运行时工具元数据，不绕过现有权限和确认机制。

### 4. Overlap 引入受限的 provenance 豁免

成功收据只在“非具体执行状态总结”场景豁免关键词关联，例如“查询已完成”“数据已同步”。回答中出现数字、日期、编号、地点、表格、业务对象或具体状态值时，仍必须有当轮收据且与收据关键标记关联；矛盾标记仍触发 warning/block。

同时扩展 marker 规范化：保留大小写无关的 ASCII 标识、日期/时间、数字和中文连续片段的稳定摘要，允许同一收据的结构化 JSON 和模型中文概括共享关键标记。该优化只降低真实收据的误杀，不把“有成功调用”作为全部事实的放行条件。

### 5. 流式撤回模式默认关闭

读取系统配置 `agent_grounding_block_mode`，合法值为 `strict_buffer` 和 `stream_with_retraction`，非法值回退 `strict_buffer`。

- `strict_buffer`：继续暂存严格证据回答，审计通过后一次性发送；失败时只发送安全答复。
- `stream_with_retraction`：严格证据回答先正常发送可见 delta；结束审计失败时发送 `retraction`，内容为安全答复，并保留已有 fallback notice。最终持久化以 retraction 后的正文为准。

普通 grounding warning、权限确认挂起、工具过程日志和非事实回答不进入新的撤回分支。

### 6. 多工具计划与独立证据合同

新增轻量 `ToolNudgePlan`：只有用户句子被明确连接词拆成至少两个独立子句、每个子句各自命中不同的高置信证据型只读工具时才生成。计划包含首工具、后续工具顺序和每个工具的 `tool_name`、`required_evidence_types`、`freshness=current_turn` 合同。

首工具沿用现有 `tool_choice`，后续工具只通过系统提示注入执行顺序，交给模型按正常循环调用。预检日志增加 `evidence_contracts`，并保留原有 `required_evidence_types` 字段兼容单工具消费者。

严格审计时，每个合同都必须有当轮、匹配 producer 的成功收据；具体事实还要通过对应收据的关键标记关联。缺任一合同、收据复用上一轮或工具失败，整体使用安全答复。单工具、低置信复合问题和写工具保持原路由。

## 数据流

```text
用户问题
  -> 元问题判定
  -> 单工具 nudge 或多工具 ToolNudgePlan
  -> 首工具 tool_choice + 证据合同日志
  -> AgentScope 工具调用/结果
  -> 当前轮 EvidenceLedger（按 producer 分组）
  -> strict_buffer 审计 或 stream_with_retraction 审计
  -> 放行真实答案 / retraction 安全答复 / strict block 安全答复
```

## 兼容性与风险控制

1. 元问题只关闭强制取证，不删除工具描述，因此模型下一轮仍能理解能力范围；真实查询不会被误判为能力咨询。
2. Generic API 表内接口统一按只读查询处理，因此 POST 查询也能进入实时证据链路；不新增字段或数据库迁移。
3. 流式撤回不是默认值，前端继续使用已有 retraction 替换累积正文的逻辑。
4. 多工具合同是严格增量路径，无法稳定识别时退回已有单工具/普通回答，不服务端猜测或批量执行工具。
5. 本次不修改数据库表结构，也不在 Agent 运行时执行 DDL。

## 测试策略

覆盖元问题与混合查询、fallback 阈值和 gap、Generic API 的 GET/POST 只读运行时元数据、非具体总结/具体事实/矛盾事实的 grounding 审计、两种 streaming 模式的事件序列、前端 retraction 消费、多工具计划识别、每个合同按 producer 独立校验，以及既有权限确认/历史复用/单工具流程回归。
