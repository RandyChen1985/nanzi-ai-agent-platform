# 快捷结果追问路由设计

## 目标

修复从 ChatBI/查数回答中的通用 `quick:` 按钮继续提问时丢失来源的问题：保留多轮对话上下文，同时让明确来自查数结果的快捷追问重新进入查数执行链，避免主助手参考旧结果生成未经查询的新数字。

## 设计

- `MessageRenderer` 继续作为通用 Markdown 渲染器。快捷事件增加可选来源信息，但普通调用方仍可只接收问题字符串。
- `EmbedChat` 在渲染具体助手消息时识别可信的 ChatBI 结果来源，将快捷事件标记为 `chatbi_result`，并携带结果 ID和 `requires_fresh_data=true`。元数据只存在于内存和请求体，不显示在用户气泡或正文中。
- 普通欢迎卡、写作/系统命令、知识库入口和数据门户自身的快捷入口不自动套用 ChatBI 标记，保持原有路由。
- 服务端把快捷来源作为当前轮路由提示：历史上下文继续由会话加载，但当前轮必须重新获得查数凭证；没有成功工具结果时只返回友好引导，不接受旧上下文中的具体数字作为本轮事实。

## 验证

- raw Markdown `quick:` 从可信 ChatBI 消息点击后，发送请求包含内部来源标记并触发查数路由。
- 普通 `quick:` 仍只发送问题，不携带 ChatBI 强制标记。
- 结果 ID等内部字段不会进入展示文本。
- 无本轮证据时不生成具体查数结论；已有真实工具结果的正常多轮追问不受影响。
