# 工具证据来源与执行卡片一致性设计

## 目标

修复通用助手在需要外部/实时数据时可能跳过工具调用、仍生成具体答案的问题，并让思考卡片与执行链路能准确表达当轮工具执行状态。

本次不针对车票、天气或任何单一业务工具写特判，规则基于工具的来源、证据类型和只读能力元数据。

## 当前根因

1. 通用工具预检默认是 `soft`，普通 MCP 工具只收到 prompt 提示，不一定真正调用。
2. 只读 MCP 工具虽然已经拥有 `evidence_types`，但 `resolve_tool_metadata()` 将它们返回为中性 metadata，通用 nudge 不会据此强制首调用；证据工具的低相关度分支还可能退化成任意工具 `required`。
3. 执行链路只展示已落库的 trace span；没有当前轮 `tool_call` span 时，前端无法区分“模型跳过工具”和“复用了历史结果”。
4. 当前接地审查多数情况下只追加风险提示，不阻止当前轮没有证据支撑的具体事实。
5. 工具完成 trace 使用模型调用计数器的当前值，没有为工具单独递增，多个事件可能共享 `step_number`，导致审计排序不稳定。
6. 预检异常仅记录日志后继续，会让证据门禁 fail-open；按名称推断的已知工具 metadata 也可能覆盖运行时写权限。

## 设计

### 1. 统一识别证据型只读工具

`resolve_tool_metadata()` 保持未知工具的默认中性行为，但对以下工具返回 `nudge_mode="evidence"`：

- 已声明 `evidence_types` 的只读工具；
- 来源为 `mcp` 且运行时权限为 `read` 的工具；
- 通用 HTTP `GET` 工具（工厂显式标记为只读）；
- 已有静态证据 metadata 的内置工具。

这只是执行策略提示，不授予工具权限。实际权限仍由 AgentScope permission hook、确认策略和工具自身执行边界决定。

### 2. 证据型工具命中后强制首调用

通用 `resolve_tool_nudge()` 选中证据型工具后，将 `force_first_call=True`，且无论相关度是否达到普通强制阈值，都锁定这个具体工具。因此默认 `soft` 模式也会为高相关证据工具构造首步 `tool_choice`；`off` 仍保留为明确关闭预检的兼容开关。运行时 `permission_scope` 优先于按名称推断的 metadata，写工具不会被误标为证据工具。

预检 SSE 日志增加安全诊断字段：

```json
{
  "current_turn_evidence_required": true,
  "required_evidence_types": ["external_tool"],
  "force_first_call": true
}
```

前端继续使用现有日志链路，不需要把工具参数或结果写入预检日志。

### 3. 当前轮证据最终门禁

当预检日志声明 `current_turn_evidence_required=true` 时，Assistant runner：

- 暂存本轮最终正文 delta，继续实时发送思考、工具和权限事件；
- 工具成功结果由现有 `EvidenceLedger` 记录；
- 严格校验要求动态证据，并从审计视图中排除 `reuse_previous` 历史收据，避免上一轮结果满足本轮门禁；
- 结束时使用已有 `GroundingService` 检查证据类型和内容关联；
- 证据缺失、过期或与具体答案不匹配时，不发送模型生成的具体事实，只发送统一的安全说明和 `grounding_blocked` 标记日志；
- 明确的“暂无结果、无法确认、需要重试”等非事实回答可以正常放行。

普通可选接地请求仍保持原有风险提示语义，避免扩大到所有普通问答。

### 4. 执行可观测性

- AgentScope `TOOL_CALL_START` 和工具完成日志显式设置 `category="tool"`，不再依赖标题文本推断。
- 预检日志暴露是否要求当前轮证据，便于思考卡片解释为什么工具必须执行。
- 工具完成 trace 创建前递增执行步骤编号，保证同一 trace 内事件顺序稳定。
- `<backend_tool_run_summary>` 仍只进入模型上下文，不进入用户可见正文或思考卡片。

## 数据流

```text
工具解析
  -> 证据型只读 metadata
  -> 通用工具 nudge
  -> 首步 tool_choice
  -> TOOL_CALL_START / TOOL_RESULT_END
  -> EvidenceLedger + tool_call trace + 思考卡片日志
  -> 最终证据校验
  -> 放行真实答案，或阻止未核实具体事实
```

历史结果复用仍走现有 `reusable_result_status` 和 artifact 上下文；复用场景不标记为当轮工具调用，前端使用已有复用提示表达来源。

## 错误与降级

- 模型供应商不支持强制 `tool_choice` 时，现有兼容 fallback 可以继续尝试，但最终证据门禁仍生效。
- 工具权限确认、外部执行挂起和恢复沿用现有流程；恢复成功后由同一账本参与最终校验。
- 工具失败或空结果允许模型明确说明失败/暂无结果，但不得继续声称具体实时数据。
- 预检解析失败时，若存在匹配的证据型只读工具，则使用最小安全 metadata 重新锁定该工具并开启当前轮证据门禁；无匹配证据工具时才保持普通问答兼容。
- 不新增数据库表和迁移，不修改已有历史 `tool_run_text` 的模型上下文语义。

## 测试策略

覆盖以下回归矩阵：

1. 未知只读 MCP 工具 metadata 被识别为证据型。
2. 通用工具 nudge 命中证据型工具时强制首调用；普通未知工具仍不强制。
3. 预检事件正确携带当前轮证据要求和证据类型。
4. 当前轮没有证据时，具体事实被阻止；明确无结果文本放行。
5. 当前轮工具证据与答案关联时放行。
6. 标准工具开始/完成日志带 `category="tool"`。
7. 工具 trace 步骤编号递增且不与前一模型调用共享编号。
8. 既有历史复用、权限确认、普通问答和原有接地 warning 测试保持通过。

## 非目标

- 不强制所有 MCP/API 工具调用；写入工具仍遵循权限确认。
- 不改变前端 trace 查询接口和数据库表结构。
- 不把所有普通问答改成必须有工具证据。
- 不删除或清空模型上下文中的历史工具摘要。
