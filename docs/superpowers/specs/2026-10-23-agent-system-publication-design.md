# 智能体系统级发布机制设计（A 期：系统级生命周期）

- 日期：2026-10-23
- 范围：智能体中心的系统级治理（发布、下架、申请审核、发布历史、通知）
- 不在本期：智能体分享与克隆（B 期，见文末）

## 1. 背景与问题

现状：

- `ai_agents.is_system` 是智能体级布尔，**管理员在创建/编辑表单里直接勾选**即可设为系统级。
- 系统级身份在运行时被大量消费：自动委派候选（`agent_delegate_tool`）、路由候选（`router_service`）、授权口径（`permission_service` 中「系统智能体需授权才能对话」）。
- 版本自身有 `DRAFT / PUBLISHED / ARCHIVED` 状态与「发布版本」接口，但**版本发布与系统级身份之间没有任何关联**，也没人记录「谁在什么时候把哪个版本变成了平台基线」。
- 结果是：管理员一次勾选就能把一条智能体变成平台公共资产，没有审核、没有历史、没有下架流程；普通用户也没法申请把好东西沉淀成平台能力。

目标：

1. 系统级只能通过「发布」动作获得，创建/编辑表单不再能直接设置（管理员也不行）。
2. 发布 / 下架都有操作记录，且能查看每次发布的内容快照。
3. 普通用户可提交发布申请，管理员审核通过后成为系统级；系统级期间所有者只读，只能复制（clone）另开一条继续开发。
4. 下架前提示已分配给多少人，并给已分配用户发站内信。

## 2. 关键决策

| 决策点 | 结论 |
| :--- | :--- |
| 分期 | 分两期：A 系统级生命周期（本文档），B 智能体分享与克隆 |
| 锁定粒度 | **智能体级锁定**：发布后整条智能体对非管理员只读（不能建版本、不能改草稿），只能复制；下架后恢复可编辑。所谓「基线」就是运行时取的当前 PUBLISHED 版本，不额外引入基线字段 |
| 申请与审核角色 | 申请：该智能体所有者；审核/直接发布/下架：持 `element:agent:system_publish` 权限的人（管理员天然拥有）。管理员自己发布直接生效，不走审核 |
| 直接发布的范围 | 持权限者可对**任意**智能体直接发布（强制上架），但必须同事务给该智能体所有者发站内信告知「你的智能体已被发布为系统级」 |
| 审核人兜底 | 提交申请时若查不到任何持 `element:agent:system_publish` 的用户，兜底通知全部 `role=admin`；管理员天然持有该权限，因此实际不会出现无人可审 |
| 紧急停用 | **不新增能力**：复用现有「启用/禁用」按钮（`is_enabled`）。系统级智能体被禁用时保留系统级身份与基线、不通知使用者、静默生效；唯一新增是操作时记一条 `TOGGLE_ENABLED` 事件（现在这类操作完全不留痕）。「下架」仍是独立动作，用于真正退场 |
| 审核的能力边界 | **审核只读**：审核人只做「通过 / 驳回（必填理由）」，不能改内容。内容要改由申请人改了重新提交，或上架后由管理员发布新基线。审核的价值是**记录流程与留痕**，不是二次创作 |
| 上架后的内容更新 | 管理员可对已上架的系统级智能体「编辑 → 发布新基线」：基于当前基线另存新版本、编辑、发布（archive 旧基线），每次记一条 `PUBLISH` 事件。原申请人无此权限 |
| 发布历史范围 | 每次申请/审核/发布/下架都记：操作人、时间、版本号、动作、理由 + **完整内容快照**；仅管理员与该智能体所有者可见 |
| 时间线数据来源 | **申请单表 + 事件表合并**按时间排序展示；同一件事不写两处 |
| 下架后的授权 | **保留授权记录但失效**（不再是系统级，除所有者外无人可用）；重新发布可恢复原授权 |
| 下架通知接收人 | 用户直配 + 角色命中的成员**并集**（真实的可用人群），批量发站内信。**通知与否由操作者在弹窗里勾选，默认勾选**；取消勾选时事件表仍记录 `affected_user_count` 便于事后追溯 |
| 重新上架通知 | 跟随该智能体上次下架时的选择：上次没通知，本次也不通知；上次通知了，本次默认通知（同样可取消） |
| 发布后的可用性 | 发布时**自动把所有者加入该智能体授权名单**（他本来就是使用者），其余人由管理员分配 |
| 不可下架例外 | **主助手（Main）不可下架**：平台默认兜底专家，名称/ID 被路由硬编码引用 |
| 删除策略 | 系统级智能体**禁止删除**，必须先下架；待审期间也禁止删除（需先撤回） |
| 首次发布的入口 | 智能体卡片操作菜单「发布为系统级」（仅持权限者可见）：点击 = 把 `is_system` 置 true + 记一条事件，**与现在表单里勾选该开关等价**，不涉及版本选择、不改变任何版本状态。已上架后的内容更新复用现有「发布版本」流程，发布时自动记 `PUBLISH` 事件 |
| 引擎范围 | **仅 `engine_type = 'LOCAL'` 的智能体可发布为系统级**：RAGFLOW / OPENCLAW 没有版本概念，运行时也取不到配置，走授权/分享（B 期）给同事使用，不进系统级。校验失败返回 400「该引擎类型不支持发布为系统级」 |
| 申请理由 | 申请单增加 `request_comment`（**可选**）：申请人填一句「为什么值得上架、面向谁」，供审核人参考 |
| 待审角标 | 智能体中心顶部「发布审核」入口显示待审数量（`GET /agents/system/requests/count`，仅审核权限可见） |
| 前置校验（必须有已发布版本） | 设为系统级前校验该智能体**至少有一个 `PUBLISHED` 版本**，否则拒绝：「请先发布至少一个版本，再设为系统级」。原因：运行时只按 `status='PUBLISHED'` 取配置（`_latest_published_versions_by_agent`），只有草稿或完全没有版本都会导致设为系统级后无法被调用。申请、直接发布、审核通过三处都要校验 |
| 重新上架通知 | 下架后重新发布，给原授权用户发「智能体 Y 已重新上架，你可以继续使用」（是否发跟随上次下架时的勾选，默认发） |
| 所有者自救 | **A 期不做「申请下架」**：所有者被上架后只能复制或联系管理员下架；下架是管理员单侧动作 |
| 审核通过后是否立即生效 | **立即生效**：`is_system = true` 即进入自动委派与路由候选，与现有勾选行为一致；审核页需提示「通过后将立即参与自动委派」 |
| 孤儿归属 | 下架时若 `created_by` 对应用户已不存在，把 `created_by` 改为本次操作的管理员，避免智能体无人可编辑 |
| 停用/启用记录 | 使用独立事件类型 `TOGGLE_ENABLED`（`reason` 记录「停用」/「启用」），不混入 `META_UPDATE` |
| 审核入口 | 智能体中心顶部「发布审核」入口（仅审核权限可见），待审列表用抽屉 |
| 数据模型 | 方案 A：申请单表 + 事件表 |
| 管理员改元数据 | 名称/描述/头像等元数据管理员可直接改（记一条 `META_UPDATE` 事件）；提示词、工具、模型等**版本内容**必须走「发布新基线」 |
| 申请提交对象 | **不选版本**：申请只是「申请把这条智能体设为系统级」，提交时自动对当前内容做快照（元数据 + 最新版本配置）用于留痕与对比。版本本身的状态、是否 PUBLISHED 都不参与判断 |
| 待审期间编辑 | **冻结，但只冻结所有者**：普通用户提交后进入「审核中」锁定态——不能改元数据、不能建版本、不能发布、不能删除；可撤回（撤回立即解冻）。要并行开发就复制一份。**管理员（持 `element:agent:system_publish` 者）豁免**，可随时编辑，审核只负责留痕 |

## 3. 数据模型

### 3.1 `ai_agents` 新增字段

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `system_status` | `VARCHAR(20) NOT NULL DEFAULT 'NONE'` | 流程状态：`NONE` / `PENDING_REVIEW`。**不**表示是否系统级 |
| `system_pending_request_id` | `VARCHAR(36) NULL` | 当前待审申请单 id（列表一眼看到「审核中」） |

`is_system` 语义保持不变，仍是运行时唯一判定依据：`True` ⇔ 已发布为系统级。避免「双事实源」，迁移风险最小。

### 3.2 `ai_agent_system_requests`（申请单）

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | `VARCHAR(36)` PK | |
| `agent_id` | `VARCHAR(36)` NOT NULL | 索引 |
| `snapshot_version_id` | `VARCHAR(36)` NULL | 快照取自哪个版本（仅用于追溯，不参与发布决策） |
| `snapshot` | `LONGTEXT`（JSON） | 提交时的完整内容快照（元数据 + 版本内容） |
| `status` | `VARCHAR(20)` NOT NULL DEFAULT 'PENDING' | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` |
| `requested_by` | `BIGINT` NULL | 申请人用户 id（用户被删时置空保留审计） |
| `requested_at` | `DATETIME` NOT NULL | |
| `reviewed_by` | `BIGINT` NULL | |
| `reviewed_at` | `DATETIME` NULL | |
| `request_comment` | `TEXT` NULL | 申请人填写的申请理由（可选） |
| `review_comment` | `TEXT` NULL | 审核意见（驳回时必填） |

索引：`(agent_id, status)`、`(status, requested_at)`。

约束：同一 `agent_id` 同时最多一条 `PENDING`。不能用 `(agent_id, status)` 唯一索引（同一智能体历史上会有多条 `APPROVED`），部分索引 MySQL/PG 不便统一，因此由服务层在事务内 `SELECT ... FOR UPDATE` 先查后写，并发用例见 §10。

索引：`(agent_id, created_at DESC)`。

## 4. 状态机

```
                提交申请（冻结）
   NONE ────────────────────> PENDING_REVIEW
     ^                              │
     │ 驳回 / 撤回                   │ 通过
     │                              v
     └────────────────────────  PUBLISHED  (is_system = true)
                                    │
                                    │ 下架
                                    v
                                  NONE  (is_system = false)
```

不变量：

- 同一智能体同时最多一条 `PENDING` 申请。
- `PENDING_REVIEW` 期间 `is_system` 仍为 `false`（未发布）。
- `PENDING_REVIEW` 期间该智能体**对非管理员只读**：元数据更新、版本新增/编辑、版本发布、删除一律 409；只允许「撤回」「复制」「查看」。管理员（持审核权限者）不受限。
- 冻结只拦**非管理员的普通写接口**；管理员的一切写入、以及 `approve`/`publish` 事务内部写入均不受限。
- 复制不受影响：复制产出的是另一条普通智能体，与本次申请无关。
- 管理员在待审期间「直接发布」时，同事务把该智能体的 `PENDING` 申请置为 `APPROVED`（`review_comment = '管理员直接发布'`），不留悬空申请单。
- 审核通过：`is_system = true`、`system_status = NONE`、`system_pending_request_id = NULL`、写 `PUBLISH` 事件、自动授权所有者。**不修改任何版本状态**，也不跑 readiness 校验（版本发布时已校验；设状态本身与现有勾选行为等价）。
- 前置校验：`submit` / `publish` / `approve` 三个入口都要求该智能体已有至少一个 `PUBLISHED` 版本，否则 400；申请提交时校验可避免「申请通过后才发现不能发布」，审核通过时再校验一次兜底（期间版本可能被删）。
- 下架：`is_system = false`，写 `UNPUBLISH` 事件，通知已分配用户，授权记录保留。
- 重新发布（此前有 `UNPUBLISH` 记录）：给原授权用户发「已重新上架」通知；授权因记录仍在而自然恢复。
- 已发布状态下管理员「发布新基线」：不新建申请单，直接发布新版本并写 `PUBLISH` 事件。
- 主助手下架 → 400；系统级删除 → 409（提示先下架）。
- 启用/禁用（复用现有 `is_enabled` 开关）：不改变 `is_system` 与 `system_status`，只让运行时不再选中它；对系统级智能体操作时写一条 `TOGGLE_ENABLED` 事件（`reason = '停用'` / `'启用'`），静默、不通知使用者。非系统级智能体的启用/禁用保持现状（不记事件）。
- 审核通过即生效：`is_system = true` 后该智能体立刻进入自动委派/路由候选（与现有勾选一致），无额外确认步骤。
- 下架时若 `created_by` 对应用户不存在：把 `created_by` 改为当前操作管理员，保证下架后的智能体有人可编辑。
- 直接发布他人智能体：发布成功后给所有者发站内信，申请单（若有）同事务置 `APPROVED`。
- 审核**不校验**「审的版本」与「发的版本」是否一致：审核的职责是记录流程与留痕，管理员在待审期间改了内容也照常发布，历史里保留提交快照即可对比。

## 5. 接口

| 方法 | 路径 | 权限 | 说明 |
| :--- | :--- | :--- | :--- |
| POST | `/agents/{id}/system/requests` | 所有者 + `element:agent:edit` | 提交发布申请（body：`comment` 可选，服务端自动快照当前内容）；无 `PUBLISHED` 版本或非 LOCAL 引擎 → 400 |
| GET | `/agents/system/requests/count` | `element:agent:system_publish` | 待审数量（顶部入口角标） |
| GET | `/agents/system/requests?status=PENDING` | `element:agent:system_publish` | 待审列表（智能体名、申请人、提交时间、版本号、已等待时长） |
| GET | `/agents/system/requests/{request_id}` | 审核人或申请人 | 申请详情：只读快照 + 当前内容（供对比） |
| POST | `/agents/system/requests/{request_id}/approve` | `element:agent:system_publish` | 通过（body 仅 `comment` 可选）：只把 `is_system` 置 true 并记事件，不动版本状态、不跑 readiness；仍无 `PUBLISHED` 版本 → 400 |
| POST | `/agents/system/requests/{request_id}/reject` | 同上 | 驳回，`comment` 必填 |
| POST | `/agents/system/requests/{request_id}/cancel` | 申请人 | 撤回，解冻 |
| POST | `/agents/{id}/system/publish` | `element:agent:system_publish` | 直接设为系统级（任意智能体，通知所有者；body：`reason` 可选 + `notify_restore` 默认 `true`，无版本参数）；无 `PUBLISHED` 版本或非 LOCAL 引擎 → 400 |
| GET | `/agents/{id}/system/unpublish-preview` | `element:agent:system_publish` | 下架预览：受影响人数 + 前 20 个用户名 |
| POST | `/agents/{id}/system/unpublish` | 同上 | 下架，body：`reason` 必填 + `notify`（默认 `true`） |
| GET | `/agents/{id}/system/history` | 管理员或所有者 | 时间线（申请单 + 事件表合并，分页） |

`create_agent` / `update_agent` **忽略**请求体里的 `is_system`（管理员也不能直接设置）：系统级只能由 `publish` 路径产生。

待审冻结：`system_status = PENDING_REVIEW` 的智能体，**非管理员**调用 `PUT /agents/{id}`、`POST|PUT /agents/{id}/versions`、`POST /agents/{id}/versions/{vid}/publish`、`DELETE /agents/{id}` 一律 409（`detail`：「审核中已冻结，请先撤回申请」）；持 `element:agent:system_publish` 者不受限；`POST /agents/{id}/duplicate` 对所有人不受限。

已发布为系统级的智能体：管理员可改元数据（写 `META_UPDATE` 事件）；所有者与其他任何人 `PUT` 一律 403；版本内容改动只能走「发布新基线」。

## 6. 权限

- 新权限点：`element:agent:system_publish`（发布、下架、审核）。需同时登记到后端权限清单与前端权限常量，否则角色管理里分配不出来。
- 现有 `element:agent:edit` 决定能否编辑；系统级期间所有者 `is_editable = false`（现状已如此）。
- 发布时自动把所有者写入该智能体的用户级授权（`resource_permissions` 的 agent 资源），已存在则跳过。

## 7. 通知（站内信）

| 触发 | 接收人 | 文案要点 |
| :--- | :--- | :--- |
| 提交申请 | 持 `element:agent:system_publish` 的用户 | 「X 申请将智能体 Y 发布为系统级，请审核」 |
| 审核通过 | 申请人 | 「你的智能体 Y 已发布为系统级，期间只能复制后继续开发」 |
| 审核驳回 | 申请人 | 「你的发布申请被驳回：{理由}」 |
| 下架 | 授权用户并集（直配 + 角色成员） | 「智能体 Y 已下架，你暂时无法使用；如需继续请联系管理员」 |
| 下架 | 所有者 | 「智能体 Y 已下架，你可以继续编辑」 |
| 直接发布（他人智能体） | 所有者 | 「你的智能体 Y 已被管理员发布为系统级，期间只能复制后继续开发」 |
| 启用/禁用 | 不通知 | 复用现有开关，属于即时运维动作，仅对系统级智能体记事件 |
| 重新上架 | 原授权用户并集 | 「智能体 Y 已重新上架，你可以继续使用」 |

复用 `portal_notification_service`；批量插入按 500 条分批。

## 8. 前端

1. **移除**创建/编辑表单里的「设为系统智能体」开关（含 `Admin Only` 徽标文案）。
1.1 申请弹窗：可选「申请理由」文本框（最多 500 字）。
2. 智能体卡片操作菜单（按权限与状态）：
   - 所有者 + 非系统级 + 无待审：「申请发布为系统级」
   - 审核权限 + 非系统级：「发布为系统级」（点击即设状态，弹窗只填可选说明）。该智能体无 `PUBLISHED` 版本时按钮**置灰**，tooltip「请先发布至少一个版本」；所有者的「申请发布为系统级」同理置灰
   - 审核权限 + 系统级：「发布新基线」「下架」（启用/禁用沿用列表里现有开关，不放进菜单）
   - 管理员或所有者：「发布历史」
   - 待审中（**所有者视角**）：卡片显示「审核中」徽标；操作仅保留「撤回申请」「复制」「预览」；编辑、新建版本、发布版本、删除置灰并提示「审核中已冻结，请先撤回申请」；详情页横幅：「审核期间内容已冻结，如需继续开发请复制一份」
   - 待审中（**管理员视角**）：不置灰、不提示冻结，可照常编辑/建版本/发布；额外提供「通过并发布」「驳回」入口
3. 顶部「发布审核」入口（`v-has-perm`，带待审数量角标）：抽屉为待审列表（支持按提交时长排序，超 24h 高亮），点开详情为**只读快照** + 与当前内容对比，底部「通过并发布」「驳回」。
4. 下架确认弹窗：调 `unpublish-preview`，展示「已分配给 N 人」+ 名单前若干个 + 理由必填 + 勾选框「通知这 N 位用户」（**默认勾选**）；取消勾选时给灰字提示「用户将不会收到通知，可能不知道无法使用的原因」。
5. 发布历史抽屉：时间线合并展示申请（提交/通过/驳回/撤回）与事件（发布/下架/元数据更新），每条可展开看快照 JSON 格式化视图。

### 8.1 卡片与工具栏（实现后按实际观感调整）

**卡片只回答三个问题**：这是什么、能不能用、我能做什么。原先一张卡上有 12 类信息（头像/名称/系统徽标/类型/引擎/就绪度/禁用态/标识符/开关/描述/待完善/能力 chips/创建者/更新时间/调用次数/三个按钮），扫视成本过高。落地时调整为：

| 处理 | 内容 |
| :--- | :--- |
| 删除 | 标识符行（并入标题 `title`）、创建者、更新时间、「暂无描述」占位与固定 `min-h-[2.5rem]` |
| 合并 | 类型徽标 + 引擎 → 一枚 `通用助手 · LOCAL`；调用次数 → 一个 chip 并入能力行 |
| 保留 | 头像、名称、系统徽标、就绪度、启用开关、描述（有才渲染）、能力 chips |
| 新增 | 审核中冻结条（可点直达申请进度） |

**审核中必须「看起来就不能点」**：主按钮变灰「审核中」并 disabled，菜单隐藏「编辑 / 删除」，启用开关 disabled，列表行内编辑按钮禁用但保留位置（避免图标跳动）。**「复制智能体」不参与锁定**——它是所有者当下唯一的出路，锁掉等于把人堵死。

> 冻结条需要「提交时间」，为此 `AIAgentResponse` 增加 `system_requested_at`，由 `attach_system_status()` 在原有那条 SQL 上 `LEFT JOIN ai_agent_system_requests` 一次带出，不额外增加查询。

**工具栏**：视图切换 / 发布审核 / 新建 作为一个操作组整体参与换行，窄屏时整组下移，不再出现「新建智能体」被单独挤到第二行最右的情况。

#### 最终形态（按原型确认后重排）

上面的「操作组打包」只是缓解，最终改成三段式，让「主操作被挤走」在结构上不可能发生：

| 行 | 内容 |
| :--- | :--- |
| 第 1 行 | 标题 + 「共 N 个」+ 说明入口 ‖ **发布审核、新建智能体**（独立容器，不与筛选同流） |
| 第 2 行 | 搜索框独占一栏（`min-w-[220px] flex-1`）‖ 批量 / 网格 / 列表 ‖ 筛选 |
| 第 3 行 | 仅在筛选生效时渲染：chip 回显 + 「清除全部」+ 结果数 |

**7 个分段 tab 整排取消**，筛选维度并入「筛选」面板：状态、类型、引擎、就绪度、来源。原因：tab 中「通用助手 / ChatBI / 知识库」与「类型」下拉是同一维度，两处入口必然出现「各选一个 → 结果全空」。信息没丢——「全部 N」的计数移到标题旁，就绪度与来源成为面板字段。

条件藏进面板后最大的风险是「筛了但忘」，因此用三件套补偿：按钮数字角标（有几个条件生效）、chip 回显（可单个移除）、结果数（找到 N 个）。

> 面板里的「排序」（手动 / 最近更新 / 调用最多）是**新功能**而非搬家，会牵动卡片拖拽与 `sort_order` 持久化，本轮不做。

## 9. 迁移

| 库 | 文件 | 内容 |
| :--- | :--- | :--- |
| MySQL | `db-prod/V185-create_agent_system_publication.sql` | 建 `ai_agent_system_requests`、`ai_agent_system_events`；`ai_agents` 加 `system_status`、`system_pending_request_id` |
| PostgreSQL | `db-prod-pg/V85-create_agent_system_publication.sql` | 同上 |

存量数据：

- 现有 `is_system = true` 的智能体：`system_status` 保持 `NONE`，各补一条 `PUBLISH` 事件（`actor_name = 'system'`，`reason = '存量迁移：历史系统智能体'`，`version_id` 取最新 PUBLISHED 版本，`snapshot` 取该版本当前内容）。
- 若无已发布版本，`snapshot = NULL` 并在 `reason` 中标注。

> 序号已核对：MySQL 当前最新 V184、PostgreSQL 当前最新 V84。

### 9.1 实现记录（落地时补）

**建表必须显式写 collation。** 首次执行 V185 报 `1267 Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT)`：`ai_agents` 是老表、collation 为 `utf8mb4_unicode_ci`，而库默认已升到 `utf8mb4_0900_ai_ci`，新表继承库默认，于是补存量事件的 `e.agent_id = a.id` 直接比较失败。生产库同为此结构，所以建表语句写死 `COLLATE=utf8mb4_unicode_ci`，不要依赖库默认。

**两列不写进 ORM。** `system_status` / `system_pending_request_id` 若声明在 `app/models/agent.py`，任何尚未执行迁移的环境都会因为 `Unknown column 'system_status' in 'field list'` 让智能体列表、对话、自动委派全线 500——这和之前 `ResourcePermission.agent_id` 那次事故同一级别。改为：

- `app/services/ai/agent_system_columns.py` 负责探测（进程内缓存，失败 30s / 列缺失 60s 后重试）与原生 SQL 读写；
- 未迁移时 `assert_migrated()` 返回 400「请先执行数据库迁移 V185（MySQL）/ V85（PostgreSQL）」，而不是 500；
- 列表接口用一条 SQL 批量把状态 `setattr` 到 ORM 对象上供 `AIAgentResponse` 序列化，schema 里给默认值 `NONE` 兜底。

代价是这两列不能用 ORM 过滤/排序，只能按主键点查或原生 SQL——本期没有按状态列表查询的需求（审核队列查的是申请单表），可以接受。

## 10. 测试

后端：

- 状态机：重复申请、驳回后重提、撤回、待审中发布、下架后再发布。
- 权限：非所有者申请 403；无审核权限审核 403；管理员直接发布成功且待审申请自动置 `APPROVED`；管理员发布新基线成功并记事件。
- 冻结态：待审期间 `PUT /agents/{id}`、建版本、改版本、发布版本、删除均 409；撤回后全部恢复；待审期间复制成功且副本 `system_status = NONE`。
- 状态语义：`publish`/`approve` 只改 `is_system`，不改变任何版本 status；版本仍由原有「发布版本」接口管理。
- 前置校验：无版本 / 只有 `DRAFT` 版本时，`submit`、`publish`、`approve` 均 400 且不改 `is_system`；有 `PUBLISHED` 版本时正常通过。
- 引擎校验：`engine_type != 'LOCAL'` 时 `submit`/`publish` 返回 400「该引擎类型不支持发布为系统级」。
- 角标接口：待审数量随申请/审核变化。
- 审核通过前版本被删：approve 再次校验，返回 400 而非发出一个不可用的系统智能体。
- 约束：并发提交两条申请只成功一条。
- 主助手下架 400；系统级删除 409。
- 下架：`unpublish-preview` 人数（含角色成员）正确；下架后授权记录仍在、`list_allowed_agents` 不再包含；`notify=true` 时站内信落库给并集内每个用户、`notify=false` 时零条但事件仍记人数；重新发布后授权恢复。
- 重新上架通知：上次 `notify=false` 时不发「已重新上架」；上次 `notify=true` 时默认发。
- 发布时自动授权所有者（已存在不重复插入）。
- 迁移契约：两份 DDL 均含两张表与两个字段。
- `create_agent` / `update_agent` 传 `is_system` 被忽略。
- 直接发布他人智能体：发布成功 + 所有者收到站内信 + 既有 PENDING 申请被置 `APPROVED`。
- 管理员豁免：待审期间管理员可编辑/建版本/发布，非管理员被 409。
- 重新上架：下架后再发布，原授权用户收到「已重新上架」通知且权限生效。
- 已系统级的智能体发布新版本时自动写 `PUBLISH` 事件（复用现有发布接口，不新增入口）。
- 启用/禁用：对系统级智能体调用现有启用/禁用接口时，`is_system` 不变、写 `TOGGLE_ENABLED` 事件、不发任何通知；对非系统级智能体不记事件（保持现状）。
- 孤儿下架：`created_by` 用户不存在时，下架后 `created_by` 变为操作的管理员。

前端契约：

- 表单不含「设为系统智能体」；
- 卡片操作按权限/状态显示正确，待审态只留撤回/复制/预览；
- 审核抽屉为只读快照 + 通过/驳回两按钮；
- 下架弹窗展示受影响人数；
- 历史抽屉时间线同时含申请与事件两类条目。

## 11. 风险与未决

- **`is_system` 与 `system_status` 双字段**：约定 `is_system` 为唯一事实，`system_status` 只是待审标记，评审时守住。
- **审核时长与开发停滞**：冻结编辑意味着审核慢会挡住作者。缓解：待审列表展示等待时长，超 24h 高亮；待审态明确给「复制一份继续开发」的引导。
- **审核只读的副作用**：审核人发现小问题只能驳回，可能来回一轮。可接受——申请人在提交前应自查，驳回理由要具体。
- **版本上限**：管理员发布新基线会新增版本，若存在版本数上限需确认是否占用。
- **事件表体积**：已约定下架事件不存快照；发布事件保留快照，暂不设保留期，后续按实际增长再定归档策略。
- **回滚可行，无需新设计**：现有 `publish_version` 不限制 `ARCHIVED → PUBLISHED`（它先 archive 当前 PUBLISHED，再把目标置 PUBLISHED），因此「回滚到上一基线」= 重新发布旧版本 + 记一条 `PUBLISH` 事件，UI 上在发布历史里给「以此版本重新发布」入口即可。
- **授权用户反查要用原生 SQL**：`ResourcePermission.agent_id` 刻意未在 ORM 声明（走列探测 `_supports_agent_scope`），下架预览与通知的「受影响用户并集」必须沿用 `PermissionService` 的原生 SQL 口径，不能直接走 ORM 查询，否则未迁移环境会 `Unknown column`。
- **权限反查目前没有现成方法**：`PermissionService` 只提供「查某人有哪些权限」，没有「查谁拥有某权限」。通知持 `element:agent:system_publish` 的人需要新写一条（用户直配 ∪ 角色成员）查询，注意角色展开后的去重。
- **审核详情页的内容对比**：申请快照 vs 当前内容是两段 JSON，前端需要并排渲染 + 字段级高亮，这块交互工作量约 2 天，若赶进度可先做「左右两栏 JSON 原文对照」。

## 12. 实现时按以下默认处理（不再单独确认）

- 「发布为系统级」卡片菜单点击后弹窗：只有可选 `reason`，无版本选择；无 `PUBLISHED` 版本时按钮置灰（不进入弹窗）。
- 下架预览的「已分配 N 人」**不含所有者**（所有者单独提示「下架后你可继续编辑」）；若所有者同时也在授权名单里则去重后再算。
- 发布历史分页默认 20 条，时间线按 `created_at DESC` 合并两表后在内存排序（单智能体记录量很小）。
