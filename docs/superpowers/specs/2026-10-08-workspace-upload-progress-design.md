# 工作空间上传进度与状态反馈设计

- 日期：2026-10-08
- 状态：待评审
- 范围：工作空间浏览器（`WorkspaceBrowserDrawer`）的「上传到此目录」链路，含前端上传编排与后端上传接口
- 不在范围内：nginx / ingress 网关缓冲对齐（用户明确排除）、`.py/.sh` 等脚本类扩展名的禁传策略（保持现状）、分片上传与断点续传（当前文件规模不需要）

## 1. 问题陈述

用户在执行「上传到此目录」后，界面在文件传输与后端落盘的整个过程中没有任何可见反馈，仅在每个文件成功或失败时弹出一句 toast。文件较大时，这段静默期会被用户感知为「卡死」。

现状代码事实：

- 前端 `uploadToWorkspaceDir()`（`frontend/src/utils/workspaceFilePreview.ts:380`）是普通 `axios.post`，未配置 `onUploadProgress`。
- 抽屉的 `handleUploadFiles()`（`frontend/src/components/embed/WorkspaceBrowserDrawer.vue:1256`）以 `for ... await` **串行**上传，循环期间界面无 loading 态、无取消入口。
- 后端 `upload_to_workspace()`（`app/api/v1/endpoints/fs.py:932`）以 `contents = await file.read(MAX_UPLOAD_BYTES + 1)` **一次性把整个文件读入内存**，再整块 `handle.write(contents)`，无分块、无中途截断。
- 上传上限为模块级常量 `MAX_UPLOAD_BYTES = 20 * 1024 * 1024`，不可配置。

## 2. 关键实测结论（决定方案形态）

在「浏览器直连 uvicorn」拓扑下（dev 经 Vite 代理、生产由 `app/main.py:484` 的 `StaticFiles` 托管，链路中无网关），用 axios 1.13.2 实测 `onUploadProgress` 行为：

| 文件大小 | 事件触发次数 | 耗时 | 服务端接收耗时 |
| --- | --- | --- | --- |
| 5 MB | 1 次（0% → 100% 直接跳完） | 19 ms | 9 ms |
| 60 MB | 2 次（43.6 MB → 100%） | 114 ms | 78 ms |

结论：

1. **字节流传输耗时是毫秒级**，浏览器把数据写入内核 socket 缓冲区即视作完成，真正让用户等待的是后端落盘与目录刷新。
2. **`onUploadProgress` 事件粒度不可依赖**：快链路下只触发 1 次，甚至 `loaded === total` 时才有唯一一次回调。因此不能以「进度事件驱动」作为进度条的唯一驱动源。
3. 用户等待的实际构成是「传输 + 后端落盘 + 目录刷新」，其中后两项**没有任何进度信号**，必须显式建模为状态，否则进度条会在 100% 处长时间滞留，观感比没有进度条更差。

设计目标因此从「做一个上传进度条」修正为：**让上传的每个阶段都可见、可取消、可重试。**

### 2.1 链路分组

由于本平台是 SaaS 多租户、链路不确定，组件必须对两类链路都退化为可用：

- **快链路**（内网/局域网）：传输瞬间完成，用户看到的是「服务端写入中 → 完成」。
- **慢链路**（公网/跨地域）：传输真实耗时数秒至数分钟，进度条与速率有真实价值。

## 3. 设计

### 3.1 分层与职责

| 单元 | 位置 | 职责 | 依赖 |
| --- | --- | --- | --- |
| HTTP 进度传输 | `frontend/src/utils/workspaceFilePreview.ts` | 带 `onUploadProgress`、`AbortSignal` 的单文件上传，只负责搬运字节并回调进度 | axios |
| 上传队列编排 | `frontend/src/composables/useWorkspaceUploadQueue.ts`（新增） | 任务状态机、并发调度、速度估算、取消/重试、批量汇总；**不接触 DOM，不弹 toast** | 上述传输函数 |
| 上传面板 UI | `WorkspaceBrowserDrawer.vue` | 渲染任务列表与阶段状态、提供取消/重试/清空入口 | 队列 composable |
| 上传接口 | `app/api/v1/endpoints/fs.py` | 分块流式落盘、动态上限、失败清理 | — |
| 上传上限配置 | `app/core/config.py` + `env.example` + `docker/env.example` | `WORKSPACE_UPLOAD_MAX_MB`，默认 200 | — |

把队列编排放进独立 composable 而非继续堆在抽屉组件里，原因是抽屉文件已超过 2400 行，且队列逻辑（并发、计时器、状态机）是可以脱离 Vue 组件单独推理与测试的部分。

### 3.2 任务状态机

```
queued ──► transferring ──► committing ──► done
   │            │                │
   │            ├──► canceled ◄──┘
   └────────────┴──► failed ──► (retry) ──► queued
```

- `queued`：已入队，等待并发槽位。
- `transferring`：HTTP 请求体在发送（快链路下极短）。
- `committing`：请求体已发完，等待服务端落盘与响应。**该阶段是快链路下的主要等待期，必须显示「服务端写入中…」而不是停在 100%。**
- `done` / `failed` / `canceled`：终态；`failed` 提供重试。

### 3.3 进度与速率

- 进度值 `percent` 一律由 `loaded / total` 计算，`total` 取事件提供的值，缺失时回退为 `file.size`。
- **驱动源为时间 tick 而非事件**：`transferring` 期间以 400ms 间隔刷新（进度事件仅作为 `loaded` 的更新来源），保证即使事件只触发 1 次，UI 也有稳定的刷新节奏与粘贴感。
- 速率取**最近 2 秒滑动窗口**的平均值（而非瞬时值），避免事件稀疏导致速率大幅抖动；窗口内样本不足时显示为空。
- 剩余时间仅在速率稳定后显示，且对小于 1 秒的剩余量不显示，避免闪烁。
- 顶部汇总：并行任务聚合为 `已完成/总数` 与 `总已传/总大小`，聚合速率按总量加权。

### 3.4 并发模型

并发上限 3（常量 `MAX_CONCURRENT_UPLOADS`）。理由：

- 串行在批量场景下总耗时线性叠加，且用户要等很久才看到第二个文件开始。
- 后端 `open_upload_storage_file()`（`app/utils/fs_access.py:35`）已用 `open(path, "xb")` + 重试分配唯一名，天然并发安全，服务端无需改动。
- 并发 3 在带宽占用与总耗时之间平衡；每个任务的进度条独立，互不干扰。

### 3.5 文件名反馈（现状的隐性困惑）

后端存储名会追加 4 位随机后缀（`build_upload_storage_name`，`app/utils/fs_access.py:23`），即上传 `报告.pdf` 实际落盘为 `报告_a3f2.pdf`。这本身是防覆盖的正确设计，但当前 UI 完全不提示，用户会认为自己传错了文件。

处理方式：面板中每个任务显示 `原名 → 落盘名`，并在两者不同时标注「已加后缀避免重名」。这是纯展示改动，不改变后端命名策略。

### 3.6 取消语义

前端通过 `AbortController` 中断传输。由于链路中无网关，中断会直接传导到 uvicorn，服务端读取循环会抛错。处理方式：

- 后端在流式写入的异常分支中**删除写了一半的目标文件**并清理临时文件，保证「取消后不残留半截文件」。
- 若文件已完整写完、仅响应未送达，前端标记为 `canceled` 但该文件实际已落盘。此时不自动删除（删除存在误删已落盘内容的风险），而是保留记录并标注「可能已保存」，由用户决定。

### 3.7 后端接口改造

`upload_to_workspace()` 改为：

1. 逐块读取（块大小 1 MiB）写入目标文件，累计计数。
2. 累计超过动态上限时，**立即中止**、删除半截文件、返回 `413`（原实现为一次性读满后返回 400，既占内存又无中途截断）。`413` 语义比 `400` 准确，但会让前端错误处理分支变化，前端需同步识别。
3. 落盘后 `flush`，再 `os.stat`，返回原名 `name`（当前实现返回的是落盘名，语义有误需修正为原始 `file.filename`）与落盘名 `stored_name`、`size`、`mtime`。
4. 权限校验（`_resolve_writable_entry_path`）与扩展名禁传校验**保持在前**，顺序不变，避免出现「先写盘再拒绝」。

响应模型 `FileUploadResponse`（`app/api/v1/endpoints/fs.py:756`）新增**可选**字段 `stored_name: Optional[str] = None`，属非破坏性扩展；`name` 改为返回原始文件名是接口语义修正，前端同步读取该字段即可。

配置项：

- `app/core/config.py` 新增 `WORKSPACE_UPLOAD_MAX_MB: int = 200`，接口按需读取，兼容配置未加载的场景（读取失败回退 200MB 默认值，与配置默认值保持一致）。
- `env.example` 与 `docker/env.example` 同步补充该变量及注释。

前端提交前用 `file.size` 做**预检**并直接标红，避免用户传了 200MB 才被服务器拒绝。

### 3.8 错误处理

| 场景 | 表现 |
| --- | --- |
| 超出上限 | 上传前预检拦截，任务标红「超出 xxx MB 上限」；服务端 413 作为兜底同样映射为该文案 |
| 扩展名禁止 | 服务端 403，面板显示服务端 `detail` |
| 网络中断 | 任务 `failed`，提供「重试」，重试沿用同一队列槽位 |
| 权限不足 | 服务端 403/404，显示 `detail` |
| 部分成功 | 顶部汇总区分「成功 n / 失败 m」，失败项保留可单独重试 |

### 3.9 目录刷新策略

当前实现每个文件上传成功都调用一次 `fetchDirectory`。改为：队列中仍有活动任务时不刷新，全部进入终态后**统一刷新一次**（保留搜索状态）。避免批量上传时十几次目录请求互相打断滚动位置。

## 4. 测试策略

- **后端单测**（`tests/api/v1/`，现有 `test_fs_browser.py` 尚无上传用例，需新增）：
  - 正常上传落盘，返回 `name` / `stored_name` / `size`。
  - 超限时返回 413，且**目标目录中不残留文件**。
  - 禁传扩展名返回 403 且不产生文件。
  - 权限不足用户上传到非授权目录被拒。
  - 上限配置项生效（可被测试覆盖）。
- **前端契约测试**（`tests/frontend/`，纯源码断言，沿用 `pytest --confcutdir=tests/frontend` 与现有 `.mjs` 运行时脚本风格）：
  - 队列状态机的并发上限、取消、重试、汇总计算。
  - 上传请求确实携带 `onUploadProgress` 与 `signal`。
  - 面板在 `committing` 阶段展示「服务端写入中」而非 100% 卡住。
- **构建校验**：`vue-tsc --noEmit`。

## 5. 验收标准

1. 上传 1 个 50MB 文件时，用户可看到：入队 → 传输（含已传字节与速率）→ 服务端写入中 → 完成并刷新列表，全过程中不存在无反馈的静默期。
2. 上传 10 个小文件时，并发 3 执行，面板显示 `已完成/总数`，可取消任一任务。
3. 上传超过上限的文件时，在发起请求前即被拦截并说明原因。
4. 取消一个正在落盘的任务后，目标目录不残留半截文件。
5. 服务端内存占用不随文件大小线性增长（分块落盘）。

## 6. 风险与权衡

- **进度条在快链路下观感有限**：这是链路特性而非实现缺陷，方案以阶段状态兜底。
- **取消的边界语义**（3.6）无法做到严格一致，选择「不误删」优先。
- **413 状态码变更**会让既有前端错误分支失效，需同步修改，已纳入改动清单。
- **无网关**是当前拓扑结论；若后续引入 nginx/ingress，需追加 `proxy_request_buffering off` 与 body 上限对齐，否则进度条会在 100% 处滞留。此项已由用户明确排除在本次范围外。
