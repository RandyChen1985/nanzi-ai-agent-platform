# 实体关系智能发现策略设计

## 背景

当前关系推荐先按表名、字段名、主键和业务术语生成候选表对，再读取数据库外键元数据，最后只将候选表对交给 AI。对于没有配置主外键、且字段命名不规范的数据源，候选预筛可能在 AI 调用前就归零。业务数据行抽样已经关闭，因此不能以查询业务行的方式补召回。

## 目标

- 提供“严格模式”和“智能推断”两种可见策略。
- 保留严格模式的低误报行为，并兼容未传策略的旧 API 调用。
- 智能推断模式在没有主外键时，使用表名、字段名、中文术语、字段描述、类型、索引/唯一性等结构化元数据扩展候选。
- 两种模式均不读取业务表数据行，不改变最终人工确认后保存的流程。
- 将本次扫描的关键计数和策略返回给前端，减少“未发现合适关系”的黑盒感。

## 非目标

- 不恢复业务数据行抽样。
- 不自动保存 AI 推断关系。
- 不修改数据库主键、外键或索引。
- 不让 AI 自由枚举全部表对并绕过后端候选约束。

## 方案

### 策略

使用 `strict` 和 `smart` 两个内部枚举值：

- `strict`：沿用现有强候选规则；候选必须有明确外键、实体键命名、同名非通用键字段或同业务术语键字段等证据。
- `smart`：保留严格候选，并增加结构化语义候选。新增候选必须满足字段类型兼容，并至少具备表名/字段名/中文术语/描述/索引唯一性中的可解释线索；不使用业务行值。智能候选使用较低分数进入 AI 复核，最终仍执行现有确定性校验。

智能候选设总量上限，按分数和稳定的表顺序截取，避免 38 张表产生的 703 个组合全部送入模型。超出上限的组合只记录在诊断计数中，不对用户伪装为已分析。

### API

`RelationshipRecommendRequest` 增加可选字段 `strategy`，允许值为 `strict`、`smart`，默认 `strict`。同步支持普通推荐和 SSE 推荐接口。前端默认发送 `smart`，旧调用方不传参数时保持严格模式。

返回 `_debug.strategy`、`_debug.smart_candidate_pair_count`、`_debug.candidate_pair_limit` 和现有候选/分组计数。SSE 完成事件同步携带策略和诊断计数。

### 前端

在关系发现弹窗的表选择区域之后、开始分析之前放置分段选择器：

```text
发现策略    [智能推断（推荐）] [严格模式]
智能推断：不查询业务数据，结合字段语义和结构信息扩大候选，结果需人工确认。
```

智能推断默认选中；切换策略只影响下一次分析。运行中禁用选择器。结果卡片继续使用“外键确认”和“AI 推断”来源标识，不新增会误导为数据库事实的来源名称。空结果时优先展示后端诊断数据，再保留通用提示。

### 安全与错误处理

- 智能推断仍然只接收导出的 Schema 和结构化元数据，禁止生成或执行业务表查询。
- 任何 AI 输出都必须通过表、字段、候选表对、连接条件和置信度校验。
- 无候选组时继续跳过模型初始化，但返回明确的策略和候选诊断。
- 未知策略由 Pydantic 请求校验拒绝；旧请求不传策略时使用严格模式。

## 验证

- 服务测试覆盖严格模式兼容性、智能模式在无主外键命名场景下产生候选、候选上限和 AI 输出校验。
- API 测试覆盖普通接口与 SSE worker 将策略透传给生成器。
- 前端契约测试覆盖策略选择器、默认智能推断、请求参数和诊断展示文案。
- 运行关系推荐定向 pytest、前端契约 pytest、`vue-tsc --noEmit`、定向 `py_compile` 和 `git diff --check`。
- 不在本次变更中启动服务、连接真实数据源或执行部署；真实 UI 和真实数据库目录权限仍需用户在控制台验证。
