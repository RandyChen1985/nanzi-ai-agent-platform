NanZi AI 引擎 · 三类专家场景 · 配置门禁与运行护栏

仓库：RandyChen1985/nanzi-ai-agent-platform

上篇把平台装起来了；这篇解决更实操的问题：在控制台里新建一个能跑、能发布、能被路由和委派调用的智能体，到底要点什么、填什么、为什么会被拦。

很多教程停在「选类型 → 填名字 → 保存」。NanZi 要多几步：选对专家类型 → 配好模型和工具 → 点发布，用户才能真正用起来。下面分章讲；每章开头先用大白话交代「这节在解决什么问题」，再展开技术细节。读完后你应该能：

· 按业务场景选对通用助手 / 问数专家 / 知识库专家

· 走完版本配置向导，知道哪些在「智能体档案」里改、哪些在「版本」里改

· 发布失败或被拦时，对着提示改配置，不用猜

· 用「十分钟验收」确认三类智能体真的在跑，而不是页面能开、对话空转

先给结论：类型选错比模型选错更伤——想让 AI 查数，就得建「问数专家」，不是给通用助手多挂几个工具。知识库要先绑文档库，不然检索是空的。改完配置记得点发布，否则用户聊到的还是旧版。

01｜NanZi AI 引擎（LOCAL）与三类专家

大白话：可以把 NanZi 想成一家公司：LOCAL 引擎是自家办公大楼（NanZi AI 引擎），楼里再请三种岗位——前台万能助手、数据分析师、档案管理员。岗位不同，能干的活和「上岗前检查清单」也不一样。选错岗位，后面挂再多工具也白搭。下面先讲这三种岗位分别干什么、上岗前要查什么、上班后平台怎么管。

控制台「引擎」下拉里的 LOCAL，就是 NanZi 自研的本地 AI 执行引擎——底层统一跑在 AgentScope 2.x ReAct（Agent + Toolkit + ReActConfig），经平台适配层 app/services/ai/runtime/agentscope/ 接入调度。文档和后文统称 NanZi AI 引擎。

在这个引擎下，你再选主类型（agent_type）——平台据此锁定主能力、选 Executor/Runner，并套上对应的配置门禁与运行后门控。三者共用同一套 AgentScope 工具权限模型，但业务护栏强度不同。

NanZi AI 引擎（LOCAL）= AgentScope ReAct

· 版本化配置：模型 / 工具 / 提示词 / Skills / 欢迎语写在 AIAgentVersion，必须发布后才参与运行时

· 运行时真相：get_active_agent_config 读 Agent 元数据 + 最新 PUBLISHED 版本

· 统一工具门控：三类专家都走 AgentScope permission_scope（read / write / ask / dangerous）→ 用户确认 / 外部执行挂起与恢复

· 与外部引擎区分：RAGFlow / OpenClaw 不走 NanZi AI 引擎，不经 AgentScope ReAct，也不吃本地版本向导（后文第 04 节 engine_config 再提）

主类型 锁定能力 执行路径
GENERAL general_chat AssistantExecutor → AssistantAgentRunner
CHATBI data_query DataQueryExecutor → DataAgentRunner + ChatBI 域
KNOWLEDGE_BASE knowledge_base KnowledgeExecutor → KnowledgeAgentRunner

■ GENERAL 石墨灰 · ■ CHATBI 赭石 · ■ KNOWLEDGE_BASE 板岩蓝（全文三类专家沿用此配色）

normalize_agent_capabilities 保证锁定主能力始终在 capabilities 首位，扩展标签可追加、不可替换。

① GENERAL · 通用助手

适用场景：主工作台对话、办公自动化、多 Agent 编排中枢、挂 MCP / 通知 / HTTP / 任务调度 / Skills。不直连业务库，不得编造内部业务数据。

上岗前检查（发布 / 委派时）

· published_version — 须有已发布版本

· primary_capability — 须含 general_chat

上班后怎么管（对话运行时）

· 路由/意图：会话级通用分类（data query 降级、knowledge、skill、general 等）

· 工具权限：write/ask 默认要用户确认；dangerous 拒绝；支持 external_execution 挂起恢复

· 工具预检（可选）：agent_tool_preflight_mode off / soft / hard，按问题与已挂工具相关度促发

· 主助手数据 Guard：主通用助手在强内部查数信号下，拦截「假装已查库」等话术（柔性追加提示，不硬阻断流）

· Grounding（按入口默认值）：原始 API / AgentDebug 默认关，EmbedChat 默认开；最终由 execution_options.grounding_enabled 布尔值决定

② CHATBI · 问数专家

适用场景：自然语言查数、报表下钻、数据门户（/dataset_portal）、简报订阅。必须配数据源 + 元数据/数据集授权。

上岗前检查

· 通用两项：published_version + primary_capability（data_query）

· data_query_tool — 版本 tools 须启用 get_dataset_schema 或 execute_sql_query（任一）

上班后怎么管（护栏最强，第 04 篇展开）

· 分诊：外层路由进 ChatBI 后，DataQueryTurnClassifier 为最终判定（新查数 / 追问 / 元数据 / 复用结果 / 非查数等）

· SQL 安全：只读 SQL；必须先 schema 后 SQL；静态风险 / 重复 SQL / 计划门禁；SqlQueryBinding 防「Schema 一套、执行另一套」

· 数据真实性：空结果诊断、修复轮次、结果栈（最大深度 10）；交付须绑定可追溯 result_id

· 工具权限：同 AgentScope 统一模型；另叠加 RBAC 数据源 / 元数据 / 数据集授权

③ KNOWLEDGE_BASE · 知识库专家

适用场景：企业制度 / 产品手册 / 内部文档问答，回答应带 chunk 引用。菜单权 ≠ 全库可读，须单独授 dataset 资源。

上岗前检查

· 通用两项：published_version + primary_capability（knowledge_base）

· knowledge_base_binding — engine_config.dataset_ids 非空

· knowledge_base_tool — 版本 tools 须启用 search_knowledge_base

上班后怎么管

· 检索前置：ReAct 前自动调用 search_knowledge_base；无 dataset / 服务不可用则终止，不让模型脑补

· 范围约束：检索范围 = 显式参数 ∩ Agent 绑定 dataset ∩ 用户授权 dataset

· 引用约束：空召回或缺有效引用时长事实回答 → 反思重写；耗尽后保留回答并追加风险提示

· 工具权限：同 AgentScope 统一模型；可叠加通知 / MCP 等业务工具

三类护栏强度对比（一句话）

GENERAL偏柔性（工具确认 + 可选预检）→ KNOWLEDGE_BASE中等（检索范围 + 引用）→ CHATBI最强（分诊 + SQL 全链路 + 结果栈）。选错类型 = 选错护栏，不是换几个工具能补救的。

旁路：外部引擎（非 NanZi AI 引擎）
若已有 RAGFlow App → 选 RAGFLOW（RAGExecutor）；已有 OpenClaw 集群 → 选 OPENCLAW。二者主类型强制 GENERAL，不走版本发布，门控由外部系统自管。企业问数 / 知识库若要用 NanZi 护栏，请选 LOCAL + 对应主类型。

02｜控制台路径：从新建到第一次对话

大白话：这一节就是「跟着点一遍」。打开智能体管理 → 新建，相当于填入职表：先登记是谁（名字、类型），再配技能包（模型、工具、提示词），最后挂牌上岗（发布）。只点保存不算上岗——没发布，用户对话时用的还是旧配置，或者根本调不起来。

入口：智能体管理 → 新建。平台有两种心智模型——快速编辑（已有 Agent 点版本抽屉）和引导式 onboarding（首次创建 LOCAL 专家）。下面按 LOCAL 新建一条完整链路讲。

Phase A · 创建 Agent 骨架

1. 选主类型 + 引擎（此步决定后续向导步数）

2. 填物理标识符 name（全局唯一，路由 / API / 委派用）和显示名称 display_name

3. 填引擎必填项：RAGFlow 的 app_id；OpenClaw 的 base_url + model

4. 服务端 create_agent_onboarding：按类型拉系统模板（main / chat-bi / knowledge-base 的已发布配置），生成 v1 DRAFT；onboarding_step=VERSION

Phase B · 版本配置向导（VersionConfigStep）

LOCAL 新建走 六步（含欢迎语）；编辑已有 LOCAL 从「模型策略」起（不再改 agent 步）；新建 RAGFLOW/OPENCLAW 通常只走 agent 一步就结束——外部引擎不吃本地版本工具/提示词向导。

① agent 智能体信息 — name / 引擎必填项

② model 模型策略 — 编排模型 + temperature；可选合成模型

③ tools 工具能力 — 静态 / MCP / Skills 三 Tab；KB 类型此步强制勾选 search_knowledge_base 且 agent 已绑 dataset

④ prompt 系统提示词 — 必填；可从模板复制再改

⑤ welcome 欢迎语 — 仅 LOCAL；关 enabled 可跳过；开 manual 须填齐 3 张卡片

⑥ review 确认保存 — 草稿入库；不等于发布

Phase C · 资源与发布

· 保存版本后 onboarding_step 进入 RESOURCE（知识库绑 dataset_ids、ChatBI 绑数据源/元数据等）

· 点发布 → publishVersion → 服务端跑就绪门禁 → 旧 PUBLISHED 变 ARCHIVED → 目标版本 PUBLISHED → onboarding COMPLETE

· 发布后 Router 缓存失效；委派列表只展示就绪且已发布的子 Agent

向导门禁（前端也会拦）

canReachVersionConfigStep：前面的步未完成不能跳步。常见提示：「请先完善模型策略」「请先完善工具能力：为知识库检索工具绑定至少一个知识库」。这和后端 409 AGENT_NOT_READY 是同一套契约的前后端分工。

03｜版本与发布状态机

大白话：版本就像 Word 文档的「草稿」和「定稿」。你在抽屉里改模型、改提示词，改完保存只是存了草稿；用户聊天用的是已发布那一版。所以最常见的一句抱怨是「我明明改了提示词，怎么没变？」——十有八九是没点发布，或者改的是草稿。已发布的版本不能直接改，要克隆一份新草稿 → 改完 → 再发布。

LOCAL 智能体的「线上行为」= Agent 元数据 + 唯一活跃 PUBLISHED 版本。理解状态机，就不会疑惑「我明明改了提示词为什么没变」。

版本 status

· DRAFT — 可编辑；不参与运行时

· PUBLISHED — 运行时唯一真相；不可原地改，需克隆新版本再发布

· ARCHIVED — 历史发布快照；可删；不可再激活

publishVersion 事务（简化）

evaluate_agent_readiness(missing?) →
UPDATE all PUBLISHED → ARCHIVED →
UPDATE target → PUBLISHED →
agent.onboarding_step = COMPLETE →
router_service.invalidate_cache()

反例：只保存 DRAFT 就去对话 → get_active_agent_config 返回空 / 404，路由可能 fallback 别的 Agent。只改工具不发布 → 线上仍跑旧工具集。PUBLISHED 版本想改字段 → 必须「克隆为新版本 → 编辑 DRAFT → 再发布」。

04｜engine_config：Agent 层运行时参数

大白话：智能体有两层配置容易混：版本管「这人会不会说话、会哪些技能」（模型、工具、提示词）；engine_config 管「这人连哪条线、查哪个库」（比如绑哪些知识库、RAGFlow 的 App ID）。改 engine_config 一般不用重新发布版本，但知识库专家如果这里没绑库，发布时照样会被拦。

engine_config 挂在 Agent 记录上，不随版本 DRAFT 走——改它不需要重新发布版本（但 KB 的 dataset 绑定会影响就绪门禁）。按引擎分列如下。

LOCAL

· dataset_ids — 知识增强（GENERAL 也可挂库做 RAG 增强；KB 类型发布门禁必填）

· ragflow_similarity_threshold / ragflow_vector_weight — 检索参数，运行时可能归一进 rag_params

· default_markdown_theme / hide_message_border — 对话 UI 偏好

· ChatBI 问数工具在版本 tools 里勾；get_dataset_schema 还可绑 metadata_dataset_ids 收窄 Schema 范围

RAGFLOW（必填 app_id）

· 必填 app_id — RAGFlow 侧 Agent/App 标识

· 可选 dataset_ids、相似度 / 向量权重

· 运行时 model_name 固定展示为 RAGFlow-Remote；不走 AgentScope Toolkit

OPENCLAW（必填 base_url + model）

· 必填 base_url、model（机器人 ID）

· 可选 api_key、safety_check_enabled（默认开）、input/output prompt 与 strategy（默认 append）、stream

· 安全审计在 OpenClaw 适配层，不走本地 SQL / 工具权限矩阵（见门控契约）

05｜就绪门禁：发布前的「上岗检查」

大白话：点「发布」时，平台会跑一张上岗检查表：有没有定稿版本？问数专家有没有查数工具？知识库专家有没有绑库？缺一项就发布失败，页面会告诉你缺什么（missing 码）。主助手要委派子智能体时，也只看「检查通过」的那些——没配齐的子 Agent 根本不会出现在列表里。

技术名是 evaluate_agent_readiness。HTTP 409 会返回 AGENT_NOT_READY 和 missing 列表——对着下表改就行。

missing 码 含义 怎么修
published_version 没有已发布版本 保存 DRAFT 后点发布（RAGFlow/OpenClaw 不走此条）
primary_capability 缺锁定主能力 检查 agent_type 与 capabilities 是否被 normalize 破坏
data_query_tool CHATBI 未启用问数工具 版本 tools 勾选 get_dataset_schema 或 execute_sql_query（任一即可）
knowledge_base_binding KB 的 dataset_ids 为空 Agent engine_config 或 RESOURCE 步绑至少一个知识库
knowledge_base_tool 未启用检索工具 版本 tools 勾选 search_knowledge_base

委派侧：主 Agent 的 sub_agent_call 工具枚举子 Agent 时，只列出用户有权访问 + evaluate 通过的目标。子 Agent 缺发布版或缺问数工具，列表里直接没有——不是运行时失败，是配置期就被滤掉。

06｜三类最小可用：跟着做就能验收

大白话：前面讲原理，这节是菜谱。按 A/B/C 三套步骤各建一个智能体，再用最后清单打勾——十分钟内能确认「真的在跑」，而不是页面能开、一问就懵。建议第一次部署时三种各做一个，后面再按业务裁剪。

A. GENERAL 通用助手（LOCAL）

目标：主工作台对话 + 可挂通知/MCP/HTTP/任务调度

1. 类型 GENERAL · 引擎 LOCAL · 从 main 模板生成 DRAFT

2. 选编排模型 · 勾需要的静态/MCP 工具 · 写 system_prompt

3. 发布 · RBAC 给用户授权 agent 资源

验收：对话能触发已挂工具（Trace 见 tool_call）；主助手建议开工具预检（agent_tool_preflight_mode）与 Skill 扫描

B. CHATBI 问数专家（LOCAL）

目标：自然语言查数 + 数据门户 + SQL 护栏

1. 类型 CHATBI · 模板自带 schema/SQL 工具 · 发布前确认 tools 未删

2. 【数据源管理】登记连接 · 【元数据/数据集】授权给目标用户/角色

3. 可选：工具级 metadata_dataset_ids 收窄可见表

验收：问简单计数 → Trace 见分诊类型 + schema/SQL 工具链；门户 /dataset_portal 能出菜单。护栏细节见第 04 篇

C. KNOWLEDGE_BASE 知识库专家（LOCAL）

目标：基于企业文档问答，回答带引用

1. 先在【知识库管理】建 dataset · 同步 RAGFlow 索引

2. 类型 KNOWLEDGE_BASE · tools 勾 search_knowledge_base · engine_config 绑 dataset_ids

3. 发布 · 给用户 dataset 资源授权（菜单权 ≠ 全库可读）

验收：问库内事实 → 回答带 chunk 引用；换无权限用户应检索不到

十分钟总验收清单

☐ 三类各一条：发布成功 · onboarding COMPLETE

☐ GET /api/portal/agents/{id}/active-config 能返回预期 model/tools

☐ 对话 Trace 里 Executor 类型与 agent_type 一致

☐ 主 Agent 委派列表能看到就绪的子 Agent（若做了多 Agent 编排）

07｜常见踩坑与排障顺序

大白话：这一节是过来人经验贴。配置智能体时，十个人里有八个会在同一几个坑里绊一下——类型选错、只保存不发布、有菜单没数据权限、以为 RAGFlow 引擎会吃本地提示词……每条后面给了「该怎么改」。真遇到问题，按文末排障顺序从上往下查，比乱改配置快。

把 ChatBI 建成 GENERAL 再硬挂 SQL 工具

→ 路由可能进 Assistant 而非 DataQueryExecutor；分诊 / 结果栈 / SQL 门禁全吃不到。应改 agent_type=CHATBI。

知识库只勾工具不绑 dataset_ids

→ 前端 tools 步可能拦；就算绕过，发布报 knowledge_base_binding。RESOURCE 步和 engine_config 都要填。

RAGFlow 引擎却期待本地 prompt/tools 生效

→ get_active_agent_config 对 RAGFlow 返回 managed 占位配置；行为由 RAGFlow App 决定。改 NanZi 版本抽屉无效。

有菜单无 dataset 授权

→ 智能体能打开，检索/SQL 空结果或权限错误。排障：用户有效权限 ∩ agent 绑定资源。

推荐排障顺序：active-config 有没有 → 版本是否 PUBLISHED → missing 码 → RBAC 资源授权 → Trace 里 Executor 对不对 → 再查模型/数据源/RAGFlow 连通性。
