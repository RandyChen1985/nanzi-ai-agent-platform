很多刚接触 AI 智能体开发的同学，常常有一种直觉误区：觉得 Agent 的提示词（Prompt）就是一段“写好后固定不变的大长文本”——在前端配置框里敲一段人设，直接作为参数发给大模型接口即可。

然而，一旦你动手构建一个真正的企业级 Agent 平台，你会发现提示词拼装（Prompt Assembly）绝不是简单的字符串加号（prompt += "..."），而是一个极其精密、涉及多达 8 个子系统异构融合的“工业级总装流水线”。

系统既要实时注入平台安全防线、工具调用 Schema、动态技能白名单、长期记忆召回、用户权限范围、意图路由决策与时间锚点，又要面对单次输入高达 20,000 ~ 40,000 Tokens 带来的高额成本与首字等待延迟（TTFT）。

如何设计出一套职责解耦、支持版本热更、具备流水线编排能力，同时又能完美命中大模型 KV Cache（上下文前缀缓存）实现成本断崖式下降的提示词拼装架构？本篇结合 NanZi 开源智能体平台的实际代码演进，为你彻底拆解平台背后的装配工程设计。

📌 核心架构总结：提示词拼装是 Agent 平台执行生命周期的总装中枢。NanZi 通过「执行流水线（Pipeline AssembleStep）」统领全流程，将多源动态输入抽象为面向对象的「强类型切片 PromptSection 与编译执行计划 PromptPlan」；再配合「稳定前缀前置」物理拓扑，完美触发大模型厂商的 KV Cache 缓存池，并辅以会话级 SHA-256 哈希灰度分桶与真实 Token 观测，构建起一套高可靠、高性能的企业级提示词工程基座。

01｜平台级挑战：Agent 的 System Prompt 到底从哪来？

单体聊天机器人只需要一段 System Prompt，而平台级多智能体系统在向模型发起调用前，必须在极短时间内（通常要求在几十毫秒内）聚合来自平台方方面面的八大异构信息源：

📊 提示词八大输入源与稳定性分级清单 （👉 移动端支持左右滑动查看完整内容）

切片类别 具体注入内容 生命周期/来源 稳定性分类
1. 平台全局契约 Markdown/JSON 格式要求、代码块契约、系统底线与防越狱守则 平台代码硬契约 绝对稳定
2. 智能体专规人设 专家人设角色、业务口径定义、任务执行流程规范、Few-shot 范例 Prompt Studio 版本 高稳定（版本级）
3. 工具注册能力表 当前智能体绑定的内置工具列表、MCP 远程服务扩展、入参限制规则 ToolRegistry 注入 中稳定
4. 技能清单与白名单 已授权平台技能摘要、SKILL.md 声明、动态技能发现路径白名单 SkillResolver 检索 动态挂载
5. 用户与权限范围 当前提问人姓名、部门组织、RBAC 授权可访问的数据集与知识库清单 用户会话上下文 用户级动态
6. 长期记忆检索切片 LTM 长期偏好（如输出中文、简洁优先）、跨会话召回片段、会话摘要 向量库/记忆系统 高度动态
7. 本轮多智能体决策 Dispatcher 意图路由快照（如判定查数）、子代理委托上下文提示 调度器单轮决策 每轮都变
8. 物理环境时空锚点 服务器当前时区物理时间（如 2026-09-09 09:30:00）、客户端设备类型 物理宿主机环境 每秒都在变

⚠️ 如果缺乏架构治理，平台会陷入什么混乱？

• 硬编码混乱：每个开发都在 Runner 里随手 prompt += f"{new_data}\n"，代码碎片化，无人知道最终模型到底看到了什么；
• 权限越权与泄露：未做严格上下文边界裁决，把其他租户或未授权的数据表 Schema 随手拼进提示词，产生严重安全漏洞；
• 重复注入与 Token 暴涨：路由快照在流水线拼一次，执行器最后一公里又塞一次，造成 Token 白白浪费；
• 彻底摧毁大模型缓存：随手把动态时间或路由塞在第一行，导致厂商的前缀缓存命中率永远是 0%。

02｜装配中枢：执行流水线（Pipeline）中的 AssembleStep

在 NanZi 的平台设计中，一次智能体执行被拆解为一个严密的责任链流水线（PipelineRunner）。提示词拼装不再是散落在业务代码里的黑盒，而是被安置在承前启后的核心第四阶段：

🧭 NanZi Agent 执行流水线完整生命周期

Step 1. PreflightStep（环境与门禁预检）：校验模型可用性、API 配额与当前用户功能权限（element:*）；

Step 2. RouteStep（调度器意图分发）：根据用户输入解析执行模式（通用问答、数据分析还是知识库精准检索）；

Step 3. ContextStep（多源异构上下文准备）：并发检索向量记忆、捞取技能文件、过滤当前会话授权的数据集清单；

⭐ Step 4. AssembleStep（系统提示词分层装配中枢）：输入多源切片，调用 PromptAssembler 执行计划，完成编译重排与度量打点；

Step 5. ExecutionStep（运行时模型推理）：驱动 AgentScope 运行时，执行模型调用、工具调用 ReAct 推理与流式输出；

Step 6. FinalizeStep（后置归档与沉淀）：沉淀本轮长期记忆、持久化 Trace 审计日志、统计调用成本。

收敛执行边界：消除执行器私货。
许多 Agent 系统之所以难以维护，是因为下层的具体执行器（如通用对话 AssistantRunner、知识问答 KnowledgeRunner、数据问数 ChatBIRunner）各自在最后一公里塞“私货”。NanZi 明确规定：所有 Runner 必须收敛至统一的装配模型，杜绝执行器私自修改首尾顺序，从而确保提示词全链路的确定性与可观测性。

03｜面向对象抽象：从字符串拼接进化到 PromptPlan

在 NanZi 的代码实现中（位于 app/services/ai/prompt_assembler.py），系统彻底抛弃了纯字符串拼接，将装配过程抽象为了两套核心领域模型：

🧩 核心领域对象：PromptSection 与 PromptPlan

• PromptSection（强类型提示词切片）：包含 name（切片唯一标识）、order（排序权重）、text（内容文本）、stability（稳定性：stable 稳定 / dynamic 动态）以及 source（来源模块）。每一个要塞入大模型的信息都被封装为一个切片，严禁匿名注入。

• PromptPlan（编译与执行计划）：将切片划分为 stable_sections 与 dynamic_sections 两个确定性元组。内置自动查重校验、状态过滤、声明式按序渲染，以及字符级精细度量（section_char_counts）。

# app/services/ai/prompt_assembler.py 核心对象定义
@dataclass(frozen=True)
class PromptPlan:
    stable_sections: tuple[PromptSection, ...] = ()
    dynamic_sections: tuple[PromptSection, ...] = ()

    def render_stable(self) -> str:
        # 稳定前缀层：保证全会话字符级 100% 绝对一致
        return self._render_ordered(self._filtered_sorted(self.stable_sections))

    def render_dynamic(self) -> str:
        # 动态后缀层：时间、记忆、路由追加在后，绝不污染前缀
        return self._render_ordered(self._filtered_sorted(self.dynamic_sections))

设计洞察：为什么坚决不用 HTML 伪标签注释当缓存边界？
业内部分框架喜欢在提示词中间插入类似 <!-- NANZI_CACHE_BOUNDARY --> 的 HTML 注释，试图作为分界标识。但 NanZi 在实测中发现：绝大多数主流大模型供应商（OpenAI、DeepSeek 等）根本不会识别这种客户端私造的注释，这种标签反而白白浪费注意力窗口。真正的缓存机制，靠的是从物理层重构 Token 顺序！

04｜拓扑重构与 KV Cache：稳定前缀前置模型

解决了装配架构的面向对象解耦后，我们如何将它与大模型的 KV Cache（键值缓存，中间注意力状态缓存） 结合，实现千万级 Token 降本？

大模型服务端的缓存匹配机制是基于公共前缀树（Prefix Tree）的。它有且仅有一条刚性铁律：

⚡ KV Cache 命中的铁律

必须从请求的第 1 个 Token 开始完全一致，且连续匹配达到阈值（通常为 1024 Tokens 以上），前缀树才能命中！
哪怕开头第 1 行只变了 1 个时间字符（如 09:30:01 变成 09:30:06），整条命中指针立刻断裂，后续紧跟着的 20,000 个静态字符全部无法命中！

🏗️ NanZi PromptPlan 拓扑架构（稳定前缀前置模型）

🟢 1. 稳定前缀层（Stable Prefix Ahead） 命中金矿 · 首字符起严格匹配

★ 核心特性：会话内 100% 字符级稳定一致（单智能体约 12,000 ~ 20,000 Tokens 缓存池）

• 平台固定规则：Markdown / JSON / 代码块契约与输出格式防线

• 安全合规门禁：基础事实门禁、防注入防越狱与系统级底线原则

• 智能体发布规约：Prompt Studio 发布的专家角色、意图目标与 Few-shot 样例

⬇️ 连续物理拼接 · 保持前缀匹配树不被打断 ⬇️
🔵 2. 动态后缀层（Dynamic Suffix Appendices） 末尾追加 · 零损耗前缀缓存

★ 核心特性：每轮按需动态追加，内容变动全部约束在尾部，完全不破坏前面的缓存

• 平台时区动态时间锚点：当前物理时间（Time Anchor）

• 长期记忆检索切片：用户画像、近期习惯与摘要召回（LTM Profiles）

• 用户个性化技能目录：会话绑定的动态工具与权限清单（Skills Directory）

• 本轮执行决策快照：多智能体调度器的路由状态（仅供单轮执行参考）

通过这样的重构，原本动辄几万 Token 的大模型输入，在前缀部分实现了会话内 100% 字节级一致。首轮调用写入缓存后，后续无论用户追问多少轮，前置的 15,000+ Tokens 全部秒级从显存缓存命中返回，不仅开销直降 80%~90%，首字响应时间（TTFT）更由原先的 8~12 秒缩短至 1~2 秒！

05｜生产级灰度与无感升级：三态策略与会话哈希

改动提示词拼装顺序直接影响智能体的推理表现。对于承载业务的生产系统，严禁无灰度一刀切上线。NanZi 设计了严密的两级策略控制：

🎛️ 系统参数：agent_prompt_layout_mode（总控三态）

• legacy（传统兼容模式）：全量走老逻辑，完全保持原有拼装顺序，作为全局秒级熔断底线；
• observe（仅观测基线模式）：保持传统老布局发送，业务逻辑 0 变动、0 风险；但后台打通供应商真实缓存 Token 提取，统计当前未优化环境下的命中基线；
• enabled（启用稳定优化模式）：正式激活稳定前缀新布局，此时系统才会显示并启用下方的灰度滑块。

🎯 系统参数：agent_prompt_cache_rollout_percent（会话哈希分桶）

只有在模式选为 enabled 时，灰度滑块才允许调节。平台基于每个会话的 conversation_id 进行 SHA-256 哈希取模（0~99）：
• 单会话强粘性保障：同一个对话窗口内，只要命中分桶，整场对话从头到尾必定稳定走新布局，绝不会“第 1 轮走新、第 2 轮跳回老逻辑”；
• 平滑放量与即时熔断：支持从 10% 试水，逐步拉大至 50%、100%；如遇突发异常，切回 legacy 即刻全网秒级回退。

06｜真实观测闭环：拒绝伪造，拿真实 Usage 说话

有些平台为了“好看”，会在界面上假装显示命中数据。NanZi 平台坚决秉持「绝不虚标」的工程原则：

在中间件（ModelCallStatsMiddleware）中，精准提取大模型底层返回的原生字段：
• OpenAI / DeepSeek 标准：prompt_tokens_details.cached_tokens；
• Anthropic 标准：cache_read_input_tokens。
如果供应商并未返回缓存数据，系统如实标记为 unavailable，绝不伪造。

在前端界面上，每条消息的大模型调用详情弹框直接提供「调用次数 | 总耗时 | 总输入 | 总输出 | 缓存命中」五列统计大卡片，并在单次调用的输入 Token 右侧以醒目的绿色徽标（如 命中: 12,480 (85%)）直观展示实效收益。

07｜开发者自建 Agent 平台的避坑指南

⚠️ 实战中容易踩入的四大深坑

1. 下层执行器动态偷塞：外层 AssembleStep 虽然把动态内容挪到了尾部，但如果底层的某个执行器又在最终发包前把 route_hint 偷塞回了字符串最开头，整套优化瞬间报废。必须在全链路执行网关建立防线；
2. 上下文去重不严格导致 Token 暴涨：多层注入时若缺少严格的切片唯一性校验，容易导致 System Prompt 里被塞了两份重复的技能摘要，反而使得输入 Token 翻倍；
3. 忽视单会话内的跳变风险：如果按单次 Request 随机分流，会导致同一个用户在上一步走新布局、下一步走老布局，前后轮前缀彻底不连续，不仅没省钱，反而每轮都在重新拉全量缓存；
4. 盲目全量，缺乏基线对比：未上线前一定要先用 observe 模式跑几天，把平均耗时、首字响应与命中率的客观基线数据记录下来，再逐步灰度放量。
