NanZi 与 AgentScope 的功能对照

11 个功能点：两侧各自怎么实现、为什么不同、如何自行核实

AgentScope 2.0.11 · dev-agentscope · 2026-10-29 核对

本文只做一件事：把同一个功能点在框架与平台两侧的实现并排放，指出差异，说明差异来自什么设计前提，并给出可以自己跑的核实命令。

口径：框架侧以 .venv 里安装的 agentscope 为准，26 个模块、123,381 行；平台侧以 app/ 为准，543 个 Python 文件、218,268 行，其中 Agent 运行时 44 个文件、22,181 行。行数含空行与注释，框架侧不含私有工具包与顶层的下划线文件。

下文命令在仓库根目录执行，Python 用 .venv/bin/python。输出与文中数字不符时，以代码为准。

01 / 执行循环：步数用完那一刻

框架按迭代次数硬停；平台在步数将尽时改成「用已有结果作答」。这是本文唯一一处平台借鉴了框架思路的地方。

表 1　一步之差的收尾行为

项 AgentScope 2.0.11 NanZi
迭代上限 ReActConfig.max_iters，默认 50 按 Agent 配置下发，另有平台级上限
超限时 以 EXCEED_MAX_ITERS 结束本轮 注入提示并把 tool_choice 置 none，让模型作答
触发依据 预算中间件按 token 加权成本触发，不按步数 剩余步数 ≤ 预留值：上限 ≤8 留 1 步，>8 留 2 步
产出保护 — 最近一条 assistant 已有正文则不干预
开关 中间件按需挂载 全局开关，异常时整体关闭

为什么不同：框架的软着陆盯的是 token 预算，累计加权成本到线才触发；那管的是「钱」。步数管的是「延迟与失控」，代理循环里没有对应的中间件。平台两条都要防，但目前只做了步数这一侧——配额耗尽仍是硬中断，这是缺口不是设计。

核实 $ python -c "from agentscope.agent import ReActConfig;print(ReActConfig().max_iters)"
输出 50
核实 $ grep -n "_reserve_steps" app/services/ai/runtime/agentscope/middleware.py

02 / 工具、MCP 与多智能体委派

框架提供工具抽象与 MCP 客户端，平台在其上补了工具的生命周期治理：谁能用、用完谁记账、模型叫错名字怎么办。

表 2　工具的供给与治理

项 AgentScope 2.0.11 NanZi
内置工具 tool/_builtin 下 9 个：bash、read、write、edit、glob、grep、ask_user、skill、powershell 注册 6 个：Bash、Read、Write、Edit、Glob、Grep；另有 37 个业务工具模块
工具抽象 Toolkit + FunctionTool / MCPTool 同一套，外加白名单与未注册工具拦截
MCP MCPClient 客户端 + MCPTool 适配 服务级注册（含别名）、按租户授权、市场只做外链
并行调用 框架调度 控制并发与结果合并，避免同文件并发写
多智能体 GoalPipeline / TeamPipeline，进程内编排 专家 Agent 作为工具被调用，带各自知识与权限

为什么不同：模型看到的工具名和平台内部的工具标识不是一套——MCP 注册给模型的是别名，内部记的是「服务名:工具名」。框架不做这层映射的校验，模型照抄内部标识就会踩空，所以平台在调用前拦一层并给出正确叫法。多智能体走委派而不是进程内 pipeline，是因为委派天然带权限与计费边界：子 Agent 用的是它自己的授权。

核实 $ ls .venv/lib/python3.11/site-packages/agentscope/tool/_builtin/
核实 $ ls app/services/ai/tools/ | wc -l
输出 37

03 / 沙箱：八个后端里没有 SSH

框架的沙箱覆盖很全，但没有 SSH 后端；平台的第五种策略是自己写的。

表 3　沙箱后端的差异

项 AgentScope 2.0.11 NanZi
后端 8 个：local、docker、k8s、e2b、daytona、bubblewrap、applecontainer、opensandbox 5 种策略：local、docker、k8s、e2b、ssh
SSH 无 自研 1,455 行，实现 WorkspaceBase，上层工具无感知
容器挂载 一个工作目录挂载点 追加两个只读子挂载：技能包、公共文档
K8s 单个 Pod 六项改造：subPath 同路径、预建目录、身份护栏、无权限降级、资源上限、按用户独立卷
路径一致性 不做约束 沙箱内路径与文件树一致，避免「点了打不开」

为什么不同：框架假设你能控制容器编排；平台面对的是客户现场——不少 GPU 机器只有 SSH，装不了容器运行时。同路径挂载也不是洁癖：左侧文件树点开的路径和 Agent 在沙箱里看到的路径必须是同一个字符串，否则用户点开文件会 404。

核实 $ ls -d .venv/lib/python3.11/site-packages/agentscope/workspace/_*/
核实 $ grep -n "SANDBOX_POLICY_" app/services/ai/runtime/agentscope/workspace.py | head -5

04 / 会话状态：谁负责持久化与互斥

框架定义状态长什么样，不定义它存在哪、谁能写。

表 4　状态的载体、存储与并发

项 AgentScope 2.0.11 NanZi
载体 AgentState（pydantic）+ ReplyContext / ToolContext / TaskContext 同左，另加 PipelineContext 承载流程态
持久化 不负责，交由使用方序列化 Redis 存整份 state，TTL 30 天
并发写 不涉及，假设一次回复在一个进程内跑完 SET NX EX 加锁并续租，保证单写入方
中断恢复 支持 HITL 中断与继续 699 行恢复逻辑 + 确认单落库

为什么不同：多实例部署叠上流式输出，两条流可能同时写同一会话，前端表现为回复重复或内容回退。框架的假设是「一个进程跑完一次回复」，没有跨实例的写者互斥，这件事只能由持有会话的一方来做。

05 / 长期记忆：文件快照与多实例检索

框架的长期记忆是 workspace 里的一组 Markdown 文件；平台是 Redis 加向量索引。两者都做到了「每轮自动注入」，载体完全不同。

表 5　记忆的存储、注入与检索

项 AgentScope 2.0.11 NanZi
存储 workspace 内 Markdown 文件 + MEMORY.md 索引 Redis Hash + 向量索引
注入 MEMORY.md 索引进 system prompt，上限 4000 token 装配阶段预加载，执行阶段注入
检索 模型读 frontmatter 选文件，最多 200 个、单文件 2000 token，异步以提示块注入 向量召回，叠加召回策略规则
隔离 随 workspace，一个目录一份记忆 按租户与用户分区，跨实例共享
重建 重写文件即可 索引可单独重建，不影响会话

为什么不同：文件方案假设「一个工作目录属于一个人」。平台的会话可能落到任意实例，一个租户下几百个用户各有各的记忆，还要能并发写、按用户删除、索引重建。这几条文件方案都不满足，所以只能换载体——但要承认，框架的「Markdown 可读可编辑」在排障时确实直观。

输出 _middleware.py:376: default=4_000
核实 $ wc -l app/services/ai/memory_*.py

07 / 权限：工具护栏与租户边界

这一节的差异最大：两者都叫权限，管的东西不是一个层面。

表 7　两种权限模型

项 AgentScope 2.0.11 NanZi
模型 PermissionRule：工具名 + 内容模式 + 行为 + 来源 RBAC：租户、角色、权限点、资源授权
粒度 Bash 按命令子串，Read/Write 按路径 glob 菜单级与元素级权限点，另加资源级
行为 allow / deny / ask，ask 触发确认 确认单、授权记录、越权审计
引擎模式 5 种：default、explore、accept_edits、bypass、dont_ask 按 Agent 配置下发审批模式
多租户 无此概念 前提

为什么不同：框架的规则是「给一个开发者配一副护栏」——他信任自己的机器，只需要挡住危险的删除和写入；平台是「给互不信任的部门划边界」——同一个模型服务要按租户隔离数据、按角色收窄功能、按次留痕。前者不需要租户，后者没有租户就无法成立。平台只复用了 3 个权限枚举来对齐工具层语义，服务本身 1,805 行自研。

核实 $ sed -n "8,40p" .venv/lib/python3.11/site-packages/agentscope/permission/_rule.py
核实 $ wc -l app/services/permission_service.py

08 / 一次调用前的六段流水线

框架的入口是「调用 Agent，得到回复」；平台的入口是一个 HTTP 请求，中间隔着计费、配额、人工确认与模型降级。

表 8　调用路径的分解

阶段 AgentScope 2.0.11 NanZi
预检 无对应位置 额度、权限、人工确认、可用模型
上下文与路由 中间件按需插入 拼装历史与记忆，选模型、选专家
装配与执行 Agent.reply() 装配提示词后执行，逐轮计 token 与成本
收尾 回复结束即结束 落库、记账、触发通知

为什么不同：框架没有「请求」这个概念，也就没有可拦截的位置。平台要在模型被调用之前完成四个判断——能不能用（停）、要不要人确认（拦）、记谁账上（记）、主模型挂了换谁（换），这四件事必须有一个统一入口，于是拆成六段，合计 1,965 行。它与框架的 pipeline 模块不是替代关系，两者不在同一抽象层。

核实 $ ls app/services/ai/pipeline/steps/
核实 $ wc -l app/services/ai/pipeline/steps/*.py | tail -1

09 / 运行时容错：两个框架不管的故障

这两个问题都来自线上，框架侧的行为是正确的——只是不足以让调用方知道「这次调用已经没救了」。

表 9　两类故障的处置

现象 框架侧 平台的处理
流静默挂起 HTTP 读超时按「相邻两次数据到达的间隔」计，中间层有心跳就永不触发 按 chunk 间隔单独计时，180 秒无数据即抛可重试异常
工具名不匹配 调用不存在的工具直接报错，提示语用模型看到的别名 白名单外拦截，并把「别名」与「服务名:工具名」的差异写进提示
超时分级 单一超时设置 请求级、工具级、流级三档，各自独立

第一次遇到是模型调用静默了 9 分钟：事件日志停在同一序号，既无异常也无重试，请求最后由兜底超时终结。查下来读超时语义本身没错——只要上游在发心跳，静默条件就不成立。所以要另一层判据：按数据块的到达间隔算，而不是按整条连接的存活算。

核实 $ grep -rn "IDLE_TIMEOUT_SECONDS =" app/services/ai/runtime/agentscope/
输出 DEFAULT_STREAM_IDLE_TIMEOUT_SECONDS = 180.0
